> 触发：实现曲线调色窗口；抓帧代码；直方图面板；AnimationCurve 调参；预设保存

## 要做什么

按 d-001 的设计，在 TA_show 项目里实现一个编辑器窗口：

1. 抓取 Game 视图当前帧并预览
2. 提取亮度 + R/G/B 直方图
3. 用亮度曲线和三条颜色曲线调节，实时预览
4. 显示调节前 / 调节后直方图对比 + 曲线 in→out 读数

## 环境

| 项 | 值 |
|---|---|
| 项目 | `D:\unity\unityProjectLocation\TA_show` |
| Unity | 2022.3.62f1c1（中国版） |
| 管线 | URP 14.0.12 |
| 进程 | Unity.exe PID 98384 |

## 已实现的内容

### 抓帧

- `ScreenCapture.CaptureScreenshotIntoRenderTexture(rt)` 抓 Game 视图最终合成结果（含所有相机与后处理）
- `Texture2D.ReadPixels` 读回 `Color32[]`
- 预览纹理用 `new Texture2D(w, h, RGBA32, false, linear: true)`，使 sRGB↔linear 两次转换互相抵消，预览与源像素一致

### 调色数学（CurveGradeProcessor）

```
1. 亮度曲线查表 -> 目标亮度 y1；增益 g = y1 / y0
2. RGB 同乘 g（保持色相）
3. R/G/B 三条颜色曲线各自在显示域直接映射
```

整条链路只用 256 项查找表，无逐像素 `Mathf.Pow`。

### 直方图

- 四组 256 桶：Luma / R / G / B
- 附带亮度分位统计：1% / 5% / 50% / 95% / 99% / 平均
- 绘制用 `Graphics.DrawTexture` + `GL.LoadPixelMatrix`，不逐柱调用 GUI
- 前后两条共用同一归一化基准，可直接比较分布位移

### 界面

- 左：预览（滚轮缩放、Alt+拖动平移）
- 右上：直方图（亮度 / RGB 叠加 / 蓝 / 绿 / 红）
- 右下：四条曲线 + 探查点 in→out 读数
- 底部：工作分辨率（0.25~1.0）、亮度计算域切换、预设存取、导出 PNG
- 工具栏：抓帧 / 重置曲线 / S 曲线去灰

## 当前状态

**调色链路已由 AI 自主验证通过**（无需人工点界面）。验证手段见 `CurveGradeSelfCheck.cs`
（无 GUI 自检）与 `CurveGradeBridge.cs`（文件轮询桥）。

### 根因：「调色后画面没变化」

完整因果链：

1. **抓帧路径 A（`ScreenCapture.CaptureScreenshotIntoRenderTexture`）在编辑器里基本失效**
   —— 2560×1440 中只有约 6.8 万个不透明像素（1.8%）。Game 视图窗口被遮挡时抓不到内容。
2. 抓回的帧 alpha 全为 0（全透明）。
3. `FrameHistogram.Build` 里有 `if (p.a == 0) continue;`，于是**整帧被跳过**，直方图全空。
4. 直方图空 → 曲线看上去毫无作用。

**修复**：
- 新增路径 B `CaptureByCamera()`：`Camera.Render()` 到 RT，**100% 像素不透明**，不依赖 Game 视图可见性。
- `CaptureFrame()` 两条路径都跑，取「不透明像素更多」的那条，并**强制 alpha=255**。
- 实测：路径 A 68625 个不透明像素，路径 B 3686400 个（满分），自动选中 B。

### 第二个 bug：预览纹理尺寸不匹配

`_previewTex` 原按**源分辨率**创建，而 `_outW/_outH` 是**工作分辨率**，
`UpdatePreviewTexture()` 里的 `_previewTex.width == _outW` 判断永远为假 →
**预览纹理从未被更新过**，永远显示抓帧时写入的原图。

**修复**：预览纹理改为按工作分辨率创建（`RecreatePreviewTexture`），
并在 `UpdatePreviewTexture` 里校验 `_outPixels.Length == w*h`。
另外 `Apply(false, false)` 的第二个参数是 `makeNoLongerReadable`，改为 `Apply(false)`。

### 第三个问题：性能

2560×1440 全分辨率处理耗时 **555ms**，拖动曲线会明显卡顿。
默认工作分辨率由 0.5 降到 **0.25**（像素数降到 1/16）。

### 验证结果（激进 S 曲线，AI 自主执行）

| 指标 | 调节前 | 调节后 | 变化 |
|---|---|---|---|
| 平均亮度 | 0.3227 | 0.3569 | +0.0342 |
| P50 | 0.2784 | 0.2275 | **−0.0510** |
| P95 | 0.6314 | 0.7843 | **+0.1529** |
| R 均值 | 0.2968 | 0.0604 | −0.2364 |
| G 均值 | 0.3071 | 0.4539 | +0.1468 |

**P50 下降 + P95 上升 = 中间调向两端分开 = 双峰**，
正是笔记里「S 曲线去灰」的定义，端到端语义与笔记一致。

- 全图 3686400 像素中 **100% 被改变**，平均通道差 **175.94**
- 20 个抽样探针 **全部 changed=True**

# 后续一：CPU 性能优化（用户追问"预览分辨率和 game 一致不行吗"）

## 根因：两处纯浪费

**浪费一**：`Process()` 开头就 `FrameHistogram.Build(src, ...)` 扫全分辨率源，
而 `histBefore` 只用于界面展示 → 改为先在**工作分辨率**抽小图再统计。

**浪费二**：逐像素含 3 次浮点除法、1 次 `y1/y0` 除法、3 次 `Nearest()` → 改为**整数 LUT**：

- `lumaOfR/G/B`：`byte[256]`，权重按 255 归一化后折进表项，三表相加即得亮度字节（乘除各 0 次）
- `gainOf`：`int[256]`，增益用 **1/256 定点**（0x100 = 1.0），消除除法
- `outR/G/B`：`byte[256]`，颜色曲线

逐像素只剩：3 次查表相加 → 1 次查表取增益 → 3 次整数乘 + `>>8`。

## 实测（2560×1440 源）

| 预览分辨率 | 输出像素数 | 优化前 | 优化后 | 提升 |
|---|---|---|---|---|
| 25% | 230,400 | 144 ms | **19 ms** | 7.6× |
| 50% | 921,600 | 230 ms | **76 ms** | 3.0× |
| 75% | 2,073,600 | 365 ms | **172 ms** | 2.1× |
| 100% | 3,686,400 | 563 ms | **304 ms** | 1.85× |

**结论**：预览分辨率与调色分辨率解耦——调参用低分辨率求流畅，成品质量由全分辨率导出保证。
全分辨率预览从"不可用"变为"可接受但拖不动"。界面已加**实测耗时提示**（滑块旁显示"上次 N ms"）。
待做改进：交互期低分辨率 + `MouseUp` 后自动补一次全分辨率。

# 后续四：【未解决·交接】抓帧缺后处理（发灰）—— 排查实录与接力指引

> **状态：未解决，交接给下一个 AI。**
> 用户报告：工具预览的图**明显比 Game 视图发灰**。本文记录已确证的事实、已排除的可能、
> 已修的缺陷、卡住的位置、以及两条可行岔路。**接手前请先读完本节再动代码。**

## 一、问题定性（已确证）

**根因**：`Camera.Render()` 走内置管线 legacy 路径，**不执行 URP 的后处理 pass**
→ 抓到的图缺 **Bloom / Tonemapping / Vignette** → 画面发灰、高光没被压、无光晕。

**证据链**：

| 证据 | 内容 |
|---|---|
| `WetPlanarReflection.cs:66` 代码注释 | 「`uac.renderPostProcessing = false; // RT 保持线性 HDR，辉光交给主相机`」→ 辉光在主相机上 |
| `SampleSceneProfile.asset` | `Bloom` / `Tonemapping` / `Vignette` 三个组件全部 `active: 1` |
| `URP-HighFidelity.asset`（激活的管线） | `m_SupportsHDR: 1`、`m_MSAA: 4`、`m_ColorGradingMode: 0`（LDR 模式，色调映射作用于 HDR 域） |
| `QualitySettings.asset` | `m_CurrentQuality: 2` = High Fidelity |

**决定性对照实验**（桥命令 `pptest`，切换 `cameraData.renderPostProcessing` 抓两次）：

```
相机 renderPostProcessing 原值 = True
开= 2560x1440  均值=0.319 P50=0.275 P95=0.624
关= 2560x1440  均值=0.344 P50=0.294 P95=0.682
差异像素 = 3686397 / 3686400 (100.00%)   平均通道差 = 30.489
```

结论：**后处理确实在生效且影响巨大**（100% 像素、平均差 30）。注意方向——
**关掉后处理时均值/P95 反而更高**（0.344/0.682 vs 0.319/0.624），这正是「发灰」的方向。

## 三、已确证的两个真实缺陷（已修，架构对了）

### 缺陷 1：程序集边界 —— 同名类型被编译进两个程序集

`CurveGradeCaptureBridge` 原先同时存在于 `Assembly-CSharp.dll` 与 `Assembly-CSharp-Editor.dll`。
**这是两个不同的静态类**：Editor 侧设的标志位，运行时 feature 读的那份永远看不到。

检测方法（可复用）：在编译产物的元数据字符串堆里找「类型名 + `\0`」：

```javascript
const needle = Buffer.from("CurveGradeCaptureBridge\0", "utf8");
buf.includes(needle)   // 对每个 .dll 分别判定
```

**修法**：把运行时部分移出 Editor 文件夹，并加 asmdef 隔离：

```
Assets/Project/Runtime/CurveGrading/
├── CurveGradeCaptureBridge.cs        抓帧请求/结果桥
├── CurveGradeCaptureFeature.cs       URP RendererFeature
└── TAShow.CurveGrade.Runtime.asmdef  autoReferenced: true（Editor 程序集自动引用）
```

### 缺陷 2：RendererFeature 放错目录

运行时类型必须放在**运行时程序集**（Editor 文件夹之外）。原先在 `Assets/Project/Editor/CurveGrading/` 下。

## 四、卡住的位置（核心，接手从这里开始）

即使 feature 正确挂在生效 renderer 上、程序集也隔离了，**URP 仍然一次都没调用它**：

```
AddRenderPasses 命中请求次数 = 0
CapturePass.Execute 调用次数   = 0
```

**推断**：编辑器空闲时 **URP 不渲染 Game 相机**，因此 `AddRenderPasses` 根本不会被调用。

而 legacy `Camera.Render()` 之所以"能工作"，是因为它是**我们主动调用**的，绕过了 URP 渲染循环。

**旁证**：抓帧的像素特征与修复前逐字节一致
（`center=RGBA(148,97,156,255)`、`corner00=RGBA(111,49,117,255)`），
说明请求始终走的 legacy 回退。

**当前 `CaptureByCamera` 的实现缺陷**：用的是**阻塞式轮询** ——

```
设标志位 → while(!done && now<deadline) { QueuePlayerLoopUpdate(); RepaintAllViews(); Sleep(4); }
```

`RepaintAllViews()` **不保证 Game 视图重新渲染相机**，所以 URP 不出帧、feature 不被调用。
最后超时 → 回退 legacy → 画面发灰。

## 五、两条岔路（请接力 AI 与用户确认后择一）

### 岔路 A：先验证 Play 模式（成本最低，建议先做）

运行时相机每帧都在渲染，feature 一定会被调用。
**验证方法（≤10 分钟）**：
1. 让用户进入 Play 模式，屏幕上有游戏在跑
2. 发桥命令 `capture`，读 `out.json`
3. 再发 `diagnose`，看 `AddRenderPasses 命中请求次数` 是否 > 0
4. 若 > 0 且画面有光照溢出 → 说明该方案可行，文档化「请在 Play 模式抓帧」即可，**代码几乎不用改**
5. 若仍为 0 → 走岔路 B

### 岔路 B：改成异步架构（工程量中等）

**不要再阻塞主线程**。正确形态：

```
点「抓帧」→ 设置标志位后立即返回（不 while 等待）
   ↓ 让编辑器自然走它自己的渲染循环
EditorApplication.update 里检查结果（或回调）
   ↓ URP 真正渲染那一帧时
feature 在管线内取图 → 投递回窗口 → 刷新预览
```

关键差别：**从「我逼编辑器渲染」改成「等编辑器自己渲染」**，URP 的 `AddRenderPasses` 才会被调用。

需要改成回调/异步的调用点：
- `CurveGradeWindow.Capture()`
- `CurveGradeWindow.CaptureAndExport()` → 以及它调用的 `DoCaptureAndExport()`
- `CurveGradeBridge` 的 `capture` / `export` 两个命令（桥是同步返回 payload 的，
  异步后需要改成「先返回 accepted，结果另写文件」或延长轮询）

**注意**：`DoCaptureAndExport()` 现在是 `public static` 且被桥/自检共用，改异步要一并调整这三处。

## 八、给接力 AI 的三条经验（避免重复消耗）

1. **不要相信统计数字就下结论**。本次 `selftest` 报的均值 0.319 一度让我以为后处理已生效，
   实际那只是 legacy 路径的值。**判定要走 `diagnose` 看 pass 调用计数**——计数为 0 就是没跑。
2. **Editor.log 会保留历史错误**，且本项目（Unity 中国版）有 `cn.tuanjie.codely.bridge`
   往日志刷大量 WebRTC 噪音。判定编译是否发生**看 DLL 时间戳**，不要看日志里有没有 `error CS`。
3. **改完代码必须重启 Unity 才生效**。本项目的增量编译管线不稳定（详见「试错记录」里的
   「最大坑」），重启是可靠手段。启动用 `cmd /c start "" /D <workdir> <exe> -projectpath <proj>`，
   **不要用 PowerShell `Start-Process`**（参数会被污染成 `System.Diagnostics.Process`）。

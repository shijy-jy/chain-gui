# Engram 设计批判与深水区分析

> **版本**：v2.0 · **日期**：2026-09-07 · **性质**：对 v1.0 论文稿的否定与重写
> **阅读前提**：本文每一处"现状"都经过代码核实（非 commit 消息转述）；每一处矛盾都给出了候选方案与决策标准。

---

## 0 · 对 v1.0 的自评：它错在哪

v1.0 论文稿的三个缺陷，本文逐一纠正：

1. **它是旧结论的形式化重排，不是新分析**。检索三层、遗忘四组件、QKV 映射全部来自既有文档的搬运；论文该做的"从证据出发的推导"缺失。
2. **现状盘点抄的是 commit 消息**。比如"watcher 覆盖外部写入"——事实是 watcher 测试只覆盖纯函数，事件循环从未被自动化验证过；"109 项测试"没有说明覆盖了什么、漏了什么。
3. **没有矛盾分析**。真正的设计困难不是"功能怎么做"，而是几个互相冲突的目标怎么裁决——v1.0 全部回避了。

结论先行：**v1.0 声称"图纸已校准定稿"是过早乐观。设计侧的硬仗还没开打，本文就是开打。**

## 1 · 现状的准确盘点（代码事实）

### 1.1 基线核实表

| 说法（来自 commit/文档） | 代码核实结果 |
|---|---|
| "MCP 核心操作层抽为共享 lib" | **半真**：`app_lib::mcp` 是纯函数层（不依赖 tauri/rmcp，设计正确），但它**新写了 walker/commands 的调用面**，没有把 GUI 的写入路径统一进来——`update_node`（GUI）与 `mcp::update_node` 是**两条并行实现**，D3 保护只活在 MCP 侧，GUI 侧没有 |
| "写入保护全覆盖" | **假**：MCP 侧有乐观锁+原子写；GUI 的 update_node 命令走的是旧路径（直接写文件），没有 tmp/rename 也没有 updated 比对。规划书 v1.1 的 D3 只兑现了一半 |
| "watcher 覆盖外部写入" | **部分真**：`start_watch` 监听 `nodes/` 顶层 `.md`（NonRecursive，300ms 去抖），MCP 写 nodes/ 能触发 ✓；但**归档/consolidate 未来写 archive/ 或 .chain 其它子目录时不会触发**，且 watcher 测试只测了纯函数 `rescan_and_emit`，事件循环零自动化覆盖 |
| "v2.7.0 已交付安装" | **真但危险**：安装目录 `D:\AIworkspace\Engram` 含 app.exe/engram-mcp.exe/uninstall.exe，**该目录不是 git 仓库**——安装版与开发版（G:\test1.x）的版本漂移没有任何验证手段 |
| "9 工具 31 项验收全绿" | 真（我自己跑过）。但 31 项覆盖的是**单进程顺序场景**：无并发双写、无错误注入、无大图、无编码边界（中文/公式/CRLF） |

### 1.2 三份代码的现实

- **G:\test1.x**：唯一 git 真相，开发迭代地；
- **D:\AIworkspace\Engram**：NSIS 安装产物，无版本控制；dsh profile 补丁 spawn 的是这里的 exe；
- **GUI 内置逻辑**：与 MCP 核心层共享 scanner/model，但**写入路径未共享**（见 1.1）。

这意味着：**"文件即唯一事实源"的代码层面镜像——"写路径也必须是唯一的"——目前不成立。** 两条写路径迟早漂移（GUI 改一处，MCP 忘改一处）。

### 1.3 测试的真实覆盖

| 覆盖 | 未覆盖 |
|---|---|
| scanner/walker/校验器（单测充分） | watcher 事件循环（notify 回调、去抖、重启） |
| MCP 全工具顺序冒烟 + 三边界 | 并发双写（GUI+MCP 同时）、进程崩溃中途写（tmp 残留）、时钟回拨 |
| 布局纯逻辑（交叉/碰撞） | 大图（n>400 走 fit 分支）、渲染性能 |
| — | 编码边界：GBK/UTF-8 混存、CRLF、中文 id 文件名 |

## 2 · 关键矛盾（v1.0 回避的全部问题）

### C1 · 治理权未定义：人与 AI 冲突时谁是权威？

乐观锁只防**覆盖**，不解决**语义冲突**：AI 想 append 一段结论，人刚刚手改了同一节点的结论——CONFLICT 返回后 AI 重试还是放弃？谁合并？

**候选方案**：
- (a) 冲突即冻结：CONFLICT 后节点进入 `[待裁决]` 前缀，人处理（GUI 近零改动）；
- (b) 分区治理：body 的"结论区"只许人写、"记录区"只许 AI append（frontmatter 标注分区）；
- (c) 现状维持（AI 放弃重试）——但这是回避，不是方案。

**决策标准**：哪个方案让"三个月后回看"最不容易出现两个互相矛盾的结论。

### C2 · 单工作区假设：GUI 是多工作区，server 是单目录进程

人可以在 GUI 里五个工作区来回切；AI 的 server 一个进程绑定一个 `--workspace`。后果：(1) 跨工作区记忆断裂——story 里的设定与 learning 里的渲染知识永远无法关联检索；(2) N 工作区 = N 进程 N 套工具命名空间，dsh 工具列表随工作区数线性膨胀（token 成本与选择负担）。

**候选方案**：
- (a) server 单实例多工作区注册表，工具加 `workspace` 参数（改动面大，但一次到位）；
- (b) 维持单工作区，跨区检索靠"引用节点"（在 A 库建指向 B 库节点的指针节点，零代码，语义弱）；
- (c) 接受 N 进程，只把最常用的 2–3 个工作区挂进 dsh（现状）。

### C3 · 编码线索的衰减：L1 依赖"写入时的 AI 预知未来的检索"

L1 要求写入时写 trigger 句——但写入的 AI 不知道未来的自己会用什么话术检索。**编码线索必然衰减，且没有反馈回路**：检索失败（零命中/命中无关）没有任何机制回写"该补线索了"。

**候选方案**：
- (a) recall 失败时返回"最近 N 次失败查询"进 `get_overview`，人/AI 择机补 trigger；
- (b) 检索日志落 stats，定期（consolidate 同期）生成"线索缺口清单"；
- (c) 嵌入模型兜底（承认 L1 只做加法不做保证）。

### C4 · 冷启动：强度统计上线即冷库

强度信号从上线才开始累积——**新库的前两周，所有记忆强度趋零，recall 排序近乎随机**，而这正是用户最需要记忆系统"开箱即用"的时期。

**候选方案**：
- (a) 冷启动兜底：强度为空时退化为"创建时间 + 图谱度数"排序并声明；
- (b) 首次全库扫描时用文件 mtime 初始化 `last_accessed`；
- (c) 接受冷启动（文档化，不解决）。

### C5 · HTTP 接入面与"本地优先"的信任边界冲突

HTTP+token 让云端 AI 够得到记忆，也把单用户本地工具变成了**网络服务**：token 存哪、谁签发、轮换吗、攻击面多大？"本地优先"是 Engram 的卖点，HTTP 是它的反面——v1.0 把两者并列却未分析冲突。

**候选方案**：
- (a) HTTP 仅限 localhost + 一次性配对 token（远程 AI 经用户本机转发，云端不直连数据）；
- (b) 公网 HTTP + 鉴权（接受新信任边界，写入安全守则）；
- (c) 不做 HTTP，维持 stdio（放弃"任意 AI"的时间表）。

### C6 · consolidate 蒸馏污染事实源

consolidate 的产物是 AI 生成的"骨架节点"，写入唯一事实源——**GIGO**：AI 摘要错了，事实源就被污染，且 I1"文件只存干净事实"与"AI 生成内容入文件"直接冲突。谁审？dry_run 只解决"先看后做"，不解决"做错了怎么办"。

**候选方案**：
- (a) 蒸馏产物落 `[蒸馏]` 前缀 + `derived: true` 标记，检索默认降权，人审后摘帽；
- (b) 蒸馏只做"候选建议"（不进图谱，只在 get_overview 输出），人用工具确认；
- (c) 不蒸馏，只归档。

### C7 · "GUI 零改动"红线的误读

红线本意是"**不破坏**现有交互"，但它正在被理解成"**不动**GUI"——涟漪权重通道、归档视图、冲突裁决界面全都需要动 GUI。红线不精确，L3 的 GUI 联动就永远"违规"。

**候选方案**：
- (a) 红线重述为"零破坏"：可加性改动允许（新增开关/视图），破坏性改动（改默认交互/布局语义）禁止；
- (b) 维持字面"零改动"，L3 全部藏在现有界面语义里（权重只影响亮度数值，不新增 UI）。

## 3 · 复杂状况分析（v1.0 完全缺失）

| # | 状况 | 分析 | 对策方向 |
|---|---|---|---|
| S1 | 双代码库漂移 | D 盘安装版无 git；exe 与源码版本无法核对 | 安装版内置 `--version` 输出 git 短哈希；发布脚本写版本文件；CI/脚本校验 |
| S2 | 三写路径格式漂移 | 人手写 / GUI 序列化 / AI 工具写——YAML 字段顺序、CRLF/LF、BOM、缩进三种风格 | 统一序列化层（GUI 与 MCP 共用同一 writer，即 C1 配套的"唯一写路径"） |
| S3 | 三进程并发 | dsh + Claude Desktop + GUI 同开同写：乐观锁的 `updated` 是**秒级**时间戳，同一秒内的两次写判不出冲突 | updated 升级为 ISO8601 毫秒 + revision 原子递增；或单写锁文件 |
| S4 | git 噪音 | stats 不进 YAML 解决了 watcher 风暴，但 AI 高频写节点仍制造 commit 风暴 | 文档化建议：AI 操作后人工 commit；或 AI 写入工具输出"建议提交信息" |
| S5 | 大图超限 | n>400 GUI 跳过力模拟只 fit；5000+ 节点时全库嵌入、get_overview 现算都会退化 | 分页/懒加载 + 增量索引；明确规模分级（<1k / 1k–10k / >10k）各给对策 |
| S6 | 嵌入的语言覆盖 | BGE-small-zh 以自然语言为主，LaTeX 公式、代码、中英混排的嵌入质量无实测 | 选型门槛测试集固定为"公式/代码/中文标题"三组样本，不达标不引入向量 |
| S7 | 故障注入 | server 崩溃中途写（.tmp 残留被扫描器误读？）、watcher 进程重启丢事件、系统时钟回拨 | tmp 命名加随机后缀且扫描器忽略隐藏 tmp；watcher 启动时全量重扫兜底；updated 用单调 revision 而非墙钟 |

## 4 · 重新校准的路线（决策点插桩）

v1.0 的 M6→M8 顺序在矛盾未裁决前是**假顺序**。修正为：

```
第 0 步（现在）：拍板 C1–C7 与 S1–S7 的候选方案（每项一行定论）
第 1 步：唯一写路径重构（S2/C1 配套）——GUI 与 MCP 共用 writer，D3 全覆盖
第 2 步：M6' = L1 规范（指南 v8）+ recall（含 C3 失败日志、C4 冷启动兜底、I7 降级链）
第 3 步：M7' = 归档 + 断边 + 强度统计（stats 落派生文件）+ watcher 事件循环自动化测试（S7）
第 4 步：M8' = 冲突检测 + consolidate（按 C6 裁决）+ HTTP spike（按 C5 裁决）
第 5 步：记忆图网络 4.1→4.2（按 C2 单/多工作区裁决决定索引布局）
```

每步的验收都附上"未覆盖项声明"（哪些状况未测，见 §1.3 右侧列）。

## 5 · 结论

Engram 的设计**远未定稿**：v1.0 的乐观来自回避。真正的难题不在"检索三层怎么做"，而在七个矛盾的裁决（治理权、工作区假设、线索衰减、冷启动、信任边界、蒸馏污染、红线语义）与七种复杂状况的对策。好消息是：现状盘点证明工程地基是诚实的（纯函数核心层、D1/D2 完整、乐观锁与原子写真实存在）；坏消息是：**写路径未统一**（C1/S2）是当前最大的结构性欠账，其余一切上层设计都建立在它之上。

**建议的下一步不是写更多文档，而是做一次 C1–C7 的逐项拍板**——每项我给过候选与决策标准，15 分钟过堂即可从"设计"进入"实现"。

# Engram 图结构 · AI 可用性分析与改进清单 v1

> 日期：2026-10-03 · 背景：三维图结构改造完成后，评估「这套图结构记忆系统 AI 用起来是否顺手」

---

## 0 · 一个必须先说清的事实

**AI 看不到那张三维图。** 3D 视图是人类观察面（球节点、树突、Bloom、脉冲），AI 通过 MCP 工具消费的是**数据层结构**：`nodes / edges / parent / rel / status / 正文 / origin`。

**推论**：3D 化对 AI 的可用性影响 ≈ 0 —— 除非把"人眼从图里看出的结构"翻译成**数据字段**暴露给 AI。所以"让 AI 更顺手"的着力点不在渲染，而在**接口是否携带结构语义**。

---

## 1 · AI 现在实际拿到什么（10 个工具）

| 工具 | 给 AI 的结构信息 |
|---|---|
| `get_overview` | 规模、`active_chain`（≤200 token 活跃链摘要，**只含非 success 节点**）、`chain_health`、`entry_hubs`（标题含索引词×100 + 度数，前 5） |
| `search` | 关键词命中（title/tags/body/骨架），返回 `id/title/snippet` |
| `recall` | 语义召回（余弦 + 强度加成），返回 `id/title/score/type/status` |
| `read_node` | 单节点全文 + 可选父/子列表 + 可选代码骨架 |
| `expand` | 1–2 层无向局部子图（nodes+edges 摘要） |
| `read_path` | 两节点最短路径 + narrative |
| `get_guide` | 协议全文（v18/v12） |
| `remember` / `consolidate` / `resolve_conflict` / `dialogue_status` | 写入、蒸馏、冻结自愈、账本状态 |

---

## 2 · 已经做对的地方（AI 视角）

1. **地图先行**：`entry_hubs` + `active_chain` 让 AI 不必盲搜就有入口。
2. **节点优先检索**：`search`/`recall` 默认只搜节点，对话不进语义召回 —— AI 拿结论，不陷进过程噪声。
3. **L1 编码规范**：`> 触发：` 句 + tags 是 AI 亲手写下的检索线索，直接决定召回上限。
4. **结构可推断**：单根树 + rel 三类型 + 状态机 → AI 能从 `parent`/`status` 推出"项目走到哪一步"。
5. **溯源与合规**：`origin`（哪次对话来的）、`conventions`（哪条规矩没守）、`legacy`（存量只读）—— AI 知道该信谁。
6. **实现级还原**：`read_node(include_code_map=true)` 给骨架全文。
7. **协议自报**：每个响应带 `guide_version`，AI 当次就能发现协议更新。

---

## 3 · 真正的痛点（按影响排序）

| # | 痛点 | 后果 |
|---|---|---|
| **P1** | **检索结果无结构上下文**：`recall`/`search` 只回 `id/title/score/type/status` | AI 要判断"这条是不是我要的、它在链里什么位置"，必须再 `read_node` —— **一次检索变三次调用** |
| **P2** | **没有导读顺序**：接手项目最需要"按什么顺序读哪 8 个节点"，只能自己从 `entry_hubs` 摸索 | 接手成本高、易漏关键节点（失败/阻塞/未闭环） |
| **P3** | **线索缺口（gaps）没有出口**：`recall` 未命中会写 `stats.gaps`，但没有工具读它 | AI 不知道"用户找过什么但没找到"，无法主动补节点 |
| **P4** | **`expand` 太弱**：1–2 层、无向、无排序、无摘要 | 拿到一堆 id 还要逐个读，等于没用 |
| **P5** | **无健康度聚合**：`updated` / index `stale` / `origin` 的指南版本 / 未闭环 task 分散各处 | AI 无法一条调用回答"哪些记忆可能过时/待补验证" |
| **P6** | **节点无一句话摘要**：只能靠 `active_chain` 猜，或读全文（长正文成本高） | 上下文预算被正文吃掉 |
| **P7** | **`active_chain` 只显示非 success** | AI 看不到"已完成部分的骨架"，容易重复劳动 |
| **P8** | **强度维度实际失效**（clamp 归零，已登记专项） | 召回排序里"记忆强度"这一维是死的 |
| **P9** | **人机心智不一致**：3D 神经元布局弱化了层级；而链协议（分析模式）是严格层级 | 人看图得"球状结构"，给 AI 的指令容易丢层级语义 |

## 4 · 改进清单（按性价比排序）

### P0 —— 低成本、直接减少调用次数【已落地，契约 v9】

1. **检索结果附结构上下文**
   `search` / `recall` 每条结果增加：`parent`、`depth`、`children_count`、`updated`、`origin`、`archived/derived`。
   → AI 一次调用即可决策"读哪条、跳过哪条"。

2. **线索缺口出口**
   `dialogue_status`（或新工具 `gaps`）返回 `stats.gaps`（最近未命中的查询）+ **未闭环 task 清单**。
   → AI 主动把"用户找不到的东西"补成节点 —— 这是记忆系统自我修复的闭环。

3. **`get_overview` 增 `structure` 块**
   深度分布直方图、叶子/孤儿/跨链数、每个 `entry_hub` 的**子树规模**。
   → 把"人眼从 3D 图看出的结构"翻译成 AI 能读的数据。

### P1 —— 修订后落地（用户 2026-10-03 审议）

4. ~~**新工具 `tour`（导读路径）**~~ → **撤销，改为 `expand.direction` + `hop`**。
   撤销理由（用户）：AI 遍历本就自适应——还原分析模式的项目时它**从根节点开始向下读**，信息量逐级指数增加，读多少由它自己判断；开发模式下它**随机读不在同一条链上的节点、每次不重复**。软件预设一条固定导读路径，等于把这个自适应过程降级成一次性导览，还会把"读原文"替换成"读摘要"。
   替代方案：`expand(id, depth, direction=children|parents|both)` + 每节点 `hop`（层距）—— **给导航数据，不给导航结论**。
5. **`expand` 升级** → **已落地**：`direction`（children 自根向下 / parents 回溯来源 / both 默认）+ 每节点 `first_line`。字段名从 `with_summary` 改为 `first_line`：**它是机械截断，不是摘要**。

6. ~~**节点摘要（gist）**~~ → **撤销，改为 `first_line` 机械截断**。
   撤销理由（用户）：**读节点内容本身就是放弃读原文**，节点是对原文的整理；若再让软件对节点做二次概括，等于把"整理"再压缩一层，只会丢失更多信息。
   替代方案：`expand` / `search` 的 `first_line` 严格只做 120 字节机械截断，禁止被当作"摘要"二次加工；`coverage.unread_ids` 支撑"跨链随机、每次不重复"的读取策略。

### P2 —— 结构性（人机同源）【已落地】

7. **结构指标入接口** → **已落地**：`degree / depth / children_count / subtree_size` 四处同源——① 后端 `structure_index`（AI 读的 `search`/`recall`/`expand`/`read_node` 结果 + 契约 v9 已带 `degree`）；② 后端 `subtree_sizes`；③ GUI 快照注解 `ops::snapshot_view`（`scan_chain` / `chain-changed` / 代码挂载两条命令都走它）；④ 显示层**不再自己重算**，球径直接读后端 `degree`，信息栏显示这四个数。
   → **人看到的球多大 = AI 读到的 degree**；"人看图看出的重要性"与"AI 导航读到的数字"终于是同一口径。

8. **布局可选强化层级** → **已落地**：新增布局算法选择（自动 / 层级球壳 / 神经元）。**自动 = 按工作区模式**：分析模式用**层级球壳**（半径 = depth × 层距，同层同壳，锥角随深度收窄；不做力导向松弛，层壳不被揉散）——层数即 AI 读到的 `depth`；开发模式保持三维神经元展开。手动可锁定任一种。

9. **覆盖遮挡** → **已落地**：图例默认折叠成一行（点标题展开，偏好持久化）；相机取景改为把内容居中到**未被浮层压住的自由区**（`measureInsets` 量图例/搜索框/缩放控件的贴边尺寸 → `centerAll` 按相机基换算像素偏移 + 按自由区放大距离）。

10. **冷启动扫描并行化** → **已落地**：文件层扫描改为按文件并行（`std::thread` + 工作队列，零新依赖），合并时**按文件列表顺序**回填，输出与串行逐字节一致。

11. **记忆层专项**（已登记，未做）：强度 clamp 归零 → 让"记忆强度"这一维真正进入排序。

## 5 · 结论

- **3D 改造优化的是"人怎么看"**，对 AI 的直接收益为零；
- AI 侧的可用性**中等偏上**：入口推荐、节点优先检索、溯源与合规标记都已到位；
- 但**每次检索都要二次调用补上下文**、**没有导航数据**、**缺口没有出口** —— 这三件是投入产出比最高的改进；
- 一句话：**让 AI 顺手的关键不是把图做漂亮，也不是替它规划读法，而是让接口携带结构语义**（结构上下文 / 方向与层距 / 覆盖度 / 缺口 / 机械截断）。
- **边界（用户定调）**：软件只提供**导航数据**（结构、方向、层距、覆盖度），**不提供导航结论**（导读顺序）；只做**机械截断**，**不做二次概括** —— 读节点正文就是放弃读原文，任何"帮 AI 省一次读"的再加工都是在替它丢信息。

## 6 · 实测（release 二进制 + MCP stdio，只读工具）

`tools/_collect_golden.mjs` 同款 stdio 探针（`_probe_nav.cjs`）直接打真实工作区：

| 工作区 | 形态 | `get_overview` | `expand(root,2,children)` | `dialogue_status` | `search` |
| --- | --- | --- | --- | --- | --- |
| `G:\ta` | 分析模式 74 节点 / 深度 11 | 666ms · 2.7KB | 32 节点 · 28ms · 15.4KB | 26ms · 1.1KB | 83ms · 5.1KB |
| `G:\perf1500` | 1500 节点 / 深度 7 | 冷启 13.5s，热 0.42s | 44 节点 · 0.37s · 19.3KB | 0.36s | 0.38s |

- **层级优先跑得通**：`structure.root_ids = ["g-001"]` 一步定位唯一入口；`expand` 逐级向下给 5 → 32 个节点，每行都带 `hop / depth / children_count / first_line`，一次调用就够决定"下探 d-006（18 子）还是先读 t-003"。
- **跨链随机跑得通**：`coverage` 直接报 `read 59 / total 74 / unread 15` 并给出 `unread_ids`（封顶 30 条）——AI 抽签不重复，读到即覆盖；`perf1500` 上同样正确（`read 1 / unread 1499`）。
- **冷启动是唯一的性能短板**：1500 节点首次扫描 13.5s（磁盘冷 + 1500 次文件读），之后每次调用 0.4s 级；与本次新增字段无关（结构索引是 O(n+e)）。**待办**：首次扫描可加增量/并行化。
- **legacy 工作区同样受益**：`G:\ta` 账本 `records = 0`，但 `coverage` 走 `stats.reads_map()`，老库照样能规划读取路线。
- `first_line` 在真实数据上取到的是 `> 触发：…`（按指南 §6 写在正文开头的触发句）——**机械规则就是"首个非空、非标题行"**；不在这里做"跳过触发句"的判断，那属于替 AI 加工内容，用户已明确否决。

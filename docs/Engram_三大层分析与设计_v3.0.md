# Engram 三大层分析与设计

> **版本**：v3.0 · **日期**：2026-09-07 · **性质**：按"软件层 / 记忆层 / 落地层"三大方向重组的完整设计分析
> **继承**：v2.0 批判版的全部代码核实结论（写路径未统一、watcher 边界、双代码库漂移、测试盲区）与七个矛盾 C1–C7、七种状况 S1–S7；本文按三层重新归位，并补全每层的模块结构设计。

---

## 层次总览

```
┌─────────────────────────────────────────────────────────┐
│ 软件层：对接与使用                                        │
│ 谁（人/哪种 AI）怎么连进来、用什么形态用、冲突时谁说了算     │
├─────────────────────────────────────────────────────────┤
│ 记忆层：AI 如何使用与管理记忆库                            │
│ 写（编码）→ 存（组织）→ 读（检索）→ 维护（巩固/遗忘）      │
├─────────────────────────────────────────────────────────┤
│ 落地层：代码落地                                          │
│ 整体架构 → 逐模块结构 → 实现顺序 → 质量验收 → 版本交付      │
└─────────────────────────────────────────────────────────┘
```

三层的关系：**软件层决定"谁怎么连"，记忆层决定"连上之后干什么"，落地层决定"怎么变成代码"**。上一层的每一个设计决策，都必须能在下一层找到落点；找不到落点的设计是空话。

---

# 第一层 · 软件层（对接与使用）

## 1.1 目标

让**所有人（开发者）+ 所有 AI（本地与云端）**以各自的自然形态用上同一份记忆——人用 GUI 看和治，AI 用工具读写——且双方长期共存、冲突可裁决。

## 1.2 子问题分解

| 子问题 | 内容 | 现状核实 |
|---|---|---|
| S-1 接入面 | stdio（本地 AI）→ HTTP（云端 AI）→ 多设备 | 仅 stdio 已交付；HTTP 未启动 |
| S-2 使用等价 | GUI 交互 ↔ AI 工具的对应关系 | 9 工具 = 搜索/涟漪/聚焦/全局的翻译，已成立 |
| S-3 治理权 | 人与 AI 语义冲突时谁是权威（v2.0 C1） | **未定义**——乐观锁只防覆盖不解决冲突 |
| S-4 多工作区 | GUI 五工作区 vs server 单目录进程（v2.0 C2） | 断裂：跨区记忆无法关联 |
| S-5 分发与版本 | 安装包、双代码库漂移、工具契约（v2.0 S1） | 安装版无 git，漂移无验证 |
| S-6 使用体验红线 | "GUI 零破坏"而非"零改动"（v2.0 C7） | 红线表述不精确 |

## 1.3 关键设计与候选方案

**接入矩阵**（目标形态）：

| 客户端 | 传输 | 能力 | 信任级别 |
|---|---|---|---|
| dsh / Claude Code / Cursor / Cline / Windsurf | stdio | 全工具 | 本机可信 |
| 云端 AI（Coze/API 型） | HTTP + token | 全工具（经用户本机转发） | 半可信 |
| 人（开发者） | GUI | 全能力 + 治理权 | 最高权威 |

**S-3 治理权——倾向方案 (a)「冲突即冻结」**：CONFLICT 后节点进入 `[待裁决]` 前缀，人处理。理由：Engram 的立身之本是"人可治"，把裁决权交给人是唯一自洽的选择；分区治理 (b) 作为远期增强。

**S-4 多工作区——倾向方案 (a)「单实例多工作区」**：server 单进程挂工作区注册表，工具加 `workspace` 参数。理由：C2 的 N 进程方案会随工作区数线性膨胀 dsh 工具列表；而"引用节点"(b) 语义弱。此决策**必须在落地层重构写路径时一并做**（一次重构解决两个问题）。

**S-5 版本矩阵**：四版本独立管理——GUI 版本 / mcp 工具契约版本 / 指南版本 / 索引格式版本；安装版 `--version` 输出 git 短哈希；发布脚本写入版本文件，双代码库漂移从此可查。

**S-6 红线重述**：「零破坏」——加性改动允许（新增开关/视图/参数），破坏性改动（改默认交互/布局语义/删减工具）禁止。

## 1.4 验收

- 任一客户端（含云端）10 分钟内完成"读全局→搜→读→写→GUI 可见"闭环；
- 人与 AI 冲突产生 `[待裁决]` 而非静默覆盖；
- 版本矩阵任一组件可回答"现在跑的是哪一版"。

# 第二层 · 记忆层（AI 如何使用与管理记忆库）

## 2.1 目标

定义记忆库的完整生命周期：**写（编码）→ 存（组织）→ 读（检索）→ 维护（巩固/遗忘）**，并明确每个环节的规则、边界与理论依据。

## 2.2 子问题分解

### M-1 写入与编码（怎么把记忆放进来）

| 项 | 设计 | 状态 |
|---|---|---|
| 编码规范 | trigger 句 + tags 写入指南 v8（L1，检索上限的决定者） | 未启动 |
| 写入守门 | 同名拦截（force 确认）、rel 三类型词表、乐观锁 + 原子写 + 串行队列 | MCP 侧已交付 |
| 写路径唯一 | GUI 与 MCP 共用同一 writer（v2.0 S2/C1 最大欠账） | **未做** |
| 关系语义 | rel 三值 + rel_desc（边说明，≤60 字，边嵌入语料） | rel 已交付；rel_desc 待 GUI 侧 |

### M-2 存储组织（记忆以什么形态存在）

- **事实源**：节点 `.md`（YAML 头 + 自由正文），只存干净事实——不变式 I1；
- **派生物**：`.chain/index/`（嵌入）、`.chain/stats.json`（强度统计）、审计日志——全部可重建，不进 YAML（防 git 噪音与 watcher 风暴）——不变式 I2/I8；
- **骨架原则**：蒸馏产物是骨架而非全文摘要（海马体索引理论的工程化）。

### M-3 检索读取（AI 凭什么想起该想的）

三层递进 + 两个被 v1.0 回避的问题：

| 层 | 内容 | 优先级 | 待解决问题 |
|---|---|---|---|
| L1 编码侧 | 写入时写触发线索 | P0（零代码） | **C3 线索衰减**：写入的 AI 无法预知未来的检索话术，且无反馈回路——方案：recall 失败日志入 stats，consolidate 同期产出"线索缺口清单" |
| L2 语义召回 | `recall(query,k)` 向量索引（可插拔嵌入，默认本地；降级链 I7） | P0 | **C4 冷启动**：新库前两周强度趋零、排序近随机——方案：强度为空时退化为"创建时间+图谱度数"并显式声明 |
| L3 联想扩散 | `expand` 升级扩散激活，rel_desc 作边权 | P1 | 度归一化消 hub 偏置；权重三因子可解释 |

### M-4 维护治理（记忆库怎么不腐烂）

四组件（含两个深水区）：

1. **强度信号**：`f(访问次数, 最近访问, 图谱度数, importance)` 落 stats.json；importance 首版单档 `high`、只影响排序不参与归档（防 AI 自评注水）；保守默认参数，真实数据回归后再调。
2. **归档而非删除**：`archive_node`（`archived: true` + `[归档]` 前缀，GUI 零破坏）；`unlink_nodes` 补断边不对称；90 天未触达为初版阈值。
3. **语义冲突检测**：create 时高相似 hint，复用 `alternative` 边表达竞争——零新增概念。
4. **巩固蒸馏**：`consolidate` 反刍，dry_run 默认；**C6 待裁决**：蒸馏产物是 AI 生成内容写入事实源——倾向方案 (a) `derived: true` 标记 + 检索默认降权 + 人审摘帽。

### M-5 记忆图网络（终态）

QKV 图元映射（Q 现算 / K 派生索引 / V 即文件 / 图结构与生命周期作先验）；注意力权重 = `sim × rel_weight × life_prior`（度归一化）；三子阶段 4.1 向量索引 → 4.2 图注意力检索 → 4.3 自适应（微调有明确门槛）。**"遗忘即检索"闭环**：M-4 的强度信号直接成为 M-5 的生命周期先验。

## 2.3 记忆生命周期状态机（记忆层总图）

```
        写入(守门)            检索命中            长期未触达(90d)       人审摘帽
新建 ──────────► 活跃 ────────► 强度↑(巩固) ──┐                 ┌──► 蒸馏骨架(derived)
                 │ ▲                        │ 建议归档        │
                 │ │                        ▼                 │
                 └ └── 触达回写 stats ◄── 归档([归档]前缀) ────┘
                                             │
                                             └── unlink 断边 / 人可恢复
```

# 第三层 · 落地层（代码落地）

## 3.1 目标

把软件层与记忆层的每个决策变成代码：整体架构 → 逐模块结构 → 实现顺序 → 质量验收 → 版本交付。**任何一个设计找不到落点，就退回设计层。**

## 3.2 整体架构（三进程拓扑）

```
进程 1 · Engram GUI（Tauri）      进程 2 · engram-mcp（stdio server）      进程 3 · 索引/统计服务（可选）
  可视化/编辑/治理                   9+ 工具、写守门、串行队列             嵌入与 recall（远期可并入进程 2）
        │                                 │                                    │
        └────────────── 共享 lib（model/scanner/唯一 writer）─────────────────┘
                                  唯一事实源：.chain/nodes/*.md
                                  派生物：.chain/index/ · stats.json · audit
```

**关键重构（落地层第 1 步）**：把 GUI 的 `update_node/create_node/set_parent` 与 MCP 核心层统一到同一个 writer 模块——D3 保护（乐观锁+原子写+串行队列）从此对两条路径全覆盖，并顺带解决 S-4 单实例多工作区的 `workspace` 参数。

## 3.3 逐模块结构（文件级落点）

| 模块 | 归属 | 落点（crate/文件） | 职责 | 依赖 | 验收 |
|---|---|---|---|---|---|
| 共享 writer | lib | `src-tauri/src/core/writer.rs`（新） | 唯一写路径：守门/乐观锁/原子写/串行队列 | model/scanner | GUI 与 MCP 走同一路径（单测断言同一代码路径） |
| MCP 核心层 | lib | `src-tauri/src/mcp/mod.rs`（已有） | 9 工具纯函数 + 未来 recall/archive/unlink/consolidate | core/writer | 31 项 E2E（已有）+ 新工具各自用例 |
| MCP 协议层 | bin | `src-tauri/src/bin/engram-mcp.rs`（已有） | rmcp 映射 + write_lock + 握手指南下发 | mcp | 协议测试脚本 |
| 索引模块 | lib（新） | `src-tauri/src/index/`（新） | K 嵌入存取（.chain/index/）、哈希校验、全库重嵌 | 嵌入后端（可插拔） | 三组中文同义词实测 + 重嵌 <1min/千节点 |
| 统计模块 | lib（新） | `src-tauri/src/stats/`（新） | 触达计数、强度公式、线索缺口清单 | mcp（read 路径埋点） | 连续使用数据回归 |
| 归档/蒸馏 | lib（新） | 并入 mcp 工具 + core/writer | archived 前缀、unlink、consolidate(dry_run) | writer | C6 裁决后的语义验收 |
| GUI 联动 | 前端 | `App.svelte` 加性改动 | 归档视图开关、权重通道开关、[待裁决] 徽标 | — | 零破坏回归（涟漪/聚焦/侧栏全量手测） |
| watcher 加固 | lib | `src-tauri/src/watcher/mod.rs` | 事件循环自动化测试、启动全量重扫兜底、archive 目录监听扩展 | notify | ignored 集成测试：server 写→2s 内事件 |

## 3.4 实现顺序（决策点插桩）

```
第 0 步  拍板：S-3 治理权 / S-4 多工作区 / C6 蒸馏 / C5 HTTP / C4 冷启动 五项各一行定论
第 1 步  唯一写路径重构（core/writer）+ 单实例多工作区参数（若 S-4 选 a）  ← 一切的地基
第 2 步  M6'：指南 v8（L1 编码规范）+ recall（L2，含降级链与失败日志）
第 3 步  M7'：archive/unlink + stats 强度统计 + watcher 事件循环自动化
第 4 步  M8'：冲突检测 + consolidate（按 C6 裁决）+ HTTP spike（按 C5 裁决）
第 5 步  记忆图网络 4.1 → 4.2（索引布局按 S-4 裁决）
```

## 3.5 质量与验收体系

- **测试矩阵**（补齐 v2.0 识别的盲区）：

| 维度 | 手段 |
|---|---|
| 单元 | 共享 writer/索引/统计/BFS/交叉 全覆盖 |
| 协议 | stdio JSON-RPC 驱动脚本（已有 31 项，扩展并发与故障用例） |
| watcher | ignored 集成测试：真实 notify + 子进程 server 写入 + 2s 断言 |
| 并发 | 双进程同写压力用例：断言要么 CONFLICT 要么 [待裁决]，绝不静默覆盖 |
| 故障注入 | 写中途杀进程（tmp 残留不污染扫描）、时钟回拨（revision 单调性兜底） |
| 大图分级 | <1k / 1k–10k / >10k 三档性能基线 |
| 编码边界 | GBK/UTF-8 混存、CRLF、中文 id 文件名 |
| GUI 回归 | 零破坏清单：涟漪/聚焦/侧栏/滑条/切换图谱全量手测 |

- **验收声明制**：每份发布说明附"未覆盖项声明"（哪些状况未测）。

## 3.6 版本与交付

- 四版本矩阵（GUI / 工具契约 / 指南 / 索引格式）进 CHANGELOG；
- 安装版 `--version` 输出 git 短哈希；发布脚本双库校验；
- 每里程碑交付：安装包（exe 附带）+ 客户端文档更新 + 未覆盖项声明。

# 结语

三层框架的价值在于**问责制**：软件层的每个"支持"承诺（任意 AI、冲突裁决、多工作区）都能在记忆层找到规则、在落地层找到文件和测试；反过来，记忆层的每个设计（线索、强度、蒸馏）都能回答"用户/AI 在软件层会怎么感知它"。v2.0 的七个矛盾被归位为：软件层裁决 C1/C2/C5/C7，记忆层裁决 C3/C4/C6，落地层用"唯一写路径重构"一次性兑现其中三个。**下一步依旧是那一步：拍板，然后重构写路径。**

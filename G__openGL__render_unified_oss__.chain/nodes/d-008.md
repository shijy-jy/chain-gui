> 触发：学习型架构规划书评审

# 评审对象

`docx/render_unified_oss_learning_architecture_v2_20260902.md`（2026-09-02 v2.0，取代按产品排期的 v1）

# 总评

**定位纠偏正确、机制有现状资产支撑、第 4 节映射表是真正可执行的核心交付物**——这是一份"从代码里长出来"的架构，不是理想主义空文。§2.2 六条现状资产已逐一在代码中核实属实（ShadingModel 枚举 t-009 / enable_spatial_+accumMode_+enable_temporal_+enable_optix_ 开关 / IRenderBackend 全虚函数默认实现 / 分层目录 / static_assert(sizeof(Material)==64) / --autotest），denoising 层实测无反向 include，单向依赖现状成立。

# 亮点

1. v2 对 v1 的纠偏正确：学习渲染器的架构约束是"为未知模块预留落点"，不是产品排期
2. 单向依赖铁律把"牵一发动全身"变成"编译器帮你数清全身"，且现状已基本符合——不是需要先重构的理想
3. 四机制全部有代码先例（新文件/新开关/新后端/契约防线），可立即执行
4. 第 4 节映射表把"学习主题→接入方式"决策前置，对非架构出身的使用者最友好
5. 风险表诚实（核心层不够用/后端膨胀/开关爆炸/语义漂移）；毕业机制避免只进不出
6. 口诀+清单的表达符合使用者画像

# 问题与修订建议（有主见的批评）

1. **raster/ 显示层在三层图没落位**：display.cpp（CUDA-GL interop）被 backends 与 app 双向使用，映射表应补一行（能力层或独立显示层）
2. **UI 分区缺绑定协议**：G2 只说"每个主题加一个入口"，未定义面板与新后端/新开关的绑定方式——建议把 IRenderBackend 的 tune* 机制泛化为面板描述符，或明确各主题面板直接操作其新类（t-005/t-006 的材质面板已是"直接操作"先例）
3. **§8 回归"像素一致"对 PT 不成立**：路径追踪是随机算法——Raster 可像素级一致；PT 只能统计一致（固定 RNG 种子 + PSNR/均值差阈值）。回归口径需按后端区分
4. **契约防线承诺过强**：目前只有 Material→raster_gpu_backend.cu 一处 static_assert；PtMaterialPod 与 denoising 侧 POD 镜像无防线。"不存在漏改悄悄出错"以防线完备为前提——G1 应包含"每个 POD 镜像都加 static_assert"（t-003 陈旧 obj 事故即防线缺口的反例）
5. **契约变更会高频化**：映射表里纹理/场景图/光源都要动 Scene/Material——建议先做预留字段（textureIndex 占位、Material 预留槽），把高频变更摊薄（呼应 d-003 的 64B 布局约束与 d-006/t-009 的 BSDF 扩展）
6. **基准场景集 G3 过薄**：Cornell+一个 obj 覆盖不了光源/降噪/相机类主题——建议"每主题类别一个基准场景"并写进 SOP 第 5 步
7. **A/B 对比呈现方式未定义**（分屏/截图/统计表），SOP 第 5 步可再具体
8. **与 .chain 图谱脱节**：工程已有链协议（g/d/t/v + PROCESS_LOG），建议"一主题一 commit"绑定链任务闭环（commit 引用 t-xxx、学习结论沉淀图谱节点），双轨互索引

# 结论

方案总体成立。建议按 1/3/4/5 修订后作为 G1（ARCHITECTURE.md）底稿落地；2/6/7 在对应功能动工时补充；8 并入链协议使用习惯。

> 触发：面板不显示根因；DPI 虚拟化挤出可见区

# 用户反馈（t-031 修复后）

控制台: font atlas 2048x2048 ✓ / ImGui ready ✓ —— 但"现在还是没又ui面板"。

# 诊断过程（本机像素取证 + 程序自诊断）

1. 屏幕网格采样: 场景渲染正常（红色 Cornell 墙 ✓），但窗口客户区 = **1066×600 而非 1600×900**（1066 = 1600/1.5）
2. 程序自诊断日志: 程序内部视角 client=1600×900、img=(0,90 1280×720)、panelX=1280、imguiReady=1 —— **程序内部一切正确**
3. ImGui 提交几何: 3 个 cmdlist / 3116 顶点 ✓ 正常提交
4. 帧缓冲 PPM 取证（零坐标歧义）: **面板在 x=1280 处有完美硬边界，面板底色精确 (25,25,27)，滑条轨道/滑块俱全 —— 面板确实渲染了**

# 根因

**DPI 虚拟化 → 程序坐标空间与实际窗口分裂：**

- vendored ImGui 的 `ImGui_ImplWin32_EnableDpiAwareness()` 在 Win10+ 用 **`SetThreadDpiAwarenessContext`（线程级）** —— 无 manifest 的 DPI-unaware 进程中，线程上下文不能高于进程上下文 → **调用是 NO-OP** → 进程始终 DPI-unaware
- 高分屏（150%/175%）上 unaware 窗口被虚拟化/压缩到 ~1066×600 可见区，但程序内部仍按 1600×900 布局 → 面板放在 x∈[1280,1600] → **完全落在可见区之外** → "面板不显示"（场景因锚定左上角仍大致可见）
- t-029 时代用户能看到面板（乱码版）是因为当时窗口未被压缩的场景不同；t-030 加入的 EnableDpiAwareness 无效调用掩盖了此问题

# 修复

- `enablePerMonitorV2Dpi()`：直接调 **user32 `SetProcessDpiAwarenessContext`（进程级）**，建窗前调用；回退链 shcore `SetProcessDpiAwareness` → `SetProcessDPIAware`
- `WM_DPICHANGED` → updateViewport()；滑条标签列宽随 dpiScale_ 缩放
- 取证后清理全部诊断代码（ui_diag.log / framebuffer.ppm / drawdata 日志）

# 验证证据（已核实）

- 程序日志: `client=1600x900 img=(0,90 1280x720) panelX=1280 uiVisible=1 imguiReady=1 dpi=1.50`
- 帧缓冲扫描: x=1240..1272 场景(123,123,123) → x=1288 面板底色 (25,25,27) → x=1296 滑块亮部 → 边界锐利 ✓

# 教训

1. ImGui vendored 后端 ≠ 权威：`EnableDpiAwareness` 的线程级调用在 unaware 进程是死代码（Win32 规则：线程上下文 ≤ 进程上下文）
2. "程序日志正常" ≠ "屏幕正常"：unaware 进程的坐标空间与实际窗口可以完全分裂——排查这类问题要用**帧缓冲取证**（glReadPixels 无坐标歧义），屏幕截图受调用方 DPI 状态污染，极易误判（本次我被自己的采样坐标坑了多轮）
3. 教训沉淀：布局类问题按"程序视角 → 帧缓冲 → 屏幕"三层递进取证

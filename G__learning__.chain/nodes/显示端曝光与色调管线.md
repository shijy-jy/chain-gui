# 方案 · 显示端：曝光→clamp→gamma（把解变成屏幕像素）

> 源自 2026-09-03 对话：学习者指着 restir_learn 面板问"这个曝光参数怎么理解，我不懂"。
> 回答口径 = 本节点：曝光不是渲染的一部分，它是**解完之后**的显示层第一个旋钮。

## 问题：为什么需要曝光？

渲染方程解出来的 radiance $L(x\to\omega)$ 是**任意单位制的 HDR 数**——光源功率是作者随手定的（灯=15、白墙反照≈0.66），$L$ 本身没有任何"天然锚点"；而屏幕只能显示 $[0,1]$（8bit = 0–255）。两者之间必须有一个**定标映射**，曝光就是它。

摄影上的对应物：曝光 = 到达传感器的光能量，$H = E\cdot\Delta t$（辐照度 × 快门时间），快门×2 = +1 EV = 亮度×2。渲染里没有真实快门，于是把"感光元件的总增益"浓缩成一个乘数 $g$——**面板曝光 = 帧缓冲的感光增益**。

## 引擎里的精确位置（restir_learn，packColorToRGBA8Kernel）

```
线性累积 radiance（PFM 原样导出，曝光前）
   → ×exposure（曝光：整帧缩放）
   → clamp [0,1]（过曝钳位成纯白）
   → ^(1/2.2)（gamma ≈ 显示器传递函数）
   → ×255 打包 8bit（BMP = 所见即所得）
```

即 $L_{\text{sdr}} = \mathrm{clamp}(g\cdot L)$，$C = L_{\text{sdr}}^{1/2.2}$。默认 $g=0.6$（当年对照 CPU 参考画面标定）。

## 三个关键性质（辩证要点）

1. **显示层 ≠ 求解层**：曝光不碰采样、不碰积分、不引入/消除偏差。它把信号和噪声同时放大 $g$ 倍，相对噪声 $\sigma/\mu$ 不变——**拖曝光不会让画面更干净**。三层划分（求值/积分/采样）之外，色调是"解之后"的第四层。
2. **与帧间累积正交**：$\mathrm{mean}(g\cdot x_i)=g\cdot\mathrm{mean}(x_i)$，线性缩放与等权平均可交换——所以 UI 上拖曝光**不清累积**，而移动相机才清（对照 辩证卡⑬）。
3. **语义等价**：把全部灯功率 ×$g$ 重新渲染 ≡ 显示端乘 $g$（LTE 对光源线性）。引擎永远做廉价版（矩阵末端的乘法），不重跑路径追踪。

## 那调它到底在调什么？——只在两个"非线性边界"起作用

线性缩放本身不丢信息，丢信息全在两端：

- $g$ 太大 → 高光（灯、镜面高光）顶到 1 被 **clamp 砍成纯白**：HDR 里 15 的灯和 1 的墙只能保住一个，砍掉的部分（颜色、形状）永远找不回；
- $g$ 太小 → 暗部压向 0，8bit 量化相对步长 $1/(255\cdot g)$ 变大 → **暗部色带**。

正确的用法 = 让"你关心的亮度范围"的中间调落在 $[0.2,0.8]$，两头尽量不齐 clip。

**实测锚点**（restir_learn Cornell 场景，PFM 线性域，1280×720）：中位亮度 $Y_{50}=0.23$、亮墙 $Y_{90}=0.66$、灯面 $Y=15$；$g=1$ 时 2.84% 像素过曝。换算成屏幕灰度（$g$ 变化）：

| 场景区域（线性 $Y$） | $g=0.15$ | $g=0.6$（默认） | $g=1.8$ |
|---|---|---|---|
| 中位暗部（0.23） | 55/255 | 104/255 | 171/255 |
| 亮墙（0.66） | 89/255 | 167/255 | clip→255 |
| 灯面（15） | clip→255 | clip→255 | clip→255 |

所以 $g=0.6$ 的画面：暗部偏暗但可辨、亮墙接近中灰偏亮、灯永远纯白"发光"；把 $g$ 拖到 1.8 暗部提亮但亮墙过曝；$g=0.15$ 则整图沉底。这就是为什么滑条给 ±2.6 EV 的量程（0.05–2.0）。

**gamma 为什么夹在中间**：人眼/显示对暗部更敏感，线性值直接存 8bit 会在暗部浪费位数（相邻灰阶差 1/255 在暗处肉眼可见）。$c^{1/2.2}$ 是显示传递函数的近似（sRGB EOTF 的廉价版），把编码资源按感知分配。

## 和质量度量工具的关系（防误用）

- PFM 存**曝光前的纯线性解** → RelMSE 对公共尺度因子不变（$(gt-gr)^2/((gr)^2+\varepsilon)$ 中 $g$ 上下约掉），RMSE/PSNR(LDR) 则依赖曝光；
- quality.py 的 `--exposure`（默认 0.6，与引擎一致）正是为了复现 BMP 视图再做 LDR 域比较；
- 研究规范：误差对比在 HDR 线性域做；最终 LDR 成品图必须声明曝光 + 色调映射参数，否则不可复现。

## 没解决什么（局限 → 下一站）

clamp 是"硬砍"：场景动态范围一大（灯比墙亮 $10^3$–$10^6$），单靠一个线性 $g$ 保不住两头。需要**非线性色调映射曲线**（Reinhard $L/(1+L)$、ACES、filmic 等）把 HDR 动态范围压进 $[0,1]$——那时曝光退化为曲线内部的"线性锚点"（白点/灰点定标）。该话题与去噪链同属"显示/后期管线"，M3+ 入库。另一个相关旋钮：gamma 之后才做 8bit 量化，任何 HDR 工作流（ReSTIR 中间缓冲、PFM 存档）都必须保持在量化之前。

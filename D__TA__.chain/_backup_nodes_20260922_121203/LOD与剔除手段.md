# LOD 与剔除：从顶点退化到视锥裁剪

## 优化的是三个不同的量

| 目标 | 手段 | 备注 |
|---|---|---|
| **顶点/图元量** | 网格 LOD、曲面细分自适应、顶点退化 | 顶点阶段的成本 |
| **片元量** | 距离淡出、片元早退、分辨率降档 | 片元阶段通常更贵（尤其移动端） |
| **批次/CPU** | 合批、实例化、GPU 驱动参数 | 别把 CPU 提交当 GPU 成本 |

**面试常见误区**：一上来就说"用 LOD"，却说不清 LOD 省的是哪个阶段的量、切换时的视觉代价是什么。

## 手段一：顶点退化（vertex degeneration）

把不需要的图元的所有顶点**推到裁剪空间之外**（如 `positionCS = float4(2,2,2,1)`），图元在裁剪阶段被整体丢弃：

- 优点：**零 CPU 成本**（不用改 Mesh、不用重排批次），可以在顶点着色器里按距离/掩码动态决定；
- 代价：顶点着色器仍然要跑（省的是光栅化之后的量），所以对"顶点量极大"的网格收益更明显；
- 这是 GPU 侧的 LOD，和引擎的 `LODGroup`（CPU 决定用哪个 Mesh）是**两个层次**。

实测：`TA_show` 的 41 万顶点程序化网格，用"顶点退化 + 片元早退"双保险，砍掉窗口内约 **36%** 的代价。

## 手段二：片元早退与 `discard` 的隐藏账

`clip()` / `discard` 能省后续着色，但会**破坏 early-Z**（深度预测试）：GPU 无法在着色前确定该像素是否被遮挡。在移动端 TBDR 架构上，`discard` 还会让 HSR（hidden surface removal）失效、强制走"先着色后测试"，代价可能比省下的更大。
→ 更稳的做法：**用 alpha 混合 + 预乘或写深度的不透明通道替代 discard**，或在顶点阶段就把退化做掉。

## 手段三：视锥裁剪的粒度

- 引擎默认按**包围盒**裁剪整个 Mesh——对超大网格没用（中心在视锥内就整块留下）。
- 精细做法：**整三角形裁剪**——在顶点/几何阶段判断三角形是否都在视锥外，整体退化。`water` 的海面用"距离自适应曲面细分 + 视锥整三角形剔除"（`FFTOcean_Render.cs:37-44`、shader `:90-226`）就是这个思路。
- 距离自适应：远处三角形变大、近处变小——比"统一降低细分"更符合透视误差分布。

## 手段四：索引格式——一个"静默截断"的陷阱

网格顶点数超过 **65535** 时，若索引仍是 16 位，引擎会**静默截断**（不报错！），表现为整组三角形消失。必须显式设 `IndexFormat.UInt32`。
真实事故：`TA_show` 的 extents=80 网格有 **412,804** 个顶点，横向网格线整组消失，根因就是它（`InteractiveGridLines.cs:97-99`）。
→ 面试可讲："**这类 bug 的可怕之处是没有任何报错**，只能靠'顶点数 vs 索引位宽'的检查清单提前拦。"

## 可能被追问的三层

1. **原理层**：early-Z / HSR 的工作条件是什么？为什么 `discard` 会破坏它？顶点退化与几何着色器剔除的取舍（几何着色器在移动端普遍不推荐，为什么）？
2. **实现层**：顶点退化时为什么要给 `positionCS` 一个"在裁剪空间外但有限"的值（`(2,2,2,1)` 而不是 NaN/inf）？LOD 切换怎么防止"跳变"（dither/cross-fade）？索引格式改变对内存与带宽的影响？
3. **边界层**：程序化网格（本例）为什么比静态 Mesh 更适合顶点侧 LOD？在 TBDR 上先砍什么？如何量化收益（帧时间/带宽 vs 顶点数——要说明测量口径）？

# 工程结构与协作：模块化重构（Director + 模块）

**来源**：`D:\unity\unityProjectLocation\SDF` 的 `L17` 特效系统（图谱 `d-013` 设计、`d-014` 评审、`t-050` 补档）。这是一次**有施工文档、有回退方案、有评审闭环**的重构——比"我重构过代码"这种说法有力得多。

## 一、动机（重构的理由必须写清，否则就是"改着玩"）

现状：单文件 **801 行 / 11 个功能分组**，状态机与表现逻辑纠缠。四个动因：

1. **状态机要可观察**：把相位状态独立成核心，而不是散落在各表现代码里；
2. **表现模块要能各自开关**（调试时单独看某一层）；
3. **降低双会话同文件冲突**——**这条是本项目特有的协作动因**：当时有两个 AI 会话在同一个工程上工作，同文件修改经常冲突。把文件按模块切开后，冲突面大幅下降；
4. **面板要按模块分组**（美术调参时不用在一堆参数里找）。

## 二、施工级设计文档该有什么（`d-013` 的目录就是模板）

| 章节 | 内容 |
|---|---|
| 现状盘点 | 801 行 / 11 分组，逐组说明职责与耦合点 |
| 目标架构 | 瘦身目标（≤600 行）+ 模块划分图 |
| **接口契约** | 模块只读属性 + `PhaseEntered` 事件订阅；**禁止模块写回** Director 状态（单向数据流） |
| 分步计划 | S0~S6，**每步都可独立验证、可回退** |
| **场景序列化迁移方案** | Unity 特有：脚本字段搬家后，场景里序列化的值会丢——必须逐项列出人工迁移清单 |
| 并发协作规范 | 文件归属、写前重读、冲突处理 |
| 风险表 | 每步的风险与缓解 |

## 三、落地结果

- **Director 543 行**（原 801）+ 黑板 `Modules/L17_FXModule.cs` + 5 个表现模块：Ember 239 / Orb 64 / GroundGlow 73 / HeatDistort 76 / Smoke 86 行。
- 模块支持 `solo` / `weight` / `tier` 三种控制——**"能单独看一层"是调试效率的关键**，也是这套结构最大的收益。
- 评审（`d-014`）结论：质量高、架构落地符合设计；遗留项包括 S5 暖光模块化、调参下沉、`frameSeed` 序列化等。

## 四、教训（这里才是干货）

### 1. 静态验收有盲区，重构尤其危险
重构后出现"立方体不溶解"：根因是 **`MaterialPropertyBlock` 被两次 `Get` 覆盖式丢弃**——顺序敏感的容器在静态核对下看不出来（`t-052`）。**重构后的验收必须包含运行时行为抽样，不能只做逐段代码核对。**

### 2. Unity 序列化的隐藏成本
脚本字段改名/搬家会让**场景里已序列化的值全部丢失**（容易表现为"参数全变默认值"）。所以迁移清单必须与代码改动**同时**规划，且改完要在场景里逐项核对。这是 Unity 项目重构最容易翻车的地方。

### 3. 切分依据：按"变化原因"切，不是按"代码行数"切
5 个模块分别对应 Ember / Orb / GroundGlow / HeatDistort / Smoke——**每块的表现逻辑与调参时机不同**，所以会独立变化。按行数均分只会得到 5 个互相纠缠的文件。

### 4. 数据流方向必须写进契约
"模块只读属性 + 事件订阅 + 禁写回"这条看似啰嗦，但它**排除了绝大多数竞态与调试困难**：出问题时只需要看 Director 的状态与事件，不用追 5 个模块的互写。

## 五、可复用的重构 checklist（面试可当场背）

1. 先写"**为什么**要重构"（可观察性 / 冲突面 / 可调试性），写不出就别动；
2. 盘点现状并定**量化目标**（801 → ≤600 行）；
3. 定**接口契约**（谁读、谁写、事件还是轮询）；
4. 拆**可分步验证**的阶段，每步都能回退；
5. 列出**序列化/资源引用**的迁移清单（引擎特定坑）；
6. 重构后**运行时抽样验证**（静态核对不够）；
7. 留评审与遗留清单。

## 六、可能被追问的三层

1. **原理层**：黑板模式与中介者/观察者模式的关系？单向数据流为什么能压制竞态？事件订阅的时机与生命周期管理（何时退订）？
2. **实现层**：`PhaseEntered` 事件怎么保证订阅者不丢事件（入场即触发一次？）？Unity 序列化字段迁移有哪些手段（`FormerlySerializedAs`、Inspector 手动迁移、编辑器脚本批量搬）？怎么量化"冲突面下降"？
3. **边界层**：模块拆到什么粒度就过细了？多会话/多人协作时还有哪些结构性手段（文件归属、接口冻结、每日合并）？如果团队用 Git，这套拆分怎么映射到分支策略？

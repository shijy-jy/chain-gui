# 局限 · Engram MCP 的静态绑定

## 由哪个方案引出

「方案 · Engram 多工作区 MCP 接入」：用一份补丁层 + 每条一段 stdio 服务登记的方式挂载多个知识工作区。做法简单，但**所有关键参数都在进程启动那一刻固定**，运行期不可变。

## 三个具体局限

1. **命名空间静态**：工具名由 `serverName` 决定（`mcp__<serverName>__*`）。改名 = 改工具名，此前写进提示词、对话记录、文档里的工具名全部失效。
2. **工作区静态**：`--workspace` 只在启动时读取。换目录、挪工程、复制一份新库，都必须改配置并**重启 dsh web**；进程内没有"切到另一个工作区"的入口。
3. **模式缓存**：`engram-mcp` 启动时读取并缓存 `.chain/.mode`。把工作区从 `dev` 改成 `analysis`（或反向）后，**不重启进程就仍然按旧模式的规则工作**——写入会被旧规则接受或拒绝。

## 为什么必须知道（症状）

看到"工具能用"就以为配置对了，是这类问题的典型误判：

- 在目录 A 对话，`recall` 却命中 B 工程的内容 → 没有指向 A 的登记，会话里那组工具指向别处；
- 改了 `.chain/.mode` 但行为不变 → 模式在启动时已被缓存；
- 重启前一切"看起来没问题"，重启后突然多出一组工具或行为变了 → 说明配置改动此前根本没生效。

## 判定方法（按顺序做，别猜）

1. 调用任一同命名空间工具，**读它返回的 `workspace` 字段**，与目标目录逐字符比对；
2. 若不符 → 检查 `cordis.patch.yml` 里该段的 `args.--workspace`，以及 `serverName` 是否与提示词里用的命名空间一致；
3. 改完配置或模式后**重启 dsh web**，再重复第 1 步确认（这是必需的，不是可选步骤）。

## 规避

- 一处工作区一段登记、`serverName` 用短且稳定的名字（如目录名小写），减少改名；
- 配置里保留注释（改了什么、为什么、何时改），见「工程实践」的记录约定；
- 需要频繁切换工作区时，宁可多登几段（每段一个命名空间），也不要指望运行期切换。

# TBDR 与移动端渲染（tile 内存 / HSR / 约束清单）

**为什么补这一条**：2026-09-22 的模拟追问里，"TBDR 是什么"是唯一完全答不上来的题（见「模拟追问记录」）。它属于**综合 TA 面试高频题**，而且和已建的 `LOD与剔除手段`（discard 与 HSR）、`后处理链顺序`（多 pass 与 RT 切换）直接相连。

## 一、是什么

**TBDR = Tile-Based Deferred Rendering（分块延迟渲染）**。移动端 GPU（PowerVR 血统、Mali、Adreno 等）普遍用"分块"架构，与桌面 **IMR（Immediate Mode Rendering，立即模式）**的根本差别在**片元在哪里完成**：

- **IMR（桌面）**：每个图元立即着色，结果直接读写系统内存里的帧缓冲；
- **TBDR（移动端）**：屏幕切成小块（tile，常见 16×16 / 32×32 像素），**同一 tile 的几何全部收集齐之后，在片上高速内存（tile memory）里完成着色与合并，最后统一写回主存**。

> ⚠️ **高频陷阱题**："TBDR 就是桌面那个延迟渲染（G-Buffer 延迟光照）吗？"——**不是**。TBDR 名字里的 Deferred 指"**tile 内先收集几何、再把着色推迟到可见性确定之后**"；桌面的延迟渲染指的是"**把几何属性写进 G-Buffer，再统一做光照**"。两者解决的问题不同（前者省带宽，后者解耦光照与物体数）。

## 二、为什么这么设计：带宽与功耗

手机没有独立显存带宽，也没有桌面的散热预算。IMR 反复读写帧缓冲（每个 pass、每次混合都是一轮主存往返）→ TBDR 把"多次主存往返"压成"**一次写入**"，**带宽与功耗大幅下降**。这是移动 GPU 选分块的唯一理由，也是评价移动端优化方案好坏的总标准。

## 三、关键机制：HSR（隐藏面消除）

因为一个 tile 的几何先被收集齐，GPU 可以**在该 tile 内先确定每个像素最终可见的是哪个片元**（PowerVR 的 HSR 及各家等价机制，本质是 tile 范围内的深度预排序），于是**被遮挡的片元直接不执行片元着色器**。

- 在这个意义上，TBDR 的"early-Z"是**结构性**的、近乎免费；
- 代价是它**依赖"先收集、后着色"的顺序**——一旦某个片元的可见性无法在着色前确定，这个红利就没了。

## 四、约束清单（移动端踩坑就这几条）

| 写法 | 为什么会变贵 |
|---|---|
| **`discard` / alpha test** | 让 HSR 失效（无法在着色前确定可见性）→ 退回"先着色后测试"，可能比省下的更亏 |
| 在片元着色器里**写深度** | 同上，破坏深度预排序 |
| **频繁切换 RenderTarget / 反复 Blit** | 每次都要把 tile **resolve（flush）**回主存——分块架构里最贵的操作 |
| 大量 alpha blending / 多层透明 | tile 内存有限，需要多轮往返 |
| MRT 挂太多张 | tile 内存预算被吃满 |
| 依赖**读回**帧缓冲（某些屏幕空间效果的实现） | 强制中断 tile 流程 |

**工程建议**：
- 能在**顶点阶段**做的就别放片元（例如 LOD 用顶点退化，见 `LOD与剔除手段`）——它不参与 tile 的片元预算；
- **合并全屏 pass**（能一个 pass 做完的别拆两个），减少 RT 切换；
- 视情况把 alpha test 换成 alpha blend，或用预乘/写深度的不透明通道替代 `discard`；
- 屏幕空间效果尽量在**已有 pass 内**完成，避免额外读回。

## 五、IMR 与 TBDR 对比（面试可直接画这张表）

| | IMR（桌面） | TBDR（移动端） |
|---|---|---|
| 片元完成位置 | 立即，写主存帧缓冲 | tile 片上内存，最后统一写回 |
| 深度优化 | 依赖 early-Z（**需满足前提**） | **结构性 HSR**（近乎免费，但怕 discard） |
| 最贵的操作 | 带宽（大分辨率 / 多 pass） | **RT 切换 / tile resolve** |
| 优化重心 | 减少 overdraw 与带宽 | 减少 pass 数与 RT 切换 |

## 六、可能被追问的三层

1. **原理层**：tile 内存为什么能省带宽（每像素属性读写次数从 N 次降到 1 次）？HSR 与 early-Z 的关系与差别（tile 级深度预排序 vs 像素级深度预测试）？为什么 `discard` 会同时影响两者？
2. **实现层**：Unity 里怎么少踩 tile 的坑（少切 RT、少 Blit、RenderTexture 复用的正确姿势）？怎么**验证**一个效果在移动端踩没踩（Frame Debugger 数 pass、RenderDoc / Xcode GPU 工具看 tile 往返）？`OnRenderImage`/多 pass 后处理在移动端为什么比桌面更贵？
3. **边界层**：移动端做延迟渲染有意义吗（能做，但 G-Buffer 的带宽压力与 tile 内存预算冲突，通常走前向/Forward+）？移动光追（硬件加速）会改变这套约束吗？同一效果在 IMR 与 TBDR 上的优化方向为什么常常相反（少 overdraw vs 少 pass）？

# 面试八股文题库 · 04 · 引擎与性能优化

> 本册用法：① 每题的「答（背这段）」是口述版，先背到能一口气说完，再回头看细节；②「细节 / 数字」是面试官追问时才掏的弹药，不要主动倒；③ 所有性能数字都要带口径，没口径的数字（"优化后快 3 倍"）说出来就是减分项；④ 标了「以工程实测为准」的地方不要硬背数字，换成你自己工程的实测值；⑤ UE 只背 Q20 的骨架句和代价，没做过的功能不要展开。

## 一、渲染管线与渲染路径

### Q1. Unity 内置管线 / URP / HDRP 的区别；URP 的 ScriptableRenderPass 与 ScriptableRendererFeature 职责划分与插入点怎么选

**答（背这段）**
> 三条管线是同一个引擎里的三种取舍。Built-in 是老式固定管线，没有官方扩展点，只能靠 `OnRenderImage` 和 CommandBuffer 往里塞，前向为主。URP 是面向移动和多平台的可编程管线，源码开放，前向 / 延迟 / Forward+ 三种路径都有，我们项目用的就是它。HDRP 是 PC 和主机高端向，延迟 + 集群光照、物理光照单位、体积雾、光追，基本不做移动端。
> URP 的扩展模型分两层：`ScriptableRendererFeature` 是「资产 + 插入点」，它挂在 Renderer Asset 上，每帧按 `RenderPassEvent` 把内部的 pass 排进队列；`ScriptableRenderPass` 才是真正干一次渲染活的对象。职责划分就是——Feature 决定「什么时候插、插几个、要不要启用」，Pass 决定「这一步具体怎么画」。一个 Feature 挂多个 Pass 是常态。
> 插入点按「你要读什么、写什么」来选：要读深度或法线就用 `ConfigureInput` 申请；想在透明物体之前改颜色就 `BeforeRenderingTransparents`；想读完整的不透明结果就 `AfterRenderingOpaques`；想在后处理之前插就 `BeforeRenderingPostProcessing`；想在后处理之后、UI 之前就 `AfterRenderingPostProcessing`。选错插入点的典型症状是「采样到自己刚写的东西」或者「透明物体没被处理到」。

**细节 / 数字**
- 版本前提：URP 7.x（2019）→ 10/11（2020）→ 12（2021 LTS）→ 13（2022）→ 14（2022.2+）→ 17（Unity 6）。RenderPassEvent 枚举本身从 7.x 就在，但可用项随版本增加（如 `BeforeRenderingTransparents` 在早期版本不存在，以你工程的枚举值为准）。
- URP 12（2021 LTS）起相机颜色目标从 `RenderTargetIdentifier` 改成 `RTHandle`（`cameraColorTargetHandle`），旧写法 `cameraColorTarget` 在 13/14 里逐步废弃；Unity 6（URP 17）默认走 RenderGraph，Pass 里要写 `RecordRenderGraph`，老 `Execute(ScriptableRenderContext, ref RenderingData)` 写法要靠 Compatibility Mode 过渡，具体开关以你工程版本为准。
- URP 14+ 内置了 `Full Screen Pass Renderer Feature` 和 `Render Objects` Feature，很多需求不用写代码。
- HDRP 的延迟管线对半透明和 MSAA 的支持与 URP 延迟不完全一样；HDRP 不支持 GLES、移动端基本不可用。

**追问会问什么**
- 追问 1：一个 Feature 里多个 Pass 的执行顺序怎么保证？——按 `EnqueuePass` 的调用顺序，同一 RenderPassEvent 下就是入队顺序，所以要自己控制好 Enqueue 顺序。
- 追问 2：`ConfigureInput` 和 URP Asset 上的 `Depth Texture` 开关是什么关系？——`ConfigureInput` 是「这个 Pass 需要深度，请管线保证这一帧有 `_CameraDepthTexture`」，Asset 上的开关是「全局要不要生成深度纹理」，两者是「需求」和「供应」的关系，只开一边都可能拿不到正确内容。
- 追问 3：为什么不用 `OnRenderImage`？——那是 Built-in 的接口，SRP 下不生效；SRP 下只能用 Feature/Pass 或 RenderGraph。

**坑**
- 说 HDRP「就是更高级的 URP」是错的：它们不是同一套代码，Shader 不通用，HDRP 用物理光照单位（lux/EV），材质资产也不通用。
- 别把 RendererFeature 和 Renderer 搞混：Feature 挂在 Renderer Asset 上，多个相机可以用不同 Renderer，所以「同一个 Feature 在不同相机上表现不同」是设计而不是 bug。
- 说「URP 没有延迟」也不对：URP 10+ 就有 Deferred Renderer，只是功能比 HDRP 少。

### Q2. 前向渲染、延迟渲染、Forward+（Tile / Cluster）的原理、代价与适用场景

**答（背这段）**
> 前向是「每个物体，遍历影响它的灯，直接算完颜色写进颜色缓冲」。它的代价是 O(物体 × 影响它的灯)，灯一多，像素着色器里的循环就把像素成本顶上去；但它是唯一对 MSAA、半透明、自定义混合最友好的路径，也是移动端最常用的。
> 延迟是「先把几何信息写进 G-buffer——albedo、法线、粗糙度/金属度、深度，然后一个全屏 pass 对所有灯统一算光照」。几何着色只跑一遍，灯的数量对几何成本几乎无影响，但代价是 G-buffer 的写入 + 读取带宽很大、半透明物体只能退回前向、MSAA 基本不可用（URP 的延迟 Renderer 就不支持 MSAA）、并且延迟路径对自定义材质和 Shader 变体要求更严。
> Forward+ 是「前面还是前向，但先用 Compute Shader 做光源剔除」：把屏幕切成 tile，或者再在视空间深度上切成 cluster，每个物体只取自己覆盖的 tile/cluster 里的灯。它把前向的「每物体灯数上限」这个大限制拿掉了，代价是一次额外的光源剔除 compute pass，和对硬件 compute 支持的要求。

**细节 / 数字**
- URP 前向的 additional light 每物体上限默认 8（URP Asset → Lighting → Additional Lights → Per Object Limit），这也是前向最常见的翻车点：超出的灯直接不亮。
- URP 的 Forward+ 从 12（2021 LTS）开始实验、14（2022.2+）正式可用，要求 Compute Shader 支持（部分只支持 GLES 3.0 的老 Android 设备开不了，会退回前向）。Forward+ 下的每物体灯数上限远高于 8，具体数值以 URP 文档和你工程实测为准。
- Tile 只按屏幕 XY 分块，对深度方向不区分，所以近处的大范围灯会分给很多不相干的 tile；Cluster 在视空间 Z 上也分片，更精确，但光源列表的构建和存储更贵。
- 适用判断：灯少（每物体 ≤ 4 个有意义的灯）→ 前向最便宜；灯多且都是全屏级影响、无 MSAA 需求 → 延迟；灯多但要 MSAA / 大量半透明 / 移动端 → Forward+。

**追问会问什么**
- 追问 1：移动端为什么不推荐延迟？——TBDR 上 G-buffer 虽然能在 tile memory 里省掉一部分读写，但 G-buffer 本身有 3～4 张 RT 的总量，带宽和片上内存都吃紧；加上半透明还得切回前向，路径变多，收益不明显。
- 追问 2：延迟能不能用 MSAA？——传统延迟不行（G-buffer 是逐像素数据，MSAA 会把它变成逐采样数据，成本爆炸），这也是很多引擎在延迟路径上改用后处理 AA（TAA/FXAA/SMAA）的原因；UE 的做法是在延迟之后用 TAA/TSR。
- 追问 3：Forward+ 的剔除是在哪个空间做的？——先按 tile 做屏幕空间剔除，再按 cluster 在视空间深度上细分，最后把光源索引列表塞进 StructuredBuffer 给像素着色器用。

**坑**
- 别说「延迟一定比前向快」。灯少的时候延迟一定更慢——G-buffer 的带宽是白付的。
- 别把 Forward+ 和「多 pass 前向」混为一谈，后者是每盏灯一个 pass 的老做法，成本随灯数线性增长。
- 说延迟「一次算完所有灯」要加限定：是「一次遍历全屏像素把所有灯算完」，不是「一次 drawcall 画完」。

### Q3. URP 里一个全屏后处理从分配到释放的完整流程（RT 分配、Blit、UV 翻转、色彩空间），以及「我要用深度」怎么处理

**答（背这段）**
> 流程是五步：申请、画、回到相机目标、释放、以及保证规则不破。
> 第一步申请：URP 12+ 用 `RTHandle`，通过 `RenderingUtils.ReAllocateIfNeeded` 复用一张按相机分辨率描述的 RT；老写法是 `cmd.GetTemporaryRT`。第二步画：用 `Blitter.BlitCameraTexture(cmd, src, dst, material, passIndex)`（URP 12+），它会正确处理缩放偏移和翻转；老版本是 `cmd.Blit`。第三步回到相机目标：先把相机颜色目标 Blit 到临时 RT，处理完再 Blit 回去，绝不能 src 和 dst 是同一张图。第四步释放：`RTHandle` 在 Feature 的 `Dispose(bool)` 里 `Release()`，`GetTemporaryRT` 的必须 `ReleaseTemporaryRT` 且顺序相反，否则会漏 RT。
> UV 翻转的规则是：渲染到 RT 时，D3D 系平台会把 Y 翻过来，Shader 里 `_ProjectionParams.x` 为 -1、`_MainTex_TexelSize.y` 会是负的；用 `Blitter.BlitCameraTexture` 就不用管，自己写 Blit 就必须处理 scale/offset，否则会出现「只在某些平台上下颠倒」。色彩空间的关键是中间 RT 的 sRGB 标志：项目是 Linear 时颜色贴图由采样器做 sRGB→linear，写回 RT 时的 linear→sRGB 编码由 RT 自己的 sRGB 标志决定，中间 HDR 的 RT 用 `R16G16B16A16_SFloat` 这类线性格式、不能做 sRGB 编码，到最后输出 LDR 那一步才编码。
> 「我要用深度」的正确做法是在 Pass 里 `ConfigureInput(ScriptableRenderPassInput.Depth)`，同时保证 URP Asset 上 `Depth Texture` 开着，Shader 里用 `SampleSceneDepth` + `LinearEyeDepth(depth, _ZBufferParams)`。但移动端要注意：开 `_CameraDepthTexture` 往往意味着一次深度拷贝（多一轮全屏读写带宽），能不用就不用。

**细节 / 数字**
- `_CameraDepthTexture` 需要一次 CopyDepth（额外全屏读写）；`_CameraDepthAttachment` 直接绑定当前深度缓冲，Deferred 或已开 DepthPrepass 时可用，省掉那次拷贝，但采样坐标与翻转规则不同。二选一要看你的 URP 版本，以工程实测为准。
- RT 描述要显式指定 `FilterMode`、`wrapMode`、`useMipMap`、`depthBufferBits`；不指定 depth buffer 的 RT 在需要深度测试时会静默额外分配一张。
- 半分辨率的后处理（Bloom、SSAO）用 `RenderTextureDescriptor` 把宽高各除以 2，注意 UV 采样时用 `_MainTex_TexelSize` 或双线性采样做上采样，不要直接用像素坐标。
- 色彩空间的经典症状：整体变亮一档 = 少了一次 linear→sRGB 编码；整体变暗/发灰 = 多了一次或中间 RT 被标成 sRGB 后又当线性读。Normal map、Roughness、Mask 这类贴图的 sRGB 必须关掉。

**追问会问什么**
- 追问 1：为什么 src 和 dst 不能是同一张 RT？——同一张图同时被采样和被写入时，片段写入的顺序不保证，驱动行为未定义，实际表现是画面撕裂或整屏花掉。
- 追问 2：全屏 pass 为什么要用 `Blitter` 而不是 `Graphics.Blit`？——前者走 SRP 的 RTHandle 与 scale/offset 约定，翻转和缩放已经处理好；后者在 SRP 下容易踩 flip 和临时 RT 的坑。
- 追问 3：后处理为什么有时只在 Scene 视图出错、Game 视图正常？——两个视图的相机配置/RT 状态不同（是否走 RT、是否开 MSAA、分辨率不同都会影响翻转与缩放），要两边都验。

**坑**
- 说「URP 12 之后不用管 UV 翻转」是错的：用了 `Blitter` 才不用管，自己写全屏三角形的 Blit Shader 一样要处理。
- 别把 `RenderTextureReadWrite.Default` 当成「总是对」；它跟随项目色彩空间，用 `GetTemporaryRT` 时容易和 GraphicsFormat 打架。
- 忘记释放 RT 是很常见的面试加分点：`RTHandle` 泄漏的表现是显存缓慢增长、切场景后掉帧。

### Q4. 后处理链的顺序为什么是那个顺序？举 2 个顺序错了会出什么症状

**答（背这段）**
> 顺序是按「作用在哪个数值域、依赖谁的结果」排的。大原则是：先物理、后显示参考；先 HDR、后 LDR；先改内容、后做量化补偿；抗锯齿尽量晚。
> 标准顺序是：不透明 → 天空盒 → 透明 → HDR 域处理（景深、运动模糊、Bloom）→ Tonemapping（HDR 压到 LDR）→ Color Grading / LUT → 屏幕空间效果（暗角、颗粒、色差）→ 抗锯齿（FXAA/SMAA）→ 最终 Blit 到屏幕 → UI。TAA 的位置和它们不同（历史上在 tonemapping 之前做，因为它需要在 HDR 域做色彩 clamp），以你的 URP 版本源码为准。
> 顺序错了两个典型症状：一是 Bloom 放到 Tonemapping 后面——亮部已经被压到 0-1，阈值筛选挑不出真正的高光，Bloom 变成"糊一层灰"，HDR 光源不再有光晕；二是 Color Grading 放到 Tonemapping 前面——LUT 是按显示参考设计的，输入 >1 的 HDR 值会被采样到边缘，高光整片偏色、颜色断裂。
> 另外两个常见的：抗锯齿放在 Bloom 前面，被 Bloom 放大的还是锯齿亮像素，亮部边缘会出现跳动的颗粒点；Dithering 放在 Tonemapping 前面，它是补偿 8bit 量化误差的，必须放在量化前一刻，提前加会被 Tonemapping 的非线性曲线淹没，banding 照样在。

**细节 / 数字**
- URP 13/14 的 `PostProcessPass` 顺序大体是：DoF / 运动模糊 / Bloom 等在 uber pass 里执行 → Tonemapping + Color Grading → Film Grain / Dithering → SMAA → FXAA。版本间有出入，以你工程的 Frame Debugger 实际顺序为准。
- Bloom 的迭代次数和 mip 数直接决定成本：常见的 mip 数是 4～6 级，移动端常砍到 3～4 级 + 半分辨率，画质损失比砍分辨率更不容易被看出来。
- UGUI 的 Screen Space Overlay Canvas 不经过管线后处理，Screen Space Camera 的 Canvas 在透明队列里会被后处理影响——这就是「HUD 也在发光」的原因。

**追问会问什么**
- 追问 1：Bloom 能不能放 Tonemapping 后面？——技术上可以（有些风格化项目故意这么做，做「柔光」而不是「高光溢出」），但那已经不是物理感 Bloom，要明确说这是风格化选择。
- 追问 2：为什么暗角和颗粒放在最后？——它们模拟的是镜头/显示端行为，物理上发生在成像之后，而且放最后能让强度不受 Tonemapping 非线性影响。
- 追问 3：TAA 和 Bloom 谁先谁后？——要看实现，URP 的 TAA 在 tonemapping 之前，Bloom 也在前，两者相对顺序由 pass 组织决定；面试里更稳的说法是「TAA 需要在 HDR 域、在 tonemapping 前，用它自己的历史缓冲做重投影」。

**坑**
- 不要背「后处理顺序是 XX」而死记；面试官更想听「为什么」，你就说「按数值域和依赖关系排」。
- 说「顺序不影响效果」会被直接判定没做过。
- 别把 Color Grading 说成「调色放在最后」，它必须在 Tonemapping 之后、量化效果之前。

## 二、Draw call 与合批

### Q5. 一个 drawcall 的成本由哪些部分构成？为什么「2000 个 drawcall 比 200 个慢」不只是 CPU 的问题

**答（背这段）**
> drawcall 的成本分两段。CPU 侧有：剔除与排序、合批判断与合并、SetPass 状态切换与材质属性上传、命令写入 CommandBuffer、驱动校验与转译成 GPU 命令、最后 submit 和内核态切换/fence。GPU 侧有：命令处理器解析、状态切换导致的前端流水线打断、每个 draw 的固定开销（图元装配、光栅化器启动、可能触发 PSO 查找或着色器程序切换）、以及小批次导致并行度不足和缓存局部性变差。
> 「2000 比 200 慢不只是 CPU」的意思是：如果这 2000 个 draw 每个只画几十个三角形，GPU 前端和光栅化的固定开销、状态切换造成的缓存失效、顶点/纹理反复换导致的 L2 miss 都在 GPU 上体现；移动端 TBDR 上还更贵——drawcall 越多，tiler 的 binning 列表越长，状态切换打断 tile pass 会让片上内存往 DRAM 做 store/load，那个是全屏带宽级别的代价。
> 但反过来也成立：2000 个 drawcall 如果共享同一个 SetPass、每个网格都很大，GPU 侧代价可能很小。所以「drawcall 数」这个数字本身没有意义，必须带口径：平台与图形 API、网格面数规模、SetPass 数、是否是 TBDR、以及是 CPU 时间还是 GPU 时间翻倍。

**细节 / 数字**
- 同一个 drawcall 数在不同平台完全不同：桌面 D3D11/D3D12 的驱动开销小，中低端 Android 的 GLES 驱动开销可能是桌面的数倍；所以务必写「在什么机器上、什么 API 下」。
- drawcall 会被 pass 数乘：主 pass + 阴影 pass（每个阴影投射光源一遍）+ 深度 pass + 反射/折射 pass，2000 个物体可能变成 6000+ 次提交。
- 一个可写进面试的口径句：「在中端 Android（骁龙 7 系）/ GLES3 下，drawcall 从 X 降到 Y、SetPass 从 A 降到 B，帧时间中位数从 M ms 降到 N ms，渲染线程从 P ms 降到 Q ms；同一场景同一分辨率关 vsync，采 1800 帧取中位数与 P95。」数字换成你自己的实测。

**追问会问什么**
- 追问 1：怎么判断 drawcall 是 CPU 还是 GPU 的锅？——用「减物体」实验：把一半物体 `SetActive(false)`，如果帧时间等比例下降且渲染线程 marker 也下降，是 CPU 提交侧；如果帧时间几乎不动，说明 GPU 也没被这些 draw 卡住，或者瓶颈在别处（fill/带宽）。
- 追问 2：为什么几百个 draw 在高模场景上比几千个 draw 在低模场景上慢？——因为真正决定 GPU 时间的是覆盖像素、着色器复杂度、带宽，draw 数只是其中一个维度。
- 追问 3：`CommandBuffer` 频繁重建有代价吗？——有，`new CommandBuffer` + `Release` 每次都要分配，正确做法是复用一个静态实例 + `Clear()`。

**坑**
- 不要说「drawcall 是 CPU 的事，GPU 无所谓」，会被按着问移动端 TBDR。
- 不要给「drawcall 要压到 200 以下」这种无口径的绝对数字。
- 别把 drawcall 数和 SetPass 数当作同义词（见 Q8）。

### Q6. Unity 的合批手段全对比：静态合批、动态合批、SRP Batcher、GPU Instancing、GPU-Driven / Indirect 的触发条件与限制（说清哪几种互斥）

**答（背这段）**
> 我按「在哪一层合并」来讲。
> 静态合批是预处理：物体勾 Static（或运行时 `StaticBatchingUtility.Combine`），同材质的网格顶点被烘进一个共享 VB/IB，一个 drawcall 画完。代价是内存——N 个引用同一网格的物体会存 N 份顶点，而且丢失 per-object 剔除粒度，一批里只要有一个可见就整批提交。
> 动态合批是运行时 CPU 合并：要求顶点属性总数 ≤ 900（位置+法线+UV 是 8 个属性，大概就是 300 顶点以内）、同材质、不带 Lightmap、非 SkinnedMesh。它在 CPU 上做顶点变换和拷贝，经常是省了 drawcall 亏了 CPU，SRP 下基本建议关掉。
> SRP Batcher 不减少 drawcall，它减少 SetPass call：只要 Shader 兼容（材质属性都写在 `CBUFFER_START(UnityPerMaterial)` 里）、同一 Shader 变体、不用 MaterialPropertyBlock，同一个变体的物体就共用一次状态设置。它是 URP 下 CPU 侧收益最稳的手段。
> GPU Instancing 是同一 mesh + 同一 material 一次 draw 画 N 个，per-instance 数据走 `UNITY_INSTANCING_BUFFER` 或 MaterialPropertyBlock；超过常量缓冲大小、网格不同、SkinnedMesh 都不适用。GPU-Driven / Indirect 是把 draw 参数放进 ComputeBuffer，剔除也在 GPU 上做（视锥 + Hi-Z），drawcall 数基本与物体数解耦，代价是 Unity 的自动剔除失效、阴影和排序要自己再来一遍。
> 互斥关系：material 层只有一条路——同 mesh 同 material 且勾了 Instancing 就走 Instancing，否则走 SRP Batcher。静态合批是 mesh 级的预处理，可以和后面两者叠加（合完还是一个 mesh）；动态合批和 SRP Batcher 在 SRP 下同时开通常只有负收益，官方建议关掉。

**细节 / 数字**
- 静态合批的索引上限：Unity 在 16 位索引下每个批次最多 65535 顶点，超了会拆批——所以「我都勾了 Static 为什么 SetPass 还是很多」常见原因就是这个。
- 动态合批的 900 是「顶点属性数量」不是顶点数；同材质指同一个 Material 实例，材质实例不同（哪怕 Shader 一样）也不能合。
- SRP Batcher 的验证：Frame Debugger 里看单个 draw 的详情有 `SRP Batch` 标记，或者 Shader Inspector 上看兼容性提示；Inspector 的 SRP Batcher 状态与 keyword 组合的关系要一起看。
- GPU Instancing 的 per-instance 数据量受常量缓冲（通常 64KB 级别，平台不同）限制，实例多且数据大时要走 StructuredBuffer。
- GPU-Driven 的依赖：Compute Shader + Indirect Draw 支持（Vulkan / Metal / D3D11+ / GLES 3.1+），老 GLES 3.0 设备不支持，要做 fallback 路径。

**追问会问什么**
- 追问 1：为什么用了 MaterialPropertyBlock 合批就崩了？——它给每个 Renderer 单独的属性缓冲，SRP Batcher 的「一套常量缓冲服务多个物体」前提被破坏，走不了 SRP Batcher 路径（但它是 Instancing 的常用手段）。
- 追问 2：静态合批和 Lightmap 冲突吗？——静态物体会带 lightmap UV（UV2），烘焙时需要；但动态合批明确不支持带 Lightmap 的物体。
- 追问 3：GPU Instancing 的物体还能被 Unity 自动视锥剔除吗？——`DrawMeshInstanced` 是整批剔除（按给定 bounds），`DrawMeshInstancedIndirect` 要你自己在 GPU 上算；后者如果 bounds 给大，等于没剔除。
- 追问 4：阴影 pass 会重新合批吗？——会，ShadowCaster pass 需要单独的变体，Instancing 要求在 Shader 里同时给 shadow caster 生成 instanced 变体，否则主 pass 合上了、阴影 pass 没合上。

**坑**
- 说「SRP Batcher 减少 drawcall」是硬伤，它减少的是 SetPass。
- 说「静态合批就会快」不成立：内存涨、剔除粒度丢、LOD 不适用，小场景可能是负优化。
- 别把 GPU-Driven 说成「Unity 自动帮你做」，剔除、排序、阴影都要自己写。

### Q7. 材质与 Shader 变体（shader variant / keyword）爆炸是怎么来的？怎么管理 keyword、变体收集与预热

**答（背这段）**
> 变体爆炸的根是 keyword 的组合数：一个 `#pragma multi_compile A B` 就是 2 个变体，n 个两态 keyword 是 2 的 n 次方。再叠加 Unity 内置的（阴影、Lightmap、雾、Instancing、立体渲染）和 URP 自己的（主光阴影、级联、附加灯、软阴影、屏幕空间遮蔽、反射探针混合、Forward+ 等），一个 URP Lit 的单个 pass 就能到几百上千个变体。代价有三份：构建时间、包体（每个变体都是编译后的程序）、以及运行时首次使用时的编译/加载卡顿。
> 管理手段按性价比排：能用 `shader_feature` 就别用 `multi_compile`（前者在构建时按材质引用裁剪）；不要做运行时频繁的 keyword 切换（切 keyword 等于换变体，会触发 SetPass 甚至编译），能用参数或用 `[branch]` 分支的用参数；用 `ShaderVariantCollection` 收集真实用到的变体，在 Loading 时 `WarmUp()`；用 URP Asset 里的 Shader Stripping 删掉用不到的；最硬的是写 `IPreprocessShaders.OnProcessShader` 构建回调做自定义裁剪。
> 变体收集的正确姿势不是「全都要」，而是把所有关卡、所有光照组合、所有画质档实际跑一遍，用 Variant Log 导出真实用到的集合，再去 strip。

**细节 / 数字**
- Shader Variant Log 的开关在 Project Settings → Graphics → Shader Loading 里（`Shader Variant Log Level`），导出的是运行时真正加载的变体列表，这是收集变体最可靠的来源。
- `ShaderVariantCollection.WarmUp()` 的时机要放在加载遮罩里并且分帧，一次性预热几百个变体会造成明显的加载卡顿。
- `Shader.WarmupAllShaders()` 非常重，别在运行时全量调用。
- `multi_compile_local` 用于避免和全局 keyword 冲突（URP 内部大量使用），自己写 Shader 时优先用它。
- 报数据的口径：「在 URP 14 / Android Vulkan 构建下，`Universal Render Pipeline/Lit` 的变体数从 N 降到 M，构建时间减少 X 秒，包体减少 Y MB，首帧首次进入场景的编译卡顿从 A ms 降到 B ms」——每一项都要写清平台和 strip 规则。

**追问会问什么**
- 追问 1：`shader_feature` 和 `multi_compile` 到底差在哪？——`shader_feature` 的变体只在被某个材质引用时才进包，`multi_compile` 无条件全进包；代价是 `shader_feature` 的 keyword 如果在运行时被动态打开而构建时没人引用，就会拿不到正确变体。
- 追问 2：运行时因为变体缺失出现的症状是什么？——Shader 回退到默认变体，表现是效果丢失（比如阴影不出现）或直接显示成品红。
- 追问 3：keyword 数量有没有上限？——全局 keyword 有数量上限（Unity 有 `Shader.globalKeywords` 相关的限制，历史上是每个 shader 256 个 keyword 的上限），本地 keyword 也有；超了会有编译报错或 keyword 丢失，别把大量业务开关做成 keyword。

**坑**
- 不要在 Update 里做 `EnableKeyword` / `DisableKeyword`——这是最典型的「看起来只是换个效果，其实每帧在换变体」。
- 别在 Profile 里把「变体编译卡顿」当成持续掉帧，它是一次性 hitch，排查时要分开看（见 Q17）。
- 说「strip 掉一半变体」要给口径：strip 规则、平台、以及 strip 后有没有出现效果缺失。

### Q8. SetPass call 是什么？为什么它常常比 drawcall 数更值得关注

**答（背这段）**
> SetPass call 是需要改变 GPU 渲染状态的次数，也就是「重新绑定 shader program/pass 和它的常量缓冲、纹理槽」的次数。一个 SetPass 后面可以跟任意多个 drawcall，只要状态不变。
> 它比 drawcall 数更值得关注，有四个原因。第一，真正贵的是状态切换：切换 shader 程序会打断 GPU 前端流水线，驱动要做校验甚至等待。第二，同一个 SetPass 内的 drawcall 是便宜的，只多一条命令和一次顶点拉取；10 个 drawcall 配 10 个 SetPass 远糟于 100 个 drawcall 配 1 个 SetPass。第三，它是判断「合批为什么失败」最直接的指标：drawcall 高但 SetPass 低可能无所谓，SetPass 高就说明材质或变体碎了一地。第四，移动端 TBDR 上 SetPass 变化往往意味着 render pass 断裂，触发 tile memory 的 store/load，那是全屏带宽级别的代价。
> 所以 SRP Batcher 的价值也正体现在这里：drawcall 数不变，SetPass 数大幅下降。

**细节 / 数字**
- 观察位置：Profiler 的 Rendering 区域有 SetPass Calls，Frame Debugger 顶部有 Draw Calls / Batches / SetPass Calls 三个统计。
- 「batches」和 drawcall 在 Unity 统计里不完全等价（一个 batch 可能对应多个 drawcall），报数时说清用的是哪个计数。
- 不要报绝对阈值（「SetPass 要小于 200」），要按平台给预算并和帧时间一起报；中低端 Android 的 SetPass 成本明显高于桌面。
- SRP Batcher 生效时，SetPass 会接近「不同 shader 变体的数量」，而不是「材质数量」——这是它和静态合批的区别。

**追问会问什么**
- 追问 1：SetPass 和 drawcall 的关系？——SetPass ≤ drawcall 总数；理想情况是「很多 drawcall、很少 SetPass」。
- 追问 2：为什么两个物体用了同一个 Shader 但 SetPass 还是 2？——keyword 组合不同（变体不同）、或者其中一个用了 MaterialPropertyBlock 破坏了 SRP Batcher、或者中间被别的材质打断了状态连续性。
- 追问 3：渲染顺序会影响 SetPass 吗？——会。Unity 会按材质/变体排序来减少状态切换，但你手动指定 RenderQueue 打乱顺序时，SetPass 会涨。

**坑**
- 别在面试里把 SetPass 说成「就是 drawcall 的另一个名字」。
- 别忽略「drawcall 高但 SetPass 低」这种情况下的正确结论：提交多但状态没碎，优化重点应该是减少物体数/合并网格，而不是换材质。

## 三、GPU 与移动端

### Q9. TBDR 是什么？和 IMR 的区别；为什么移动端「不清屏 / 不切 RT」代价特别大

**答（背这段）**
> TBDR 是 Tile-Based Deferred Rendering。GPU 先把屏幕分成固定大小的 tile，做一遍 binning pass，把所有几何按覆盖关系分进每个 tile 的显示列表；然后逐 tile 处理，几何和着色全部在片上内存（tile memory）里完成，最后才把结果写回 DRAM。因为一个 tile 的几何全都知道，所以能做隐藏面消除（HSR），只对最终可见的片段着色。IMR 是立即模式：整屏帧缓冲在显存里，每个图元一光栅化就把深度和颜色读写到 DRAM。
> 关键推论是：TBDR 的成本模型不是「画了多少像素」，而是「有多少次把片上内存写回 DRAM、又读回来」。每次切换 render target、或者一个 pass 结束，tile memory 都要做 store（写回）和下一个 pass 的 load；切得越碎，这笔全屏带宽付得越多。
> 所以移动端「不清屏」和「乱切 RT」代价特别大：不清屏意味着必须 load 上一帧或上一 pass 的内容（带宽），乱切 RT 意味着每个 pass 边界都要 store + load 一次。正确做法是把所有不透明物体塞进同一个 render pass，load action 用 clear/DontCare、中间深度用 DontCare，把后处理 pass 数压到最少，并且尽量合并成一次「读一次 RT、写一次 RT」的往返。

**细节 / 数字**
- tile 大小和片上内存容量随 GPU 型号不同（PowerVR / Mali / Adreno / Apple 各家不同，片上内存是几十 KB 量级起步），不要在面试里报具体数字，说「随型号不同，以厂商文档为准」。
- 厂商 API 层面对应的是 Vulkan 的 `loadOp`/`storeOp` 和 Metal 的 `loadAction`/`storeAction`；Unity 侧对应 URP Asset 里的 Store Actions 设置（Auto / Discard）以及 RenderPass 的绑定。
- TBDR 上 MSAA 相对便宜（resolve 在片上内存做），这是移动端敢开 MSAA 的原因；但廉价的前提是不打断 tile pass。
- TBDR 上 depth prepass 通常不划算：HSR 已经做了隐藏面消除，prepass 反而多一次深度写入和 store/load；只有当 alpha test/alpha blend 大量存在、HSR 效果被破坏时才值得考虑。
- 判断依据：用厂商工具（Mali 的 Streamline、Adreno 的 Snapdragon Profiler、Apple 的 Metal 计数器）看 tile memory 的 store/load 字节数和总带宽占比。

**追问会问什么**
- 追问 1：怎么减少 render pass 切换？——按「RT 绑定」而不是「材质」组织渲染顺序，把需要同一组 RT 的步骤合并；后处理的多 pass 效果尽量用一次多目标或半分辨率合并。
- 追问 2：不清屏会怎样？——GPU 必须把上一帧内容从 DRAM 读进 tile memory，等于每帧多一次全屏读带宽；而且如果用的是上一帧的随机内容，会有闪烁/拖影之类的错误视觉结果。
- 追问 3：TBDR 上 overdraw 还重要吗？——重要，HSR 只解决不透明物体的隐藏面，半透明和 alpha test 依然逐层着色；而且几何过度细分会让 binning 列表膨胀。

**坑**
- 别说「TBDR 就是延迟渲染」——这里的 deferred 指的是「逐 tile 延迟到几何收集完再着色」，和 G-buffer 延迟着色是两回事。
- 别把 TBDR 的 HSR 说成 early-Z：HSR 是 tile 级整批判定，比 early-Z 更彻底；两个概念不要混用。
- 别背片上门限的具体 KB 数。

### Q10. Overdraw 怎么测、怎么降？（列具体手段）

**答（背这段）**
> 测法从轻到重有四种。最方便的是 Unity Scene 视图的 Overdraw 调试模式，它把渲染结果按加法混合显示，亮度就是叠加层数，适合快速定位「哪块最厚」。第二种是 Frame Debugger 逐个 draw 看覆盖面积，能定位是谁在叠。第三种是厂商工具：Mali 的 Streamline、Adreno 的 Snapdragon Profiler、Xcode 的 Metal 计数器都有逐 pass 的像素/片段计数和带宽读数。第四种最硬也最能拿去面试说：自己写一个加法混合的 debug shader 渲染到一张 RT，最后用 compute 或 `AsyncGPUReadback` 把 1x1 mip 的平均值读回来，得到一个可量化的「平均 overdraw 倍数」，可以进自动化测试。
> 降的手段分三类。第一类是减少层数：严控半透明面积和排序、粒子的同屏数量和生命周期、UI 的全屏半透明层数。第二类是让不透明部分更早被剔除：不透明从前到后排序让 early-Z/HSR 生效，天空盒放最后并做深度测试，用 LOD 和远裁剪减少遮挡物的绘制。第三类是换画法：用 alpha test 或 dithered opacity 替代半透明（注意 alpha test 会破坏 TBDR 的 HSR，在移动端是双刃剑）、把多个全屏后处理合并、避免「一层遮罩盖一层遮罩」的 UI 结构。

**细节 / 数字**
- 报告 overdraw 要给口径：是「不透明 + 透明合计的平均倍数」还是「半透明部分的倍数」，是整屏平均还是只在某区域；平均 2x 和「局部 20x」的体验完全不同，所以要看热力图 + 平均值两个数。
- 排序规则的边界：不透明可以从前到后，但半透明必须从后到前才能得到正确混合——所以半透明的 overdraw 只能靠减少面积和层数，不能靠排序优化。
- 粒子的 overdraw 是最常见的元凶：同屏粒子数、每个粒子的贴图面积、以及「软粒子」的额外采样都在加码；移动端通常要限制发射率和粒子屏幕占比。
- 全屏后处理每多一个 pass 就等于多 1x 全屏读写；把 Bloom、色调映射、调色合并进一个 uber pass 是移动端的标准动作。

**追问会问什么**
- 追问 1：Overdraw 调试模式的结果能当性能数据吗？——不能，它只能定性看分布，因为它把颜色改成了加法混合，测量的是「显示出来的叠加层数」，性能结论要回真机计数器。
- 追问 2：为什么天空盒要放最后？——先画天空盒等于给整屏铺一层底色，所有物体都在它上面叠加；把天空盒放在不透明之后并做深度测试，只有没被遮住的像素才着色。
- 追问 3：alpha test 对 TBDR 的影响？——它让片段可以丢弃，破坏了 HSR 提前确定可见性的能力，可能让 tile 内更多片段进入着色；移动端上「alpha test 不一定比 alpha blend 便宜」是常见误区。

**坑**
- 只说「减少 overdraw」不说怎么量化，会被认为没测过。
- 别把 overdraw 和 fill rate 当同义词：overdraw 是原因，fill rate/像素着色吞吐和带宽是表现。
- UI 的 overdraw 常常被忽略，但全屏半透明遮罩叠几层就非常可观。

### Q11. 移动端最大的瓶颈通常是带宽还是算力？怎么判断？（给可操作的判据）

**答（背这段）**
> 绝大多数情况是带宽和 fill rate，不是 ALU 算力。原因是移动 GPU 的算力近年涨得很快，但内存总线宽度和功耗预算是硬约束；再加上移动端要写多张 RT、做后处理、MSAA，DRAM 读写很容易先撞墙。所以怀疑顺序是：带宽 → fill rate/overdraw → 纹理采样 → ALU。
> 判断要给可操作的实验，不能只说「看 profiler」。我做四个对照实验：一是把 renderScale 从 1.0 降到 0.5，帧时间明显下降就是像素/带宽相关；二是把片元着色器替换成输出常数的极简版本，如果帧时间几乎不动，说明瓶颈不在 ALU；三是把颜色 RT 格式从 8888 降到 565、或者关掉 MSAA，明显变快就说明是带宽敏感；四是减少全屏后处理 pass 数，变快同样是带宽信号。反过来，如果减一半物体帧时间不变，那就不是顶点或 CPU 提交侧。
> 最后一定要加一个移动端专属的条件：必须先让机器跑满 60 秒以上取稳定值。移动端会因为发热降频，前 10 秒和持续一分钟后可能是两个完全不同的帧时间，拿冷启动数据报性能是耍流氓。

**细节 / 数字**
- 厂商工具能直接给带宽数：Mali 上用 Arm Streamline 看 external read/write bytes 和 L2 miss；Adreno 上用 Snapdragon Profiler 看 GPU 计数器和内存带宽读数；iOS 上用 Xcode Metal 计数器看带宽和 occupancy。有工具就报工具读数，没工具就用上面四个对照实验。
- 纹理采样也可能是伪装的瓶颈：采样数多、mip 缺失导致 cache miss、各向异性过滤等级高，都会以「带宽不够」的形式表现出来。
- ALU 真的成为瓶颈的典型场景：复杂 PBR + 多层光照 + 程序化噪声 + 高精度（fp32）运算，尤其在低端机上。判断方法同实验二的反面——把 shader 简化后帧时间明显改善，就是 ALU 或纹理侧。
- 报数口径模板：「机型 + 分辨率 + 画质档 + 持续运行 60s 后的帧时间中位数与 P95 + 是否有降频」，再给带宽读数。

**追问会问什么**
- 追问 1：怎么确认是热降频？——跑 3 分钟，按 10 秒一档记录帧时间；如果单调变差并稳定在某个更低水平，配合机身温度和 GPU 频率读数就是降频。
- 追问 2：把分辨率减半是不是万能手段？——它对带宽和 fill 类瓶颈有效，对 CPU bound 或顶点/剔除类瓶颈基本无效，这也是它作为「判据实验」的价值。
- 追问 3：MSAA 在移动端贵不贵？——TBDR 上相对便宜（片上 resolve），但会增加 tile memory 占用和 RT 带宽；开 4x MSAA 在部分机型上会因为片上内存不够而退化成多次 pass，此时非常贵。以机型实测为准。

**坑**
- 别给「带宽 25GB/s、算力 X TFLOPS」这类具体数字当结论，除非你说清了是哪台机器的哪个配置。
- 别把「GPU 占用率高」等同于 GPU bound：占用率高可能是等待内存（stall）而不是在算。
- 报数据不写持续运行时长，是移动端最容易被抓的点。

### Q12. 移动端渲染的常见降级手段清单，以及「降级要先砍什么」的排序依据

**答（背这段）**
> 清单按模块分：分辨率与画质档（renderScale、动态分辨率、目标帧率分 60/30）、阴影（级联数、距离、分辨率、关软阴影）、后处理（关 SSAO/SSR，Bloom 降 mip 数和分辨率，关运动模糊和景深）、光照（减少逐像素灯数、关附加灯阴影、关实时反射改用 cubemap）、材质（降级到 simple lit / unlit、减采样数、降法线贴图分辨率）、贴图（更低的 mip、更省的压缩格式、关 Opaque/Depth Texture）、几何（更激进的 LOD、impostor、关 GPU 蒙皮以外的重方案）、透明特效（粒子上限、简化 shader、限制屏幕占比）、UI（减少半透明层数、合并图集）。
> 排序依据有三条。第一，按「画质损失/性能收益」的比值排，优先砍收益大、用户又不容易看出来的项。第二，优先砍同时降低带宽和 overdraw 的项——移动端通常卡在这里，所以阴影和透明特效的优先级天然很高。第三，先砍全局开关再砍数值：关掉 SSAO 比把 SSAO 采样数从 16 降到 12 收益大得多、也更好维护。
> 具体顺序我会排成：renderScale → 阴影（级联/分辨率/距离/软阴影）→ SSAO/SSR 类重后处理 → 透明特效面积 → 附加灯数量与阴影 → 分辨率相关 RT 与格式（Opaque/Depth Texture、MSAA）→ 贴图与材质档位 → 几何 LOD → 最后才是帧率档位切换。理由是从像素和带宽开销最大的地方开始砍，而且每一步都可以单独验证。

**细节 / 数字**
- 每一项都要有独立的开关和可测的收益，做成 Quality Level 或设备分档（低端/中端/高端）而不是散落在代码里的 if。
- 降级要配套 verifier：改完用 Q16 的口径重测，确认收益并把「降级前/后」的画面截图留档，面试时能说「我砍了 X，帧时间从 A 降到 B，画面损失是 Y」。
- 阴影的收益通常最大：级联数从 4 降到 2、阴影距离减半，往往能省下整个帧预算的两位数百分比（具体数值自己测）。
- 动态分辨率是最容易自动化的一项：按帧时间反馈调节 renderScale，注意它会造成清晰度抖动，需要加滞回和平滑。

**追问会问什么**
- 追问 1：为什么先砍分辨率而不是先关阴影？——如果瓶颈是 fill/带宽，分辨率是全局一击；但阴影通常同时吃 CPU（阴影 pass 的 drawcall）和 GPU（多一张 shadow map 的 RT 与采样），所以两者常一起动，具体先后看你工程的 profile 结果。
- 追问 2：怎么保证降级后美术不骂人？——拿并排截图和热力图对比，只在「看不清的细节」上砍，并且把降级参数化，方便按机型回退。
- 追问 3：低端机要不要直接锁 30fps？——可以，但要在锁定前确认 GPU 有余量，否则 30fps 也稳不住；锁帧不如把预算花在稳定 P95 上。

**坑**
- 不要给「一刀切砍一半」的方案，降级必须分档、可验证、可回退。
- 别把「关后处理」当第一选择——很多项目的后处理是美术风格的核心，先砍分辨率和阴影往往争议更小。
- 别忽略降级的维护成本：散落在 if 里的降级逻辑比一个统一的 Quality 配置难得多。

## 四、性能测量与优化

### Q13. 怎么判断一帧是 CPU bound 还是 GPU bound？给确定性的测量方法（不要只说「看 Profiler」）

**答（背这段）**
> 前提是先去掉干扰：关 vsync、关 `Application.targetFrameRate` 限制、用 IL2CPP 的非 Development 构建做最终确认、开发构建只用于看 Profiler marker。
> 然后做三个确定性实验。实验一：把 renderScale 降到 0.5。帧时间基本不变 → CPU bound；明显下降 → GPU 的像素/fill 类瓶颈。实验二：在主线程 Update 里插入一个已知的 CPU 空转，比如忙等 3ms。如果帧时间增加约 3ms，说明 CPU 是决定帧率的那一侧（GPU 有余量）；如果几乎不变，说明 CPU 早就在等 GPU，是 GPU bound。实验三：临时隐藏一半可见物体（`SetActive(false)`），帧时间等比例下降说明 CPU 提交/剔除或顶点相关；几乎不变说明瓶颈在 fill/后处理或不在渲染。
> 再补一个工具侧的交叉验证：Unity Profiler 里看主线程耗时和渲染线程的等待状态，GPU 模块（平台支持的话）看 GPU 时间；真机上用 systrace/Perfetto 或 Xcode Metal 看 CPU 线程是否长期卡在 present 或 GPU fence 等待。判据是：GPU 时间接近帧时间 → GPU bound；GPU 时间明显小于帧时间 → CPU bound。要注意双/三缓冲会把 GPU 时间平滑，必须看持续平均值而不是单帧。

**细节 / 数字**
- vsync 必须关：开着 vsync 时帧时间会被量化到 16.6/33.3ms 的整数倍，而且即使 GPU bound，CPU 也会表现成「在等 vsync」，判断直接失效。
- Unity 的 GPU Profiler 有平台要求（部分 Android 需要 Vulkan 且设备支持），采不到 GPU 时间就退回上面三个实验。
- 混合情况很常见：一段时间 CPU bound、一段时间 GPU bound，所以要报「在什么场景、多长时间窗口内」的结论。
- 还要区分主线程 / 渲染线程 / Job worker：渲染线程忙说明提交侧重，主线程忙说明脚本/物理/动画重，两者优化手段完全不同。
- 口径模板：「关 vsync、Development Build + Profiler、同一场景同一相机路径、采 1800 帧」；最终结论要用 Release 构建复测一次。

**追问会问什么**
- 追问 1：为什么 CPU 空转实验有效？——因为它给 CPU 加了一个确定的负载：如果帧时间跟着涨，说明帧率由 CPU 决定；如果不涨，说明 CPU 的时间被 GPU 掩盖了。
- 追问 2：Profiler 本身会不会影响结论？——会，它会引入采样开销，所以用它定位「哪段代码」而不是定绝对帧时间；绝对值要用无 Profiler 的 Release 构建配自定义计时。
- 追问 3：三缓冲下怎么看 GPU bound？——看多帧平均，并且看 CPU 是否稳定处于「等待 fence/present」状态；单帧读数会因为队列里有 2～3 帧在飞而误导。

**坑**
- 只说「看 Profiler」是低分答案，因为 Profiler 只告诉你「哪里花时间」，不直接告诉你「哪一侧是瓶颈」。
- 别在开着 vsync 的情况下下 CPU/GPU bound 的结论。
- 别把 Editor 的 Play 模式数据当性能数据：Editor 有额外开销，且 GPU 行为与真机不同。

### Q14. Unity Profiler / Frame Debugger / RenderDoc / Xcode GPU Capture / Snapdragon Profiler 各自回答什么问题，什么时候用哪个

**答（背这段）**
> 我按「回答什么问题」来分。Unity Profiler 回答「谁在吃时间」：主线程、渲染线程、Job 的时间线分布，哪个脚本哪个系统占了多少，以及内存和 GC。Frame Debugger 回答「这一帧画了什么、按什么顺序、为什么没合批」：它逐 draw 回放，能看到每个 draw 的 shader、keyword、RT、SetPass 分组，是排查合批问题最好的工具，但它会锁帧重放，不能用来测性能。RenderDoc 回答「GPU 实际收到了什么、像素怎么算出来的」：完整的 pipeline state、资源绑定、纹理/RT 内容、pixel history，PC 和 Android（Vulkan）都能抓。Xcode 的 Metal Frame Capture 是 iOS 上最准的，有逐 pass 时间、带宽和 ALU 计数器。Snapdragon Profiler 面向 Adreno：实时 GPU 计数器、带宽、shader 利用率，Mali 对应的是 Arm Streamline。
> 顺序是：先用 Unity Profiler 定位「哪一段」，再用 Frame Debugger 定位「哪些 draw、顺序、合批」，然后上真机用厂商工具或 RenderDoc 定位「GPU 具体花在哪」，改完回到第一步复测。桌面端可以先在 RenderDoc 里看清 GPU 管线，移动端必须上真机——PC 上的结论不能直接搬到手机上。

**细节 / 数字**
- Frame Debugger 的典型用法：顶部看 Draw Calls / Batches / SetPass Calls 三个统计，然后找「同样材质的 draw 为什么没被合在一起」，点开看 keyword 和 SRP Batch 标记。
- RenderDoc 在 Android 上需要 Vulkan（GLES 抓帧支持有限），并且要能被设备调试；抓帧会让程序暂停，不要用它测帧率。
- Xcode 的 Metal 计数器能直接给每 pass 的带宽和 ALU 占比，是 iOS 上判断「带宽还是算力」最省事的路径（对应 Q11）。
- 厂商工具差异：Mali 用 Arm Streamline / Mobile Studio，Adreno 用 Snapdragon Profiler，PowerVR 用 PVRCarbon；面试里说清「我用的是哪一类，看的是哪些计数器」就够。
- 所有 GPU 抓帧工具都会增加开销或改变调度，所以「用抓帧工具得性能数值」是不可靠的，只能得结构和计数。

**追问会问什么**
- 追问 1：为什么不能只用 Frame Debugger？——它不给你时间，只给顺序和状态；「渲染顺序对但就是慢」的 case 必须上 GPU 工具。
- 追问 2：Profiler 的 GPU 模块和厂商计数器冲突吗？——不冲突，前者是引擎视角（粗），后者是硬件视角（细），先粗后细。
- 追问 3：抓帧会不会改变渲染行为？——会，尤其涉及多线程提交、异步计算和驱动优化的路径；对比时要在同一条件下抓。

**坑**
- 别把 Frame Debugger 当成性能工具报数。
- 别只提 Unity Profiler——面试官问这题往往就是想知道你有没有上过真机和 GPU 工具。
- 别把 RenderDoc 说成「手机上也能像 PC 一样随便抓」，Android 的限制（Vulkan、部分驱动不支持、厂商锁）要提一句。

### Q15. 帧预算怎么拆？以 60fps（16.6ms）和 30fps（33.3ms）为例，给一张可写进面试答案的预算表

**答（背这段）**
> 先立两个前提，不然这张表没有意义：第一，预算是按目标机型测出来的，不是通用的，我下面给的是「拆分口径」而不是绝对数值；第二，CPU 和 GPU 不是相加关系，它们是流水线并行的，所以正确的约束是「CPU 帧时间 ≤ 帧预算」且「GPU 帧时间 ≤ 帧预算」，而不是加起来小于预算。
> 拆的时候按渲染阶段分：CPU 侧分游戏逻辑（脚本、物理、动画、UI）、剔除与合批、命令提交、以及渲染线程；GPU 侧分阴影、不透明、透明、后处理、UI/合成。60fps 的 16.6ms 里我会给 CPU 留 4～5ms、GPU 留 12～13ms，并且留 15%～20% 的余量给发热降频——也就是说目标不是「刚好 16.6」，而是「冷机跑在 14ms 以内」。30fps 的 33.3ms 宽松得多，但同样要留余量，而且 30fps 下用户对单帧卡顿更敏感，所以更该盯 P95。
> 报预算表的时候一定要写：机型、分辨率、画质档、是否关 vsync、采样多少帧、是冷机还是持续运行 60 秒后的稳定值。

**细节 / 数字**
- 拆分口径示例（中端 Android / 1080p / URP / 单实时主光 + 阴影 / 无 SSAO / Bloom 半分辨率，冷机 30 秒采样中位数）：

| 阶段 | 60fps 预算（16.6ms） | 30fps 预算（33.3ms） |
| --- | --- | --- |
| CPU 游戏逻辑（脚本/物理/动画） | ≤ 3.0ms | ≤ 8.0ms |
| CPU 剔除 + 合批 + 提交 | ≤ 1.5ms | ≤ 3.0ms |
| 渲染线程 | ≤ 3.0ms | ≤ 5.0ms |
| GPU 阴影 | ≤ 2.0ms | ≤ 4.0ms |
| GPU 不透明 | ≤ 5.0ms | ≤ 10.0ms |
| GPU 透明 | ≤ 2.0ms | ≤ 4.0ms |
| GPU 后处理 | ≤ 2.5ms | ≤ 5.0ms |
| GPU UI/合成 + 余量 | ≥ 1.5ms | ≥ 3.0ms |

- 每一行都要能落到具体指标上才能用：CPU 行看 Profiler 的 marker，GPU 行看厂商计数器的逐 pass 时间；只写总量不写「谁负责」等于没拆。
- 留余量的量级：移动端至少 15%～20%，因为热降频会把冷机性能吃掉一截；桌面端可以少留，但要考虑后台程序。
- 60fps 的精确预算是 16.67ms、30fps 是 33.33ms；面试里说 16.6/33.3 都可以。

**追问会问什么**
- 追问 1：CPU 和 GPU 时间能相加吗？——不能。它们是并行流水线，实际帧时间由较慢的一侧决定（还要算上 present 与缓冲队列的影响）。
- 追问 2：为什么要留 20% 余量？——为了热降频、为了后台干扰、也为了让 P95 不掉帧；按平均值把预算用满是必崩的做法。
- 追问 3：怎么让预算表落到团队里执行？——把它做成自动化检测：CI 上跑固定场景采帧时间，超过阈值就报警，附上同一口径的历史曲线。

**坑**
- 给一张没有口径的表就说是「移动端标准预算」，会被追问到底。
- 别把「帧预算」理解成「优化目标就是平均值达标」，必须盯 P95。
- 别漏掉 UI/合成这一段：它在移动端经常是 1～2ms，容易被忽略。

### Q16. 报告性能数据的规范：为什么必须给中位数与 P95、为什么要关 vsync、为什么要锁定构建类型与分辨率

**答（背这段）**
> 给中位数是因为它代表「典型体验」，给 P95 是因为它代表「卡顿感知」。平均值会把偶发的长帧平均掉，一个偶尔 60ms 的帧在平均值里几乎看不见，但玩家一定会感觉到；而只看最坏帧又无法代表整体，所以中位数 + P95（必要时加 p99 和 max）是一组最小完整的指标。采样量要够：至少上千帧或连续 30 秒，并丢掉预热的前若干帧（着色器编译、资源加载、温度未稳定都在这段时间里）。
> 关 vsync 是因为它会把帧时间量化到刷新周期的整数倍——所有帧都变成 16.6 或 33.3ms，真实耗时被完全掩盖，CPU/GPU bound 的判断也会失效；同时还要关掉 `Application.targetFrameRate` 和系统的帧率限制。等优化做完、要做最终体感验收时再开 vsync 看是否掉到下一档。
> 锁构建类型是因为 Development Build 会开 Profiler 支持、关闭部分优化，Profiler 采样本身也有开销；Mono 和 IL2CPP 差异很大，脚本后端和代码裁剪设置都必须固定，最终数值要用 Release + IL2CPP。锁分辨率是因为帧时间对像素数的敏感度极高——renderScale 差 10% 结论就可能反过来；画质档、目标机型、系统版本、GPU 驱动版本、电量与温度状态也都要一起锁定。

**细节 / 数字**
- 完整数据块模板：机型 + SoC + 系统/驱动版本 + 构建类型（Release/IL2CPP）+ 分辨率与 renderScale + 画质档 + vsync 状态 + 场景 + 采样帧数 + 冷机/持续运行时长 + 中位数/P95/P99/max（CPU 主线程、渲染线程、GPU 分别给）。
- 「快 3 倍」这种话必须展开成：「帧时间中位数从 22.0ms 降到 7.3ms，P95 从 31ms 降到 9ms，同一场景同一分辨率、关 vsync、Release+IL2CPP、持续运行 60 秒后的稳定值、采 3600 帧」。
- 对比实验必须单变量：一次只改一项，其他条件原样保留，否则归因不成立。
- 帧时间直方图比平均数更有说服力，面试里可以直接说「我是用帧时间直方图 + P95 判断的，不是看平均 fps」。

**追问会问什么**
- 追问 1：为什么不直接报平均 FPS？——FPS 是非线性的（16.6ms→33.3ms 是 fps 从 60 掉到 30，看起来只掉一半，但帧时间翻倍），平均 FPS 还会掩盖 stutter。
- 追问 2：Development Build 的数据完全不能用吗？——看用途：定位「哪段代码慢」可以用，报绝对值不行；因为它的优化等级和真机构建不同。
- 追问 3：怎么保证可复现？——固定场景、固定相机路径（自动巡航而不是手动跑）、固定帧数、CI 上重复跑并记录曲线，把环境信息随数据一起存档。

**坑**
- 只给一个中位数不给 P95，等于没覆盖卡顿。
- 温度/降频状态不写，移动端数据会被直接质疑。
- 数据来自 Editor Play 模式的，不要拿去面试说。

### Q17. 一个「画面正常但帧率掉一半」的排查流程，写出固化顺序与每步判据

**答（背这段）**
> 我的第一原则是「先证明是真掉帧，再找是谁」。第一步固定变量并复现：确认是持续掉还是间歇掉，记录机型、分辨率、场景、什么时候开始掉的；移动端先跑满 60 秒看是不是热降频——如果前 10 秒正常、之后掉一半，那不是 bug 是散热。
> 第二步定性：关 vsync、用带了 Profiler 的构建，看主线程时间、渲染线程时间和 GPU 时间三者谁翻倍。CPU 侧翻倍就往脚本/物理/动画/GC 查；渲染线程翻倍就往 drawcall/SetPass/提交查；GPU 侧翻倍就往 pass 数、shader、overdraw、RT 与带宽查。
> 第三到第五步分头查具体元凶。CPU 侧最典型的是每帧分配导致的 GC、某系统的调用次数翻倍（物理、寻路、动画层数）、以及 per-frame 的字符串/Debug.Log。渲染线程/提交侧看 drawcall 与 SetPass 数是否翻倍——新增粒子、新增材质变体、有人加了 MaterialPropertyBlock 把 SRP Batcher 打断了，都会让合批失效。GPU 侧用 Frame Debugger 看 pass 数与顺序是否变化（是不是多了一次全屏 pass、多了一个阴影 pass），再用真机 counter 看是带宽、ALU 还是纹理翻了。
> 最后一个动作最重要：单变量回滚验证归因。把可疑的那一项改回去，帧时间应该回到基线；如果没有，说明归因错了，要继续二分。整个过程要重测并记录，而不是凭感觉下结论。

**细节 / 数字**
- 常见「画面正常但掉一半」的元凶清单（按我遇到过的频率排）：分辨率或 renderScale 被改（后处理 RT 又乘了一倍）、MSAA 或后处理从 1 个 pass 变成多个、阴影级联数或阴影距离被放大、多了一个实时灯或一盏带阴影的灯、透明特效面积或粒子数翻倍、UI 半透明层数翻倍、贴图 mip 掉了导致带宽翻倍（mipmap 未开或被 streaming 卸掉）、有人写了 per-frame 的 `new`/LINQ/字符串导致 GC、某个 shader 变体首次编译造成的一次性 hitch（不是持续掉帧，要分开结论）、以及移动端热降频。
- 每步判据写清楚：降分辨率后帧时间不变 → 排除 fill/带宽类；隐藏一半物体后不变 → 排除 CPU 提交与顶点类；关掉后处理后不变 → 排除后处理类；把 shader 换成输出常数后不变 → 排除 ALU 类。
- 「一次性 hitch」和「持续掉帧」要分开报：前者看首次进入场景的时间点，靠变体预热解决；后者才是持续性能问题。
- 固化成 checklist 的价值：下次同类问题不用重新想顺序，也方便交给别人执行。

**追问会问什么**
- 追问 1：为什么不先看代码改动？——可以，但「最近改了什么」是假设而不是测量；先测量能避免在错误的方向上浪费半天。
- 追问 2：怎么快速二分定位是哪一批物体？——按模块批量 `SetActive(false)`，二分法收敛，配合 Frame Debugger 对比 draw 列表的差异。
- 追问 3：掉一半正好是 2 倍，有没有可能是分辨率或双缓冲的整数关系？——很可能，先怀疑像素数翻倍、RT 数量翻倍、pass 数翻倍的整倍数关系，再去查杂项。

**坑**
- 最容易被抓的点：没有复现条件、没有基线、没有回滚验证就下结论。
- 别把热降频当 bug 修，也别把一次性编译 hitch 当持续掉帧。
- 别在开着 vsync 的状态下判断「掉帧」——那可能只是掉到下一档刷新率。

## 五、资源与内存

### Q18. 纹理压缩格式怎么选（ASTC / ETC2 / DXT / BC7），色块尺寸与质量、内存带宽的关系

**答（背这段）**
> 选择的两个维度是「平台支持」和「用途」。移动端现代设备用 ASTC：它是唯一块尺寸可选的（4x4 到 12x12），4x4 是 8bpp，6x6 是 3.56bpp，8x8 是 2bpp，块越大内存和带宽越省、块状伪影越明显；ETC2 是 GLES 3.0 的必选格式，固定 4x4（RGB 4bpp、RGBA 8bpp），质量明显不如 ASTC，现在主要用于兼容兜底。PC 和主机上用 BC 系列：BC1（DXT1）4bpp 无 alpha、BC3（DXT5）8bpp 带 alpha、BC5 8bpp 双通道（法线贴图首选）、BC7 8bpp 高质量 RGBA（质量接近 ASTC 4x4，但需要 D3D11 以上，移动端不用）。
> 色块尺寸和内存/带宽是线性关系：显存占用 = 宽 × 高 × bpp / 8，mipmap 再加 33%；带宽等于「采样次数 × 每像素字节数 × 缓存命中率」的累积，所以降低 bpp 和开 mipmap 是两个最直接的带宽手段。
> 用途上有几条硬规则：颜色贴图开 sRGB、法线/粗糙度/遮罩必须关 sRGB；法线贴图不要用 BC1/ASTC 的低质量块（块内插值会产生方向性伪影），优先 BC5 或 ASTC 4x4/5x5；HDR 用 BC6H 或 ASTC HDR。

**细节 / 数字**
- BC 系列的平台限制：BC7/BC6H 需要 D3D11 级别（PC、PS4/5、Xbox）；移动端只有部分 Vulkan 设备支持 BC，一般不做主力。
- ETC2 的 RGBA8 是 8bpp，且它的 alpha 通道质量弱；ETC1 没有 alpha 通道。
- PVRTC 是 iOS 的老格式，现在一律建议用 ASTC（iPhone 6 以后都支持 ASTC）。
- Unity 的 Crunch 压缩只省磁盘（包体/下载），不省显存，而且解压有 CPU 代价、质量有损，法线贴图不要用。
- ASTC 在低端 GPU 上的解码成本因厂商实现而异，某些设备上 ASTC LDR 解码很便宜、HDR 解码明显更贵；以机型实测为准。
- 贴图侧的三个高频错误：mipmap 没有开（远处纹理 cache miss 暴增、带宽翻倍）、sRGB 设置错（颜色/法线整体偏）、以及分辨率给得远超屏幕实际需要（一个 4K 贴图贴在屏幕上 200px 的物体上）。

**追问会问什么**
- 追问 1：ASTC 6x6 和 4x4 怎么选？——按屏幕占比：近景主体用 4x4/5x5，中景 6x6，远景和只做遮罩的用 8x8 甚至 10x10；再配合 mipmap，远处的渲染成本自然降下来。
- 追问 2：法线贴图为什么不适合 BC1？——BC1 只有 RGB 且块内只有 4 个插值色，法线这种连续方向场会出现块状和方向性错误，光照下一眼看出来；BC5 用两个通道编码 XY、Z 由重建得到，质量好得多。
- 追问 3：纹理压缩和带宽的关系怎么量化？——按「采样字节数 × 采样次数」估，再用厂商工具的带宽读数验证；结论要给具体机型的具体数值。

**坑**
- 别背「ASTC 一定比 ETC2 好」而无条件：ASTC 的解码成本和设备支持也有边界，低端机占主导的项目要实测。
- 别把 Crunch 当成「压缩格式」，它只是磁盘层。
- 别把 sRGB 设置当成小事，它是「颜色不对」类 bug 的头号原因。

### Q19. 网格与骨骼的优化手段（LOD、顶点数、骨骼数、蒙皮方案、顶点属性压缩）

**答（背这段）**
> 网格侧我分四层。第一层是 LOD：用 LODGroup 按屏幕相对高度切档，通常 3 档（近景全模、中景半模、远景 billboard/impostor），移动端可以把档位调得更激进；注意 LOD 的代价是内存（多套网格）和切换时的 popping，crossfade 会同时画两档、在移动端慎用。第二层是顶点数和属性：用 Optimize Mesh Data / Strip Unused Vertex Attributes 去掉没用的 UV2、切线等属性，用适度的 Mesh Compression（过高会导致接缝裂开和 UV 漂移），把静态物体的变换烘进顶点减少每顶点矩阵。第三层是顶点属性压缩：位置、法线、切线用低位宽量化（法线 8/10 bit、UV 16 bit normalized），但要小心 UV 精度不足导致的贴图抖动、以及不同网格共享接缝时量化必须一致。第四层是剔除：Occlusion Culling 烘焙、远裁剪、以及大量 Renderer 时的剔除开销管理。
> 骨骼侧分三块。骨骼数量直接影响蒙皮成本、骨骼矩阵常量缓冲的大小和 culling 粒度；减少手段有合并末端骨骼、远处角色用低骨骼版本的 LOD、把不需要动的部分烘成静态姿势。蒙皮方案上，CPU 蒙皮省带宽但吃 CPU，GPU 蒙皮（含 Compute Shader / DOTS 方案）把成本挪到 GPU 但要占带宽、并且要注意它和 SRP Batcher / Instancing 的配合。另外 Unity 的 `Optimize Game Objects` 能去掉骨骼 Transform 层级、省下可观的 CPU 与剔除开销，代价是不能再直接 `GetBoneTransform` 或往骨骼上挂点；Animator 的 Culling Mode 和 Update Mode、以及层数与 Avatar Mask 的数量也都直接换算力。

**细节 / 数字**
- LOD 阈值要带口径：「相对屏幕高度 0.6 / 0.2 / 0.05」这种配置要说明是哪个角色、在什么分辨率下测的；不同分辨率的等效像素占比不同。
- 顶点数的目标值必须按项目定：不要背「角色 5000 面」这类数字，说「我们主角是 X 面、同屏 N 个、GPU 顶点处理约占 Y ms」。
- 顶点属性压缩的工具链成本不低：Unity 内置的量化支持有限，通常要自己写 Mesh 后处理工具或用第三方（Simplygon、meshoptimizer 之类）；面试里说清「我们做了哪一步、省了多少带宽」。
- 静态合批与 LOD 不兼容（每级 LOD 是不同网格），大世界通常用 HLOD / impostor 组合，而不是硬合批。
- `Optimize Game Objects` 打开后挂点要用 `Animator.BindTransform` 之类的替代方案，改动前要评估项目里有没有依赖骨骼 Transform。

**追问会问什么**
- 追问 1：GPU 蒙皮一定比 CPU 蒙皮好吗？——看瓶颈：CPU 被蒙皮顶住且 GPU 有余量时收益明显；带宽紧张或角色很少时可能反而更差。必须用 Q11/Q13 的判定方法先定性。
- 追问 2：交叉淡入（crossfade）为什么慎用？——过渡期两档同时渲染，drawcall 和顶点数都翻倍；移动端通常直接用硬切 + 距离阈值微调来掩盖 popping。
- 追问 3：顶点属性压缩的风险？——精度损失导致的接缝、UV 抖动、法线方向错误（光照出现硬边），必须在目标机型上逐项肉眼验收，不能只看数值。

**坑**
- 别把「顶点数少」等同于「性能好」：顶点着色器复杂度、顶点属性数量和 drawcall 数同样重要。
- 别说 LOD 能减少 drawcall——它减少的是顶点和像素开销，drawcall 数一般不变甚至还多一点。
- 别漏掉剔除这一层：很多项目的瓶颈是「剔除了但没剔干净」，尤其是大量小物体。

### Q20. UE 的两张名片：Nanite 与 Lumen 各用一句话讲清原理与代价（以及「UE 你怎么看」怎么答）

**答（背这段）**
> Nanite 一句话：把高模离线切成 cluster 层次结构，运行时用 Compute Shader 做逐 cluster 的视锥和基于上一帧 Hi-Z 的遮挡剔除，只光栅化可见的 cluster，再通过 Visibility Buffer 延迟解析材质，从而做到「几乎不用做 LOD、几乎不用管 drawcall」地渲染影视级几何量。代价是：它走的是一套 Compute 光栅化路径，硬件和 API 门槛高（需要 SM6 级别的 D3D12/Vulkan），传统上对蒙皮、顶点动画、世界位置偏移和透明材质支持受限，而且几何数据本身占磁盘和内存，小三角形多的时候还有 quad overdraw 的问题。
> Lumen 一句话：一套全动态的 GI 与反射方案——近场靠屏幕空间追踪，远场靠 Mesh Distance Field 与 Global Distance Field 做软件光线追踪，配合 Surface Cache 缓存材质光照、再由时空降噪器合成结果。代价是算力开销大（GPU 密集，硬件光追模式还要吃 RT 核心）、对降噪质量敏感、动态变化有延迟和 ghosting、薄几何和小发光体表现差，还需要构建期生成 Distance Field，并且移动端实际不可用。
> 「UE 你怎么看」我的收法是：Nanite 和 Lumen 的本质是「把过去靠美术做 LOD、靠烘焙做光照的成本，换成了 GPU 算力和平台门槛」。所以它们对 PC/主机高端项目是生产力的解放，但对多平台、特别是要上移动端的项目，传统 LOD + 烘焙仍然是主流方案；我自己的判断是「按目标平台选技术，而不是按引擎最新特性选技术」。

**细节 / 数字**
- Nanite 的适用边界：不透明和遮罩材质可以，半透明一般退回传统路径；植被之类的 WPO（世界位置偏移）在较新版本里有支持但代价高；Nanite 与某些自定义顶点动画需要专门的方案。
- Lumen 的成本控制项：Quality / Lighting Quality 档、是否开硬件光追、Surface Cache 分辨率、降噪强度；这些都会显著改变帧时间，所以报 UE 性能数字必须写清这些设置。
- 移动端：UE 的移动渲染路径不支持 Lumen，Nanite 在移动端也是受限/实验性的；把 UE 的高端特性当成移动方案是常见错误。
- 我不做 UE 项目时的安全答法：「我在 UE 上是使用者视角，没做过 UE 的管线改造；原理层面我理解 Nanite 是 cluster + 可见性缓冲 + 延迟材质、Lumen 是软件光追 + 距离场 + 时空降噪，代价是算力和平台门槛。」——承认边界比硬吹更加分。
- 如果想继续加分，可以把它和 Q6/Q19 连起来：Nanite 解决的是「几何与 drawcall 的规模问题」，Lumen 解决的是「动态光照的问题」，两者都在用 compute 与缓存换传统管线的工作量。

**追问会问什么**
- 追问 1：Nanite 和「GPU-Driven 渲染」什么关系？——Nanite 可以看成 GPU-Driven 的一个极端实现：剔除、光栅化调度都在 GPU 上，CPU 几乎不参与逐物体提交。
- 追问 2：Lumen 和传统烘焙光照的取舍？——烘焙的成本在构建期和内存、换来运行时的低开销和稳定画质；Lumen 是运行时的灵活性和动态性，换来算力消耗和时域瑕疵。
- 追问 3：如果要用 UE 做一个移动端项目你会怎么选？——关掉 Lumen，Nanite 按平台能力评估（或直接用传统 LOD），保留可切换的前向/移动渲染路径，重点放在 drawcall 与带宽控制上，也就是本册 Q6/Q11/Q12 的那套方法。

**坑**
- 别把 Nanite 说成「自动 LOD 系统」——它确实弱化了 LOD 需求，但机制是 cluster 剔除和可见性缓冲，不是生成 LOD。
- 别把 Lumen 说成「光栅化的屏空间 GI」——远场是距离场软件光追，只提屏幕空间会显得只知道一半。
- 别硬吹自己做过 UE 的源码改造，面试官一句追问就会露底。

## 性能题的自证模板

- 一句话结构：「基线是什么 → 我怎么测的 → 改了什么 → 数字变成多少 → 什么条件下失效」。
- 示例：「场景 X、中端 Android / 1080p / URP / Release+IL2CPP、关 vsync，跑固定相机路径采 3600 帧，帧时间中位数 21.8ms、P95 30.5ms，主线程 12ms 是瓶颈。」
- 归因句：「把 1200 个植被从独立 Renderer 改成 GPU Instancing 后，渲染线程从 8.2ms 降到 3.1ms，帧时间中位数 21.8ms→15.2ms、P95 30.5ms→18.9ms。」
- 边界句：「这个结论只在同屏实例数超过约 500 时成立，低于这个量级时 per-instance 缓冲的开销会抵消收益，我用开关对比验证过。」
- 工具句：「定性用 Unity Profiler 与 Frame Debugger，定量用真机 GPU 计数器看逐 pass 时间和带宽；抓帧工具只用来查结构，不用来报帧率。」
- 复现句：「所有数字都是热机稳定值，持续运行 60 秒后取；编辑器数据我不用来报绝对值。」
- 诚实句：「这一项我没测到 GPU 侧计数器，只有 CPU 侧 marker 与端到端帧时间，所以我只敢说 CPU 提交侧变快了。」
- 收尾句：「要再往前一步，我会把同一套口径做成 CI 回归，防止下次改动把它退化回去。」

# 实现办法 · 先量化再优化（诊断驱动）

## 套路（三步，顺序不能反）

1. **量化现象**：把"慢/噪/错"变成数字（帧时间、样本数、误差量级、像素占比）。
2. **量级估算定位**：用费米估算圈定嫌疑——**如果某个量级对不上，机制就找错了**。
3. **改一处、用同一把尺子复验**：一次只动一个变量，改完必须用**与改之前相同**的测量方法对比。

## 五个项目里的实例

| 现象 | 量化与归因 | 改动 |
|---|---|---|
| **SDF** 粒子 `orbCurrentY` 暴涨到 **12700+** | 从量级反推：1000 粒、$y\approx3$ 应得 $\approx6147$ → 嫌疑指向加权平均**漏乘权重**（分母算了、分子没算） | `InterlockedAdd` 补权重（1 行）+ 溢出核验 |
| **render_unified_oss** ReSTIR N=32 与 N=1 无差别 | 三层归因：M-cap **硬截断把样本质量均衡化** / 空间复用稀释 / SVGF 兜底；稳态推导有效样本 ~960 vs ~30 | 帧窗口制 `dynCap = N×F`：只压缩历史、不稀释新样本 |
| **render_unified_oss** 金属球"像玻璃球" | 数值：球内峰值 RGB **153 vs 5.6** → 根因不是材质，而是 `packColor` 硬钳制 | 显示链改软拐点 tone map（代价：全模式观感基线重建） |
| **TA_show** 雾 pass 每像素两次全步数行星积分 | 估算法：步数 × 像素数 ⇒ 纯浪费；且这部分观感由烘焙 cubemap 已能承担 | 删 ray-march，改仰角驱动解析雾 + 脏检查节流 |
| **water** 单次散射嵌套步进 32×64 ≈ **2000 次/像素** | 量级直接判死刑 | 透射率 LUT（256×128）→ 多散射 LUT 不动点迭代（32×32、2 轮） |
| **TA_show** 41 万顶点网格 | 顶点量 × 每顶点成本；分窗口统计 | 顶点退化 + 片元早退双保险，实测砍窗口内约 **36%** |
| **engram** 图卡顿 | 归因到"全图节点**每帧**写 width/height" | 位置缓存 + 样式旁路收窄 + 波前增量点亮 + 30 fps 节流 |

## 三条可复述的原则

1. **先测后猜，且要测对的东西**：帧率低不等于 GPU 慢（可能是提交/脚本/编辑器开销）；光栅是 CUDA 软件光栅化时，"draw call 太多"这种话直接暴露你不了解架构。
2. **量级估算是最便宜的诊断**：算一次"步数 × 像素数"比读一天代码快得多，且能立刻排除大半嫌疑。
3. **优化要留复验口径**：改前改后用同一命令、同一参数、同一分辨率；否则"感觉快多了"不是结论（`render_unified_oss` 的 `benchmarks/` + `regress.ps1` 就是为这个存在的）。

## 已知的短板（要如实说）

- 六个项目**几乎没有系统性的帧时间/带宽数据**：`render_unified_oss` 全仓库只有 README 一句 `~95 ms/frame @1280×720`；`water`、`windtest`、`SDF`、`TA_show` 都没有 CPU/GPU 耗时记录。
→ **面试前最该补的一件事**：任选一个项目补一次 Profiler/计时测量，把"我做过优化"升级为"我优化了 X%，测量方法是 Y"。

## 可能被追问的三层

1. **原理层**：CPU bound 与 GPU bound 怎么区分？TBDR 与 IMR 的瓶颈位置差异？为什么"减少 draw call"在软件光栅化里不适用？
2. **实现层**：Unity Profiler / Frame Debugger 分别看什么？GPU 计时为什么要用 timestamp query？怎么测"改动的净收益"（隔离变量）？
3. **边界层**：什么时候不该优化（正确性未定、需求会变、平台会换）？优化引入的复杂度怎么控制（回退开关、参数化档位）？

# 面试八股文题库 · 01 · 渲染管线与光栅化

**本册用法**：每一节的「答（背这段）」是面试现场该说的话，先背到能一口气说完；「细节／公式」是白板题要写的东西；「追问」用来做二次压力测试；「坑」是别人踩过、面试官爱抓的地方。**只背加粗部分是不够的**——TA 面试拉开差距的全在「追问」与「坑」里。

---

## 一、管线总览

### Q1. 渲染管线分哪几个阶段？哪些是可编程的？

**答（背这段）**
> 通常拆成三个阶段：**应用阶段、几何阶段、光栅化阶段**。
> 应用阶段在 CPU 上跑，负责剔除、排序、合批、把渲染数据（drawcall）准备好。
> 几何阶段在 GPU 上，把顶点从模型空间一路变到屏幕空间：顶点着色器 → （曲面细分 → 几何着色器，可选）→ 图元装配 → 裁剪 → 透视除法 → 视口变换。
> 光栅化阶段把图元变成片元：三角形设置 → 三角形遍历 → 片元着色器 → 逐片元操作（模板测试、深度测试、混合）。
> **可编程的只有三个阶段**：顶点着色器、几何着色器、片元着色器（现代 API 里再加曲面细分与计算着色器）；其余都是固定功能硬件。

**细节／公式**
- 现代 GPU 还有 **Compute Shader**，它不属于这条管线，是独立的通用计算通道，做 GPU 粒子、后处理、剔除都走它。
- 光栅化阶段的「三角形设置／遍历」是硬件的固定功能，不可编程——面试时别说成"我自己写光栅化"。

**追问会问什么**
- 追问 1：应用阶段具体做什么？→ 视锥剔除、遮挡剔除、排序、设置渲染状态、提交 drawcall；CPU 与 GPU 是**并行**的，CPU 太快会被驱动缓冲挡住（"喂不饱"不算瓶颈）。
- 追问 2：几何着色器为什么实际很少用？→ 它输出的图元数量不可预测，会破坏 GPU 的并行批次调度，很多移动 GPU 干脆不支持或性能极差。
- 追问 3：计算着色器相比片元着色器的优势？→ 不绑定光栅化、可任意读写缓冲、可跨线程共享内存做规约（比如粒子数量压缩、Hi-Z 生成）。

**坑**
- 把「裁剪」说成在 NDC 里做。**裁剪发生在裁剪空间、透视除法之前**，这是高频抓点。
- 把「逐片元操作」说成"片元着色器的一部分"，它是片元着色器**之后**的固定功能阶段。

### Q2. 顶点着色器到片元着色器之间，硬件到底做了哪些事？

**答（背这段）**
> 顺序是：顶点着色器输出的裁剪空间坐标 → **图元装配**（把顶点按索引组成三角形）→ **背面剔除**（按屏幕空间绕序）→ **视锥裁剪**（对 6 个裁剪面做齐次裁剪，裁剪产生的三角形需要重新插值属性）→ **透视除法**（$x/w, y/w, z/w$，得到 NDC）→ **视口变换**（映射到屏幕像素坐标，$z$ 映射到深度范围）→ **三角形设置**（算出边的方程）→ **三角形遍历**（找出被覆盖的像素/采样点，生成片元）。
> 到片元着色器时，你拿到的是插值后的属性。

**细节／公式**
- 透视除法：$(x_c, y_c, z_c, w_c) \to (x_c/w_c,\, y_c/w_c,\, z_c/w_c)$，$w_c$ 在标准透视投影下等于 $-z_{view}$。
- 裁剪为什么在除法前：$w$ 可能为 0 或负（顶点在摄像机后面），先除会出现无穷大与图元翻转；齐次空间里比较 $-w \le x \le w$ 就能正确裁剪。
- NDC：OpenGL 是 $[-1,1]^3$；D3D 的 $z$ 是 $[0,1]$。**别混着说**。

**追问会问什么**
- 追问 1：裁剪产生的三角形顶点属性怎么来？→ 沿裁剪边做线性插值（在齐次空间里插值 $x,y,z,w$ 与各属性，最后再统一做除法，结果才正确）。
- 追问 2：背面剔除能关吗？什么时候必须关？→ 双面材质、布料、树叶卡片、以及镜像变换导致绕序翻转的时候（**平面反射**的经典坑）。
- 追问 3：视口变换为什么 $y$ 常常要翻转？→ 屏幕原点在左上、NDC 原点在中心；加上渲染纹理（RT）在 D3D 与 GL 之间上下方向约定相反，所以后处理常要处理 UV 翻转。

**坑**
- 说"先透视除法再裁剪"——**错**，顺序反了。
- 忘了裁剪会**产生新三角形**，以为它只是"丢弃"。

### Q3. 透视投影矩阵里的 $1/z$ 是怎么来的？正交和透视差在哪？

**答（背这段）**
> 透视投影的本质是**"除以深度"**——近大远小。做法分两步走：先用一个矩阵把 $z$ 分量搬到 $w$ 分量上（这样 $w$ 就等于 $-z_{view}$），再由硬件统一做透视除法。
> 所以矩阵的作用不是"除"，而是"把要除的东西放到 $w$ 里、同时把视锥压成一个立方体"。正交投影不需要近大远小，$w$ 保持为 1，所以它只是一个缩放加平移。

**细节／公式**
OpenGL 风格的透视投影矩阵（右手系，看向 $-z$，NDC 为 $[-1,1]^3$，$n$ 近、$f$ 远）：

$$
P=\begin{bmatrix}
\frac{1}{\tan(\theta/2)\cdot a} & 0 & 0 & 0\\
0 & \frac{1}{\tan(\theta/2)} & 0 & 0\\
0 & 0 & -\frac{f+n}{f-n} & -\frac{2fn}{f-n}\\
0 & 0 & -1 & 0
\end{bmatrix}
$$

- 关键在最后一行：$w' = -z_{view}$。
- 深度映射：$z_{ndc} = \frac{-z_{view}\cdot\frac{f+n}{f-n} - \frac{2fn}{f-n}}{-z_{view}} = \frac{f+n}{f-n} + \frac{2fn}{(f-n)\,(-z_{view})}$——**深度与 $1/z$ 成正比**，这是后面所有深度精度问题的根源。

**追问会问什么**
- 追问 1：为什么深度不是线性的？→ 因为投影已经"除以了 $z$"，屏幕空间深度反比于视空间深度；近处分辨率极高、远处急剧退化。
- 追问 2：怎么改善远处精度？→ 拉大近平面（最有效）、反向 Z、对数深度缓冲、分段视锥（多相机 / CSM 思路）。
- 追问 3：正交投影还有 $w$ 吗？→ 形式上有（齐次坐标第 4 维），但恒为 1，所以透视除法是恒等变换。

**坑**
- 把 $w$ 说成"必须等于 1"。**透视投影下 $w = -z_{view}$，正是它承载了近大远小。**
- 矩阵元素记混（尤其 D3D 与 GL 的 $z$ 映射范围不同、行主序/列主序）。白板题上先声明你的约定，再写。

## 二、光栅化与插值

### Q4. 光栅化怎么判断一个像素在不在三角形里？

**答（背这段）**
> 用**边函数（edge function）**，等价于二维叉积。对三角形的三条有向边各算一次：$\text{edge}(A,B,P) = (B-A)\times(P-A)$ 的 $z$ 分量。如果三个值的符号全部一致（全正或全负，取决于绕序），点在三角形内；有零则在边上。
> 这三个值（除以总面积归一化后）就是**重心坐标** $\alpha,\beta,\gamma$，所以"判断内外"和"插值属性"用的是同一套数——这是光栅化硬件能一次算完的原因。

**细节／公式**
重心坐标：$P = \alpha A + \beta B + \gamma C$，$\alpha+\beta+\gamma=1$。
- $\alpha, \beta, \gamma$ 就是三个小三角形面积与大三角形面积之比。
- 屏幕空间内遍历时，边函数是**增量式**的：沿 $x$ 走一步只加一个常数，这是扫描线能跑这么快的原因。

**追问会问什么**
- 追问 1：采样点在像素中心还是别处？→ 默认在像素中心（D3D 的约定），MSAA 下有多个子采样点；采样位置直接决定几何边缘的锯齿形态。
- 追问 2：MSAA 为什么比 SSAA 便宜？→ MSAA 只对**覆盖率和深度/模板**做多采样，**片元着色器仍然每个像素只跑一次**；SSAA 是整个管线按更高分辨率跑再降采样。
- 追问 3：怎么处理"共享边"归属？→ 用 top-left 规则，保证共享边只被一个三角形覆盖，避免双重着色与缝隙。

**坑**
- 说"用包围盒判断"——包围盒只用来**加速**，最终判据还是边函数。
- 忽略浮点误差：屏幕空间边缘上容易出现同时落入或都不落入的裂缝/双重覆盖，这就是"几何接缝处露点/亮点"的来源。

### Q5. 为什么插值要除以 $w$？透视校正插值怎么推？

**答（背这段）**
> 因为**屏幕空间是透视投影后的空间，屏幕上的均匀步长在三维里不是均匀步长**。近处一小段屏幕距离对应的三维距离短，远处对应得长，所以直接按屏幕重心坐标线性插值属性，结果会错——最典型的就是长走廊地面的纹理被"拉扯"。
> 正确的做法是：**在屏幕空间线性插值 $\text{attr}/w$ 与 $1/w$，然后把两者相除**。

**细节／公式**
设屏幕重心坐标为 $b_i$（即上面算出的 $\alpha,\beta,\gamma$），则

$$
\text{attr} = \frac{\sum_i b_i \cdot \frac{\text{attr}_i}{w_i}}{\sum_i b_i \cdot \frac{1}{w_i}}
$$

推导要点：三维空间中的线性插值参数 $t$ 与屏幕空间参数 $s$ 满足 $t = \frac{s/w_1}{(1-s)/w_0 + s/w_1}$（一维两顶点情形），分子分母各是一次函数，故可写成上面那个统一形式。硬件保留的是 $\frac{1}{w}$ 的倒数（即 $w$），在做插值时做一次除法。

**追问会问什么**
- 追问 1：这个除法有代价吗？→ 有，片元着色器里每个透视校正插值都要一次除法；所以 `noperspective` / `nointerpolation` 修饰符在移动端偶有收益（但编译器往往已经处理了）。
- 追问 2：哪些量**不**需要透视校正？→ 本质上是"屏幕空间量"的，比如屏幕坐标、片元深度（已经是 $1/z$）；以及确实想按屏幕均匀变化的量，如屏幕空间 UV 效果。
- 追问 3：顶点着色器里算好还是片元里算？→ 能在顶点算的就在顶点算——但**注意**：顶点着色器里算的线性插值结果是屏幕空间线性的，不是透视校正的，所以像"世界空间位置"这类必须靠 `SV_Position` / `w` 反推。

**坑**
- 面试官常问："我把世界坐标插值到片元再算距离，对吗？"→ 需要除以 $w$（或直接用 `SV_Position.w` 反算），否则远处会系统性偏大/偏小。这是很实战的一个雷。

## 三、深度、剔除与排序

### Q6. early-Z 是什么？什么情况下会失效？

**答（背这段）**
> early-Z 是硬件在**片元着色器之前**先做深度测试、把被遮挡的片元直接丢掉，省下整个着色开销。这是最便宜的优化之一，但它的前提是"深度测试的结果不依赖着色结果"。
> **一旦着色器写入深度（`SV_Depth`）、使用 `discard`（clip/alpha test）、或开启了 alpha to coverage 之类的功能**，硬件就无法提前判断，会退化成 late-Z——着色照跑、最后才测深度。

**细节／公式**
- late-Z 下 overdraw 的代价是**满额**的：着色一次、被丢弃，白干。
- 常见对策：**Depth Prepass**（先只写深度的 pass，再带着 `ZEqual` 跑着色）——代价是多一遍几何，收益是复杂着色器下省掉大量无效着色。
- 如果必须 `discard`（树叶、草地、粒子），**尽量把 discard 移到最早、让着色尽量少**，或改用 alpha-to-coverage / 不透明近似。

**追问会问什么**
- 追问 1：early-Z 与 hi-Z 是一回事吗？→ 不是。early-Z 是**逐像素**的硬件优化；hi-Z（hierarchical Z）是**层级深度缓冲**，用于遮挡剔除与快速深度测试。
- 追问 2：为什么"从前到后排序不透明物体"有意义？→ 前面先画的东西能挡住后面，让 early-Z 生效；这就是渲染队列按距离排序的理由（注意：合批会打乱排序，需要权衡）。
- 追问 3：反向 Z 与 early-Z 有冲突吗？→ 没有，配合使用更好：反向 Z 让远处也有足够精度，early-Z 比较的是同一精度下的值。

**坑**
- 把 early-Z 说成"软件优化"或"引擎功能"。它是**GPU 硬件行为**，引擎只能创造条件让它生效。
- 以为 `clip()` 没关系。**现代引擎里大量效果用 clip，这正是移动端 overdraw 高的常见原因。**

### Q7. Z-fighting 是怎么来的？怎么解决？

**答（背这段）**
> Z-fighting 的根源是**深度缓冲精度在屏幕空间是非线性的**——投影时做了透视除法，深度与 $1/z$ 成正比，所以绝大部分精度被消耗在近平面附近，远处两个面即使世界空间间隔不小，在深度缓冲里也可能落到同一个量化值上，于是渲染顺序漂移、出现条纹状闪烁。
> 解决办法按性价比排：**拉大近平面**（最立竿见影）→ **用反向 Z + 浮点深度缓冲** → 缩短远近平面的比值范围 → 对数深度缓冲 → 对共面物体直接消除（把贴花抬起来、用深度偏移 / polygon offset、或者干脆合并几何）。

**细节／公式**
用浮点深度缓冲时，深度分辨率与 $\frac{z^2}{\text{near}}$ 及浮点尾数位数相关。**关键是 $f/n$ 的比值**：$n=0.1,\,f=1000$ 的比值是 $10^4$；改成 $n=1,\,f=1000$ 就降到 $10^3$，精度立刻好一个数量级。

**追问会问什么**
- 追问 1：为什么近平面推远有效？→ 精度分配是非线性的，近平面是所有精度的"锚点"；把锚点往外挪，整条曲线上的可用精度都会重分配。
- 追问 2：polygon offset 的原理？→ 在光栅化时给深度加一个与斜率相关的偏移常量，把共面几何分开；它是**规避**而不是解决精度问题。
- 追问 3：还有哪些常见 Z-fighting 场景？→ 地面与贴花、玻璃与窗框、UI 面片与背景、大规模场景中远距离物体。

**坑**
- 说"提高深度缓冲位宽就能解决"。位宽只是缓解，**非线性分布才是根因**；24 位整数深度在 $f/n$ 很大时一样打。
- 忘了 near plane 同时影响**视锥剔除**（太大会切掉近处的物体）和精度，面试时应该主动说出这个取舍。

### Q8. 常见的剔除手段有哪些？

**答（背这段）**
> 从便宜到贵排：**背面剔除**（固定功能，几乎免费）→ **视锥剔除**（把包围盒与 6 个面做测试，可做层级包围体加速）→ **距离／小物体剔除** → **遮挡剔除**（硬件 occlusion query 或软件 Hi-Z，先画大的遮挡体再测其余物体）→ 最后是 **LOD 与 impostor**（不是剔除但目的相同：降低远处成本）。
> 工程上还有一个常被忽略的：**渲染队列与批处理的剔除粒度**——剔除的粒度太细反而 CPU 更贵，要按批次/实例组做粗剔除。

**细节／公式**
- 视锥剔除就是"包围盒的顶点是否全部落在某个裁剪面的外侧"：对 6 个面逐个做平面测试，只要有一个面把所有顶点都排除，就整体剔除。
- Hi-Z 遮挡剔除：用上一帧或本帧已生成的**层级深度缓冲**做金字塔下采样，先测最大的层级（一个像素代表一大块屏幕区域），只有"可能可见"才下探到更细的层级——这是"保守 + 快速"的经典结构。

**追问会问什么**
- 追问 1：为什么遮挡剔除容易"漏剔"而不是"误剔"？→ 必须是**保守**的：宁可多画也不能少画，否则画面缺东西；所以判据是"确定不可见才剔除"。
- 追问 2：为什么遮挡查询（occlusion query）在现代引擎里不常用了？→ 它需要 GPU→CPU 回读，会造成**同步等待/管线气泡**；Hi-Z + compute 的 GPU 侧方案才不打断流水线。
- 追问 3：剔除和 LOD 冲突吗？→ 会：LOD 切换的瞬间几何变了，包围体也要同步更新，否则会出现"剔除掉了本该可见的低模"。

**坑**
- 只说"视锥剔除"就停。TA 面试更想听**遮挡剔除的实现代价**和**保守性要求**。
- 把 LOD 说成剔除。**LOD 是降成本，剔除是不画**，是两件事，面试时主动区分是加分项。

### Q9. 透明物体为什么要从后往前画？渲染队列怎么设计？

**答（背这段）**
> 因为透明走的是**混合（blending）而不是深度写入**：混合是"源与目标按权重叠加"，它**不满足交换律**，顺序错了颜色就错。为了得到正确的"从近到远的叠加"，必须先画远的、再画近的。
> 不透明物体则相反，要**从前到后**画，利用 early-Z 省掉被遮挡的着色。所以一条管线的渲染顺序通常是：不透明（前→后）→ 天空盒 / 地面 → 透明（后→前）→ 后处理。

**细节／公式**
- 排序键通常用**包围盒中心到相机的距离**，而不是逐三角形排序——逐三角形太贵，所以透明交叠严重时错误是**正常的**。
- 经典 Alpha 混合：$C_o = C_s \cdot \alpha_s + C_d \cdot (1-\alpha_s)$。
- 想真正正确，需要 **OIT（顺序无关透明）**：深度剥离（depth peeling）、加权混合（WBOIT）、逐像素链表（per-pixel linked list）。工程上最常用的是 **加权混合**：用深度做权重、可加性累加，代价低但近似，且**不含折射/透射**。

**追问会问什么**
- 追问 1：半透明物体要写深度吗？→ 通常**关掉深度写入但保留深度测试**：写深度会把后面的透明物体挡掉。
- 追问 2：PBR 的透明与 alpha 怎么配合？→ 透明仍要用线性空间做混合（在 sRGB 空间混合会偏亮/偏暗），且预乘 alpha（premultiplied）能减少多次叠加的溢色。
- 追问 3：为什么透明不能合批？→ 需要排序，而合批会按材质/网格分组、破坏排序；这是"性能 vs 正确"的经典冲突。

**坑**
- 说"透明是深度测试失败的"——不是，透明是**主动关闭深度写入**。
- 把 alpha test（硬边、写深度、可 early-Z）和 alpha blend（软边、不写深度）混为一谈。这两个是不同路径。

## 四、抗锯齿

### Q10. 抗锯齿方案怎么选？MSAA、FXAA、TAA 的原理与代价

**答（背这段）**
> 按"在哪一步解决"分三类：
> **超采样类**：SSAA 整管线高分辨率再降采样，质量最好、代价最高；**MSAA** 只对覆盖率和深度做多采样、着色仍是每像素一次，是"性价比很高的几何边缘抗锯齿"，但对**着色器内部的走样（高光、纹理、透明）无效**。
> **用词要分清「屏幕/RT 像素」和「贴图」**：MSAA 的亚像素在 RT 像素内部，既不动贴图分辨率，也不增加对贴图的采样次数——因果展开见「抗锯齿的采样层级」。
> **后处理类**：FXAA/SMAA 在最终图像上找边缘并模糊，几乎没有几何信息，因此对高光闪烁和亚像素细节基本无效，但极便宜。
> **时域类**：**TAA** 用抖动采样 + 上一帧历史 + 运动矢量做累积，覆盖面最广（几何、着色、透明都抗），代价是**拖影（ghosting）、细节变糊、运动物体边缘不稳**，需要配套的处理（速度矢量、邻域裁剪、锐化）。

**细节／公式**
- MSAA 的样本数：2x/4x/8x，显存与带宽按样本数增长；**在 TBDR 移动端，MSAA 的解析（resolve）成本和高带宽占用是主要顾虑**。
- TAA 的核心：本帧用亚像素抖动（Halton 序列）采样，把结果与投影到本帧的历史帧混合：$\text{out} = \alpha \cdot \text{cur} + (1-\alpha)\cdot \text{history}(\text{reprojected})$；$\alpha$ 越小越稳但越糊、拖影越明显。
- 现代上采样器（DLSS / FSR / XeSS）本质是"TAA + 机器学习/自适应重建"，把低分辨率渲染上采到高分辨率，同时抗锯齿。

**追问会问什么**
- 追问 1：为什么 MSAA 对高光无效？→ 因为它**每个像素只着色一次**，像素内部的着色变化根本没被采样；高光、镜面闪烁属于着色走样。
- 追问 2：TAA 拖影怎么缓解？→ 邻域颜色裁剪（clamp 历史到本帧邻域范围）、用速度矢量正确地重投影、对快速运动物体降低历史权重、对静止场景提高权重。
- 追问 3：透明物体怎么抗锯齿？→ MSAA 对透明无效（它不写深度、覆盖与着色脱节），只能靠 TAA 或 alpha-to-coverage（把 alpha 转成覆盖率，得到软边但仍写深度）。

**坑**
- 把 FXAA 说成"基于几何边缘"。它是**基于亮度梯度**的像素级启发式，没有几何信息。
- 说"开了 MSAA 就没有锯齿了"。**着色走样、纹理走样、透明边缘都还在**——这句话一说，面试官就知道你没调过画质。

## 五、渲染路径与状态

### Q11. 前向渲染、延迟渲染、Forward+ 的原理与代价

**答（背这段）**
> **前向渲染**：每个物体在同一个 pass 里计算所有光源，光照结果直接写进帧缓冲。简单、支持 MSAA、支持透明，但**光源数量直接乘进着色成本**，多光源场景爆炸。
> **延迟渲染**：先把几何信息（albedo、法线、粗糙度、金属度、深度）写进 G-Buffer，再用一个全屏 pass 逐像素解算光照。光照成本与物体数解耦、只和屏幕像素数有关，因此**支持海量光源**；代价是 G-Buffer 的**巨大带宽与显存占用**、MSAA 基本没法用（要用 MSAA 就得成倍放大 G-Buffer）、透明物体仍得另走前向、且难以支持多样的材质模型。
> **Forward+（Tile/Cluster）**：先用 compute 把屏幕切块并为每块建立光源列表，再做前向渲染、只遍历本块的光源。它拿到延迟渲染"光源解耦"的好处，又保住了前向的 MSAA/透明/材质灵活，是现代主流选择。代价是需要一个额外的光源分配 pass，且块边界处理有开销。

**细节／公式**
- 带宽估算：G-Buffer 若含 albedo(4B) + normal(4B) + 材质参数(4B) + 深度(4B) = 16 B/像素；1080p 一帧写入 + 读取至少 $\approx 2\text{M} \times 16 \times 2 \approx 67$ MB，60fps 就是 4 GB/s 量级——**移动端直接判死刑**。
- 延迟渲染的经典优化：把 G-Buffer 打包得更紧（法线用八面体编码到 2 通道、材质参数打包进一个 uint）；或改用 **Visibility Buffer**（只存三角形 ID + 重心坐标，延迟到着色时再取属性）。

**追问会问什么**
- 追问 1：延迟渲染怎么做抗锯齿？→ 通常靠 TAA/FXAA 等后处理方案，或调整 G-Buffer 布局做 MSAA；这是它与 MSAA 天生不合的根因。
- 追问 2：延迟渲染能画透明吗？→ 不能正确画。透明物体没有唯一的一个"表面"，G-Buffer 存不下多个深度层；标准做法是延迟跑不透明、透明回退前向。
- 追问 3：Forward+ 的"块"和 TBDR 的"块"是一回事吗？→ **不是**。Forward+ 的 tile 是**软件**在 compute 里划分的光源列表；TBDR 的 tile 是**硬件**的渲染分块（on-chip memory）。这个区分很能体现理解深度。

**坑**
- 说"延迟渲染一定比前向快"。它是**用带宽换光源灵活性**，在光源少、物体少的场景反而更慢。
- 忘了透明物体和 MSAA 这两个"延迟渲染的死角"。

### Q12. Drawcall、SetPass call、合批手段

**答（背这段）**
> **Drawcall** 是 CPU 向 GPU 提交一次绘制命令；**SetPass call** 是提交一次着色器/渲染状态的切换。后者往往更贵，因为它意味着 GPU 要换一整套状态、批处理被打断。
> 降低开销的手段：**静态合批**（把静态物体合并成一个大网格，用内存换 drawcall）、**动态合批**（顶点数少的小物体在 CPU 合并，现代管线基本被 SRP Batcher 取代）、**GPU Instancing**（同一网格 + 同一材质、每实例数据走实例缓冲）、**SRP Batcher**（Unity 的 SRP 下让"相同 shader 变体"的物体共享常量缓冲、只更新每物体数据，从而减少 SetPass）、**Indirect / GPU-Driven**（顶点与实例数据全在 GPU 侧，CPU 只发一条命令）。

**细节／公式**
- 触发条件各不相同且**互斥**：静态合批要求标记为静态且不移动；动态合批有顶点数上限，且会被光照、缩放、材质属性（per-renderer 材质属性）打断；Instancing 要求材质完全相同；SRP Batcher 要求**同一个 shader 变体**（不同 keyword 就断）。
- 判断瓶颈：如果 Profiler 里 `Batch Count` 高但 GPU 时间不高，是 CPU 提交瓶颈；如果 `SetPass Calls` 高，说明状态切换频繁。

**追问会问什么**
- 追问 1：为什么材质属性会打断合批？→ 因为材质参数要么进常量缓冲（每批一次更新就会断批），要么用 `MaterialPropertyBlock`；SRP Batcher 的做法是把每物体的常量缓冲**单独分配**，从而允许不同材质参数共享同一个着色器状态——这就是它能减少 SetPass 的原因。
- 追问 2：合批有副作用吗？→ 有：静态合批会增大内存与包体、破坏剔除粒度（一个大网格要么全画要么全不画）、让 LOD/遮挡剔除失效；还会打乱排序，影响 early-Z。
- 追问 3：GPU-Driven 的边界在哪？→ 剔除与提交都在 GPU，但需要 GPU 侧可见性缓冲与 indirect 参数；难点在**与 CPU 侧逻辑的一致性**（比如射线检测、动画事件仍要知道真实位置）。

**坑**
- 把 drawcall 数当作 KPI。**要看的是 CPU 提交时间与 SetPass**，不是数字本身；TA 面试说"我从 2000 降到 200"却没提测量条件，会被追问塌。
- 说"合批永远是好的"。**剔除粒度被破坏**是它的主要代价，必须主动说出来。

### Q13. 纹理采样：mipmap、LOD、各向异性过滤

**答（背这段）**
> mipmap 是一张纹理的**预计算金字塔**，每层是上一层的一半分辨率。采样时根据屏幕上的导数选合适的层，把"一个像素覆盖很多纹素"造成的走样（摩尔纹、闪烁）变成预平均，代价是约 33% 的额外显存。
> **LOD（层级）怎么选**：取 UV 对屏幕坐标的导数，算出纹素与像素的比率，取其 $\log_2$ 就是 LOD；硬件还会用 $\max$ 或 $\min$ 来避免过度模糊。
> 各向异性过滤处理"斜看平面"的情况：UV 在两个方向上的缩放差异很大，各向同性 mipmap 只能选一个层、必然一边糊一边闪；各向异性采样沿长轴多次采样再做加权平均，代价与采样次数成正比（2x/4x/8x/16x）。

**细节／公式**
理想 LOD：

$$
\text{LOD} = \log_2\!\left(\rho\right),\quad
\rho = \max\!\left(\left\|\frac{\partial u}{\partial x},\frac{\partial v}{\partial x}\right\|,\ \left\|\frac{\partial u}{\partial y},\frac{\partial v}{\partial y}\right\|\right)
$$

$\rho$ 就是"一个像素跨了多少纹素"。

**追问会问什么**
- 追问 1：LOD 取 $\max$ 还是 $\min$？→ 取 $\max$ 更保守（保证不过度模糊到闪烁），代价是斜面上会偏糊；硬件实际是 $\log_2(\max)$ 后再做层间三线性插值。
- 追问 2：什么是 trilinear？→ 在相邻两层 mipmap 之间再插值一次，消除层切换的硬边（代价是 8 次纹理采样）。
- 追问 3：什么时候要手动指定 LOD？→ 程序化生成的噪声/流场（要保证不同像素间一致，避免抖动）用 `tex2Dlod` 强制某层；后期需要锐度时用负 LOD 偏置（会增加闪烁）。

**坑**
- 忘了 mipmap 的前提是 UV 连续。**UV 在三角形内是不连续的（硬边接缝、立方体面之间）会算错 LOD**，导致接缝处突然变糊——这是"接缝处有明显模糊带"的常见原因。
- 说"各向异性过滤没有代价"。它是**带宽杀手**，移动端通常只用 2x 甚至关闭。

### Q14. `ddx` / `ddy` / `fwidth` 是什么？用在哪些地方？

**答（背这段）**
> 它们是**屏幕空间偏导数**：`ddx` 是当前片元的值相对右邻像素的变化率，`ddy` 相对下邻。硬件在一个 2×2 的像素块（quad）里并行执行着色器，用相邻像素的差值就能近似出来。
> 用途有三类：**纹理 LOD 的计算**（上面那个 $\rho$）、**屏幕空间抗锯齿/边缘检测**（`fwidth` 给出变化幅度，用来把硬阈值变成软过渡）、以及**屏幕空间效果的尺度估计**（把世界空间尺寸换算成像素尺寸，避免远处过采样）。

**细节／公式**
- `fwidth(x) = abs(ddx(x)) + abs(ddy(x))`，常用来做"一个像素宽"的线。
- 溶解效果的经典写法：

```hlsl
float noise = tex2D(_NoiseTex, uv).r;
float edge  = fwidth(noise) * _EdgeWidth;
float mask  = smoothstep(_Threshold - edge, _Threshold + edge, noise);
clip(mask - 0.5);
```

`fwidth` 的作用是让边缘宽度**恒定为一个像素**，无论噪声频率和距离多远——这正是它比固定宽度更稳的原因。

**追问会问什么**
- 追问 1：为什么必须在 2×2 quad 里算？→ 因为需要邻居的值。这也解释了为什么 `ddx` 在**非均匀控制流**里结果是未定义的：quad 里的像素如果走了不同分支，硬件没法保证一致性。
- 追问 2：quad 对性能有什么影响？→ 一个三角形只覆盖 1 个像素，quad 里另外 3 个像素仍然要走一遍着色（helper invocation），**小三角形浪费 4 倍着色**——这是"大量微小粒子/叶片"性能差的根因之一。
- 追问 3：`ddx` 能用在顶点着色器吗？→ 不能，它需要 2×2 像素块，只在片元（像素）着色器可用。

**坑**
- 在 `if` 分支里用 `ddx` 然后期待稳定结果——**未定义行为**，移动端上常表现为随机噪点。
- 拿 `fwidth` 当"通用抗锯齿"。它只提供变化率，怎么用还得自己设计。

## 六、阴影与后处理

### Q15. Shadow Map 的原理、常见瑕疵与对策

**答（背这段）**
> 从光源视角渲染一张**深度图**，然后在主相机视角把片元变换到光源空间，比较"该点到光源的距离"与"深度图里存的距离"，大于就说明被遮挡。
> 三个经典瑕疵：**shadow acne**（自遮挡条纹，因为深度图与着色点采样位置不一致）、**peter-panning**（物体与阴影脱开）、**锯齿/硬边**。
> 对策：acne 用 **深度偏移（bias）+ 法线偏移（normal offset）** 或**正面剔除**；peter-panning 是 bias 过大的副作用，要用 normal offset 而不是单纯加大 bias；硬边用 **PCF**（在阴影贴图上多点采样做滤波）或 **VSM/ESM**（用可滤波的表示，代价是漏光）。分辨率不足靠 **CSM（级联阴影）**，把视锥按距离分层、近处用高分辨率。

**细节／公式**
- bias 的本质是把比较距离往前推一点，让自遮挡面不与自己比较。斜率相关 bias（根据面法线与光线夹角调整）比固定 bias 稳。
- CSM 的分层：通常按对数分布分 3–4 级，交界处做混合（blend）避免可见的级联接缝；每级的阴影贴图可以单独控制分辨率与更新频率（远处可以隔帧更新）。
- VSM 存的是深度的**一次与二次矩**，用切比雪夫不等式估计遮挡概率，因此可以被硬件线性滤波——代价是**漏光（light bleeding）**，在遮挡体与被遮挡体距离远时尤其明显。

**追问会问什么**
- 追问 1：为什么用正面剔除（front-face culling）能减少 acne？→ 因为它让阴影贴图记录的是**背面**深度，遮挡体本身的正面就不会与自己比较，等于把整个物体往后推了一个厚度。
- 追问 2：动态物体和静态物体怎么分开？→ 静态阴影可以烘进 lightmap / 一次渲染后缓存；动态的每帧或按需更新；这就是级联 + 缓存（cached shadow map）的思路。
- 追问 3：接触阴影（contact shadow）为什么重要？→ 单张 shadow map 的分辨率永远不够贴住脚底，接触阴影用屏幕空间的射线步进补上这块高频细节，是"看起来扎实"的关键。

**坑**
- 把 acne 和 peter-panning 混起来说，或者以为"bias 大一点就好了"——**bias 越大越脱**，这是因果说反。
- 忘了阴影的开销与光源数量、更新频率、分辨率直接相关（一个高分辨率点光源阴影可能比整个场景还贵）。

### Q16. 后处理链的顺序为什么是那个顺序？

**答（背这段）**
> 一个通用顺序是：**抗锯齿相关（时域用速度矢量）→ 曝光/自适应亮度 → 色彩分级与色调映射 → Bloom → 景深/泛光等镜头效果 → 噪点/胶片颗粒/暗角 → 色调映射（或在其后）→ 最终输出**。
> 原则有两条：**一是按"物理发生顺序"**——光线在镜头里发生的效果（bloom、景深、镜头脏污）要在色调映射附近或之后；**二是按"需要什么数据"**——需要 HDR 范围的效果必须在色调映射**之前**，需要线性的必须在色彩转换**之前**。

**细节／公式**
- **HDR 是分界线**：曝光、bloom、镜头光学效果都必须在线性 HDR 空间做；色调映射把它压到显示范围后再做"看起来像 UI 的东西"（脏污叠加、有色噪点、色调分级的一部分）。
- 顺序错了的两个典型症状：
  - **先色调映射再 bloom** → 高光被压到 1.0 以内，bloom 没有可提取的亮部，光晕极其微弱、且不随曝光变化；
  - **在 sRGB/gamma 空间做混合或模糊** → 亮部扩散不自然、边缘发灰、整体偏亮（因为不是在物理线性空间平均能量）。
- TAA 通常要在**色调映射之前**（在 HDR 线性空间做累积），否则高光累积会失真；但具体实现有分歧，需要看引擎约定。

**追问会问什么**
- 追问 1：为什么后处理要用全屏三角形而不是全屏四边形？→ 三角形没有对角线接缝、且能省掉一次边的光栅化；更重要的是一次采样覆盖，配合 `SV_VertexID` 直接生成 UV，省掉顶点缓冲与插值带宽。
- 追问 2：后处理的带宽代价怎么估？→ 每个 pass 读写一整张全屏 RT：$W\times H \times \text{bpp} \times 2$ 字节；1080p、RGBA16F、10 个 pass ≈ 660 MB/帧，60fps ≈ 40 GB/s——**这就是"后处理链要合并 pass" 的量化理由**。
- 追问 3：怎么减少 pass 数？→ 合并多个效果到一个着色器里一次算完、降分辨率处理（bloom、景深用 1/2 或 1/4 分辨率）、用 compute 一次读写多张。

**坑**
- 顺序说不清就往下讲细节——**面试官最想听的就是顺序背后的理由**。
- 忽略 RT 的**格式与精度**：中间 RT 用了 8 位就丢了 HDR 信息，后面再怎么处理都是错的。

### Q17. 半透明与折射：从 Beer-Lambert 说起

**答（背这段）**
> 光穿过吸收介质时按指数衰减，这就是 **Beer-Lambert 定律**：透射率 $T = e^{-\sigma_t d}$，其中 $\sigma_t$ 是消光系数、$d$ 是穿过的距离。它同时描述了"吸收"与"散射"造成的能量损失，是水体、玻璃、雾、以及屏幕空间体积光的基础。
> 工程上还有几个配套件：**折射**在屏幕空间用"抓取背景 + UV 偏移"近似（真实折射需要光路追踪）；**菲涅尔**决定反射与透射的比例（Schlick 近似，注意透射要乘 $(1-F)$ 保持能量守恒）；**厚度**要么用模型厚度近似，要么用视差贴图/屏幕空间深度算真实厚度。

**细节／公式**
- 分段介质的累积：$T = \exp\!\left(-\sum_i \sigma_{t,i}\,\Delta d_i\right)$；**注意"累加密度再取指数"与"逐段取指数再相乘"是等价的**，但把多段的透射率简单相加是错的——这让很多体积雾的实现偏亮。
- 与渲染方程的关系：体积散射就是在路径上对渲染方程做积分，加入内散射项；实时实现就是 ray-marching。

**追问会问什么**
- 追问 1：为什么水体颜色会随深度变化？→ 因为穿透路径变长、透射率按指数下降，且不同波长的 $\sigma_t$ 不同（红光衰减快 → 深水偏青蓝）。
- 追问 2：屏幕空间折射的失效场景？→ 背景被别的透明物体遮挡、UV 偏移采到画面外、以及视线与表面接近垂直时的扭曲失真；要配套 clamp 与边缘处理。
- 追问 3：为什么半透明的"厚度"很难算？→ 因为它需要"从该片元往视线方向穿过多厚的水"——屏幕空间只有当前深度，真正的厚度需要背面深度或预先烘焙的厚度图。

**坑**
- 把"密度累加"直接当成"不透明度累加"。**必须走指数**，否则厚处会过饱和或不够黑。
- 忘了能量的另一半：反射与透射共用一个 $F$，写了反射不乘 $(1-F)$ 就凭空多出能量。

### Q18. 一个效果"看起来不对但没报错"，你怎么排查？

**答（背这段）**
> 我会把它变成**可判定的问题**，分四步：
> **第一步，确定参考**——先问清"对"是什么：是参考图、是数值、还是某条物理约束（能量守恒、白炉测试）？没有参考就先造一个。
> **第二步，缩到最小**——关掉其它所有效果、把场景简化成一个球/一个平面、把材质参数推到极端（纯白、粗糙度 0/1、金属度 0/1）。极端值最能暴露问题。
> **第三步，逐环节验证数据**——用 RenderDoc / Frame Debugger 抓帧，把中间结果可视化出来（法线用颜色画、粗糙度用灰度画、光照拆成逐项画）。**逐个通道看，而不是看最终画面**。
> **第四步，二分定位**——把链路从中间切开（直接输出上半段结果），确定问题在切点之前还是之后，然后递归。这比逐行读代码快得多。

**追问会问什么**
- 追问 1：为什么"极端参数"有效？→ 因为大多数错误是"某个量的尺度或空间错了"，极端值会把量级差异放得极大，同时也排除掉复杂的相互作用。
- 追问 2：怎么验证一个光照结果是对的？→ 白炉测试（$f_r$ 半球积分应等于 1、结果应是均匀的）、单光源解析对照、以及能量守恒检查。
- 追问 3：怎么防止"修好了但说不出为什么"？→ 记录假设 → 做最小实验 → 用判据确认 → 写回去。**能复述因果链才算修好**。

**坑**
- 一上来就改代码试。这是"碰运气"，面试官听到会认为你没有方法论。
- 只说工具名不说**判据**。"我会用 RenderDoc" 是入门答案，"我会看 G-Buffer 的哪一条通道、判据是什么"才是 TA 的答案。

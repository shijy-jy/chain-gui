# 基础渲染管线：阶段、坐标空间与现代变体

## 先分清"管线"的两层意思（面试第一句就该澄清）

1. **GPU 图形管线**：硬件/驱动的固定流程，把顶点数据变成屏幕像素。这一层是**所有引擎共有**的。
2. **引擎的渲染管线**：引擎对"这一帧怎么画"的组织方式——哪些 pass、什么顺序、怎么出图（Built-in / URP / HDRP，前向 / 延迟 / Forward+）。**`URP-RenderFeature插入点与依赖` 与 `后处理链顺序` 讲的都是这一层。**

面试被问"讲讲渲染管线"，先给结构（"我分三个层次讲：GPU 阶段、坐标空间、引擎层面的变体"），再展开。

## 一、GPU 图形管线的阶段

| 阶段 | 子步骤 | 在哪里可编程 |
|---|---|---|
| **① 应用阶段**（CPU） | 剔除（视锥/遮挡）、排序（不透明前到后、透明后到前）、**合批/实例化**、设置渲染状态（RT、混合、深度、模板、UBO）、**提交 draw call** | 否（引擎/应用代码） |
| **② 几何阶段** | **顶点着色器** → 图元装配 → （几何着色器 / 曲面细分，可选）→ **裁剪** → 透视除法 → 视口映射 | **顶点着色器** |
| **③ 光栅化阶段** | 图元 → 片元：覆盖测试（像素中心规则）、属性插值（**透视校正：按 $1/w$ 插值**）、MSAA 覆盖 | 否（固定功能） |
| **④ 像素处理阶段** | **片元着色器** → 逐片元操作：深度测试 → 模板测试 → 混合 → 写入帧缓冲（含 sRGB 编码） | **片元着色器** |

**三个最容易被追问的点**：

- **裁剪在齐次空间做**（在 `÷w` 之前）——因为 `w` 可能为负或为 0，先除法会把顶点甩到无穷远。
- **合批/实例化的价值是减少 CPU 提交与状态切换**，不是减少 GPU 工作量——所以"减少 draw call"这句话在软件光栅化（如 `render_unified_oss` 的 CUDA 光栅）里**不适用**。
- **early-Z 有前提**：片元着色器不写深度、不 `discard`、不改深度测试状态。一旦 `discard`（溶解/软粒子常用），深度预测试失效——移动端 TBDR 上还会破坏 HSR（见 `LOD与剔除手段`）。

## 二、坐标空间链（把管线串起来）

$$\text{模型}\xrightarrow{M}\text{世界}\xrightarrow{V}\text{观察}\xrightarrow{P}\text{裁剪(齐次)}\xrightarrow{\div w}\text{NDC}\xrightarrow{\text{viewport}}\text{屏幕}$$

- **法线**必须用 $M$ 的逆转置变换（推导见 `变换与坐标系`）；
- 观察空间的正负方向、NDC 的深度范围、**反向 Z**（`UNITY_REVERSED_Z`）都是约定——写反的症状很典型（雾在天空像素上判断错，`TA_show` 踩过）；
- 透视除法之后做**透视校正插值**：重心坐标要先除以 $w$，否则纹理在透视下会扭曲。

## 三、现代管线的关键变体（体现"知道为什么"）

| 变体 | 核心思想 | 代价 |
|---|---|---|
| **前向渲染** | 每个物体、每盏灯算一次；适合少灯 | 多灯时重复着色 |
| **延迟渲染（G-Buffer）** | 先写几何属性，再统一做光照：**光照次数与物体数解耦** | 带宽大、透明物体与 MSAA 不友好 |
| **Forward+（URP 默认）** | 分块（tile）收集灯光列表，前向着色只取本块相关的灯 | 需要 pre-pass 建立灯光列表 |
| **TBDR（移动端）** | 分块渲染，片元在 tile 内存中完成，HSR 省掉被遮挡的着色 | `discard`/混合会破坏 HSR |
| **GPU-driven** | 剔除与绘制都在 GPU 上做（indirect draw + compute） | 调试困难、CPU 侧不可见 |
| **光追 / 混合** | 用 BVH 求交代替光栅化（`render_unified_oss` 的路径追踪后端） | 代价高，实时需降噪（ReSTIR/SVGF） |

## 四、映射到我的项目（面试加分的落点）

- **`TA_show`**：全屏雾插在 `AfterRenderingOpaques`（就是"在不透明阶段与透明阶段之间"）；湿地倒影是**把整条管线用镜像相机再跑一遍**到 RT——这是"管线可以被整体复用"的最直观证据。
- **顶点阶段干活**：41 万顶点能量网格的 LOD 用**顶点退化**（`positionCS=(2,2,2,1)`）实现，省的是光栅化之后的成本（顶点着色器照样跑）。
- **片元阶段的 `discard`**：溶解与软粒子都用它，因此必须知道 early-Z 的代价。
- **`render_unified_oss`**：GPU 计算在 CUDA，显示层是**固定管线 GL + PBO + CUDA-GL 互操作**——它不走经典图形管线，说明"管线"是**可替换的组织方式**，不是唯一答案。

## 五、可能被追问的三层

1. **原理层**：为什么裁剪要在齐次空间做？透视校正插值的数学来源（为什么是 $1/w$）？early-Z 与 late-Z 的差别？为什么延迟渲染对 MSAA 不友好（G-Buffer 的采样数暴涨）？
2. **实现层**：一次 draw call 在 CPU 侧包含哪些开销？顶点着色器里能做什么、不能做什么（不能创建/销毁图元、不能访问其他顶点）？`discard` 具体破坏了什么（深度预测试与 TBDR 的 HSR）？
3. **边界层**：什么时候该用延迟而不是前向？TBDR 架构下要避开哪些写法？GPU-driven 管线的调试怎么做？光栅化会在什么情况下被光线追踪取代（以及为什么短期不会全面取代）？

## 八、补强（来自 2026-09-22 模拟追问，详见 `模拟追问记录`）

追问中暴露的四个精度问题，这里逐条钉死：

1. **裁剪空间的 $w$ 不是恒定的**。透视投影下 $w_{clip}=-z_{view}$，各顶点不同；只有**正交投影**才是 $w\equiv1$。
   正确表述：视锥在齐次裁剪空间里由 **6 个线性半空间（平面）**界定 → 裁剪只需平面点积判内外，边与平面求交是**线性插值**，跨近平面的三角形能正确**生成新顶点**。**不能先做 $\div w$**：$w\le0$（相机后方）的顶点除完会翻转或飞向无穷。
   顺带钉一个相关事实：**裁剪空间的深度线性可比，NDC 的深度是非线性的**（$1/z$ 才线性）——这正是深度精度问题的根源，也是反向 Z 存在的理由。
2. **early-Z 主要用在前向渲染**（不是延迟渲染），且有**前提**：片元着色器不写深度、不 `discard`、不改深度状态。`discard` 破坏的正是这个前提 → 硬件退回 **late-Z**（深度测试放到着色之后，被遮挡的片元也已经着色完了）。另外 **depth pre-pass**（先只写深度再重画一遍）是"手工 early-Z"，复杂场景常用。
3. **G-Buffer 存的是几何/材质属性**（albedo、法线、粗糙度、金属度、深度、运动矢量…）；**光照、AO、阴影是用这些属性在后续 pass 算出来的**，不是预先渲染进 G-Buffer。
4. **背面被剔除是 cull mode 干的事，不是 `discard`**。`discard` 是片元着色器主动丢弃该片元，典型用途是 alpha test。

**另补：一次 draw call 到底贵在哪**（面试高频）——瓶颈是**状态变化**而不是顶点数据本身：① 状态切换（shader program、RT/混合/深度/模板状态）；② UBO/常量缓冲的绑定与上传；③ 资源绑定与必要的同步/屏障；④ 命令写入命令缓冲；⑤ 驱动侧的校验与批处理。这解释了合批/实例化/GPU-driven 为什么有效，也解释了"减少 draw call"在软件光栅化（无 GL 管线）场景下不适用。

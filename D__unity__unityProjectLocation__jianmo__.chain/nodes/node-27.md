### ⚠️ 两个重大发现（都是坑，值得记）

**坑 1：孤儿数据块不会被渲染，也不会被保存**

`CityGround` / `Buildings` / `Buildings.001` / `Fountain` / `Ground` / `Ground.001` 这些对象
**`users_collection` 是空的**（不在任何集合里）。它们只存在于内存的 `bpy.data` 中，
**因此既不参与渲染，`save_as_mainfile` 也不会写入文件**。

诊断方法：`o.users_collection` 为空 + `o.name in bpy.context.view_layer.objects` 为 False。
修复：`bpy.context.scene.collection.objects.link(o)`。

> `CityGround` 即使重新挂载后**依然不渲染**（对象属性与渲染正常的 `City` 完全一致，
> 2400 个 1×1 面、法线朝上、单位矩阵）。它是坏数据，不要依赖它。

**坑 2：相机 `clip_end` 默认 100 —— 俯视时把地面裁掉**

把相机放到 `z = 100` 正交俯视 40×60 的地图时，地面正好落在裁剪面上被裁没，
**只有高 9 单位的建筑侥幸留下**，画面里那片"背景灰"其实是裁掉地面后的世界背景。

现象极具迷惑性：看起来像"地面材质丢了"，实际是相机裁剪。
```python
cam.data.clip_end = 1000.0     # 或者把相机放到 z = 60
```
判据：如果**建筑能渲染、地面不能**，且相机距离 ≈ 100，就是它。

### 真正的原因（"考虑整体"的具体含义）

用**场景里真实建筑几何**当障碍后又变成一盏都放不下 —— 因为**建筑连屋檐带台基正好顶到路边，路缘外侧一丁点余量都没有**。

### 三项修复

**① 建筑在地块内内缩**（`build_landmarks.PLOT_INSET = 0.45`）
```python
def plot_size(key):          # 地块 bbox -> 建筑实际占地
    w, d = FOOTPRINT[key]
    return max(2.0, w - 2*PLOT_INSET), max(2.0, d - 2*PLOT_INSET)
```
所有地标与自动民居都改用它。依据写在注释里（实测 3.94 vs 5）。

**② 障碍按"单体"算，不按合并对象算**
`LM_Houses` 是 12 栋合并成的**一个对象**，它的包围盒是 **12 栋的并集**，
几乎覆盖整个城区 → 所有候选位置都被判为"在建筑内"（净距全 0）→ 一盏都放不下。
现在改为：地标用各自包围盒，12 栋民居用 `fill_houses()` 返回的 `made` 表**逐栋**登记。

**③ 位置按参考图规律固定偏移，不最大化净距**
`solid` 探测道路边缘 → 灯放在**路缘外 0.70 格**（依次退让 0.50 / 0.35），
两侧都试取更近的一侧，都不行才跳过。实测参考图是 0.65 格 ✓

### 结果

```

仍在路面上的灯：0 盏
```

### 教训（写进规范）

1. **"最大化某个指标"往往不是正确答案。** 参考图的规律是"离路缘固定 0.65 格"，

2. **合并对象会破坏几何查询。** 做避让/碰撞/净距计算时，

3. **建筑占地不等于地块。** 参考图里的 bbox 是**地块**，建筑内缩其中；

## 最终方案：路灯**直接从参考图检测**，不再推算

### 为什么早期检测失败、后来成功

**失败原因**：早期用"暗像素数量"当特征，噪声太大（围栏、建筑阴影全命中）。

**根因（这次才查明）**：灯的调色板是深藏青
```
(40,48,88) ×39   (64,72,104) ×25   (96,96,120) ×9
灯罩 (128,128,136) ×14   (200,208,224) ×13
```
**围栏用的是同一套颜色** —— 实测围栏格 `(40,48,88)` 有 **80 个像素，比灯的 39 还多**。
所以**按颜色检测必然把围栏一起捞进来**。

**两者形状完全不同：**
```
灯    1 格宽 × 2 格高的**竖条**（灯头 + 细灯杆 + 底座）
围栏  1 格高 × 多格宽的**横条**
```

### 检测算法（`detect_lamps.py`）

1. 逐格统计**深藏青像素数**（三种调子，容差 30），≥20 为候选格
2. 候选格做**连通块**（4 邻域）
3. **只保留"宽 1、高 1~2"的竖条** → 排除围栏

实测连通块形状分布：
```
(1,2) × 15   ← 灯 ✓
(1,1) × 2    ← 灯的残块 ✓
(16,53) × 1  ← 围栏横条 ✓ 正确排除
(17,47) × 1  ← 围栏横条 ✓ 正确排除
(2,1) × 4 / (3,3) (5,3) (6,5) (7,3) (9,6) (9,12) (13,2) ← 其它图形元素
```

**检出 17 盏**。坐标换算：检测输出 (col, row) 是格角坐标 → **模型 x = col，y = -row**。

### 为什么这个数才是对的

我此前用几何推算得到 **35 盏 —— 是参考图的 2 倍**。
人工数官方地图上的灯也就是 17 盏左右。**推算会系统性地偏多，直接检测才准。**

> 改完还发现徽标被正面竖肋挡住下半部分 —— 因为竖肋伸到 `y0-0.14`，
> 而徽标只在 `y0-0.10`。把徽标移到 `y0-0.30`（竖肋前面）才对。

## 修正：地面假水面 + 两栋建筑宽度不一致

用户从近景又指出两点：
> "地面上的蓝色色块是什么，参考图没有，另外参考图里面两个建筑的宽度明显一样，这里怎么不一样"

### ❌ 问题 1：地面上出现参考图没有的**蓝色色块**

**根因：颜色分级把蓝色屋顶误判成水面。** 友好商店的蓝顶颜色接近水面色 `(89,191,232)`：

```
实测 rustboro_tiles_color.json 第 43 行：
  col15='W'  col16-17='DD'  col18='W'     ← 精灵/商店位置的蓝色被当成水
rustboro_layout.json 里同样是 'WWWW'
```

地面于是就在建筑底下画出了蓝方块。

**两层修复：**

**① 建筑占地遮罩** —— `build_ground(mask_boxes=[...])`，落在建筑矩形内的格子一律铺沙地。
但那只盖得住建筑**底下**的，盖不住**散在旁边**的（道馆下方、中心旁边、底部都有孤立蓝格）。

**② 水面连通性剪枝** —— `_prune_water()`：城区的正确水体只有左侧那片海，
所以做连通块分析，**只保留与左边缘连通（或面积 ≥40 格）的水体**，其余 `W` → 沙地。
实测剪掉 **31 个孤立水格** ✓

```
修复前: {W:179, P:942, ...}
修复后: {W:129, P:1326, ...}    ← 城区的假水面清零
```

> **教训**：颜色分级是"按最近色归类"，**蓝色物体一律会落进水类** ——
> 屋顶、阴影、冷色高光都是。用之前必须做**空间约束**
> （这里用"与主体连通"这一条就解决了）。

### ❌ 问题 2：两栋建筑宽度不一样

**实测参考图：**

## ⚠️ 修正：道馆**整个转反了 180°**

用户指出："**建模建反了**"。

### 原因

我当初判断"入口朝北临主街"，给道馆设了 `rotation_euler = (0,0,180°)`。

**但 2D 地图是俯视图，所有建筑的立面一律画在下方（朝南）** ——
参考图上道馆的**屋顶在上、门窗与招牌在下**，说明正面朝南。我却把它转了 180°，正面朝北 ✗

### 修复 + 全城核对

写了一次**朝向扫描**，逐个列出所有建筑的 `rotation_euler.z`：

```
Devon_* (9 个部件)    rotZ = 0.0°
LM_CutMaster          rotZ = 0.0°
LM_Gym                rotZ = 180.0°   <== 唯一被旋转的
LM_HouseA / HouseB    rotZ = 0.0°
LM_PokeMart           rotZ = 0.0°
LM_PokemonCenter      rotZ = 0.0°
LM_School             rotZ = 0.0°
```

**只有道馆一个被旋转** → 已改回 `rotZ = 0`。

### 教训

**俯视图里的"朝向"要从精灵的绘制方式反推。**
2D 地图把建筑画成"屋顶在上、立面在下"，这个约定本身就说明了**正面朝南**；
我却用了"哪边有路就让正面朝哪边"的**推理**，而不是**读图**。

→ 又一次印证：**能从参考图直接读出来的，就不要推理。**

### 建议固化成检查项

**每建完一栋，跑一次"朝向扫描"**（列出 rotZ），确保所有建筑统一朝南。
这类错误从单个建筑的渲染图上很难看出（正面照样好看），
只有**和地图对照**或**列出旋转值**才能发现。

> 触发：怎么核对渲染结果；像素分析；千问视觉引擎好不好用；VLM 能不能信

**类型：任务　状态：完成**

## 第一部分：确定性测量工具

`analyze_render.py`：把 PNG 转成可复算的数字与文本。

输出：对象掩码、覆盖率、包围盒、**四边留白**（判断有没有被裁切）、主色分布、指定扫描线的实心/空隙分段、ASCII 轮廓图、ASCII 颜色图。

设计要点：

- **背景色从图像边框取中位数估计**，不写死——渲染背景会随世界设置变。
- 颜色分类阈值不能太敏感：暖色石材 `rgb(132,108,108)` 会被 `r > b+18` 误判成"红"。**工具的判据本身也要被检验。**
- ASCII 轮廓是把掩码降采样后按占比填字符——用文本"看"形状。

## 第二部分：视觉引擎接入

本机视觉引擎 = llama.cpp `llama-server` + **Qwen2.5-VL-3B**（Q4_K_M + mmproj-F16），监听 `127.0.0.1:8080`。

- **modlens 桥驱动不了它**（llama-server 无法强制结构化输出契约），所以走 REST 直连 `/v1/chat/completions`。
- 交付 `vision_read.py`（命令行，支持 `--region` 裁切 + `--zoom` 放大）与 `vision_server.py`（MCP 工具 `ask_image`）。

## 第三部分：量化能力边界（本次最重要的产出）

先做**管道正确性对照**，排除"是我传图坏了"：

| 输入 | 提问 | 回答 | 判定 |
|---|---|---|---|
| 纯红合成图 | 什么颜色 | `Red` | ✅ 管道正常 |
| 合成图 | 照片还是纯色 | `Flat single colour.` | ✅ |
| 塔渲染 | 主体是什么颜色 | `Blue` | ✅ |

再做**判别力对照实验**——同一张渲染图，一块紧贴孔洞、一块同尺寸实心板面，同一问题各问 3 次：

| 区域 | 真实情况 | 3 次回答 |
|---|---|---|
| 紧贴孔洞 | **有孔** | YES / YES / **NO** |
| 实心板面 | **无孔** | NO / NO / **YES** |

**两者答案分布完全重叠。** 它不是在读图，是顺着问句语气作答。甚至出现自相矛盾输出："No, there is no hole... The shape is a circle."

辅助观察：

- **放大是最大的准确率杠杆**：全幅 640×640 问小孔 → 答"没有"；同一区域 2× 裁切 → 答"有，圆形"。
- **开放式描述不可用**：让它描述刚答对过的裁切图，它编出"两个球浮在蓝色液体里"。
- **凸起物会被误判成洞**：平放在板上的球被读成"中心圆孔"。

## 结论

**可以用**：主色调、整体布局、场景类型等粗粒度定性判断。
**不能用**：细小特征的存否、精确位置、部件计数、开放式描述。

精确几何一律走 `analyze_render.py`（实测它算出的孔位 208–278px 对得上理论值 207.6–285.8）。

若要让视觉判断真正可靠，需换 7B 模型（约 4.5GB，本机 4060 8GB 大概率可跑）——**未验证**。

## 试错记录

- ⚠️ **顺手发现渲染色彩偏差**：默认 `opengl`/workbench 工作室光照会压暗饱和色——`base_color=[0.92,0.35,0.2]` 的红球渲出来像素值仅 `rgb(156,108,84)`，视觉模型读成 "brown"。**要判色准必须用 `engine='eevee'`。**
- ⚠️ **MCP 服务端是长驻进程**：改完 `vision_server.py` 不会自动重载。第一次调用返回的还是旧格式，才发现 DSH 跑的是旧代码。触发重连的办法是改一下 `cordis.patch.yml` 里对应条目。
